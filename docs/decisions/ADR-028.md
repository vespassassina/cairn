# ADR-028: Pages record when their facts were last verified

Status: accepted
Date: 2026-09-14
Relates to: ADR-008 (revisions), ADR-009 (review console), ADR-011 (server instructions), ADR-013 (three surfaces), ADR-016 (export), ADR-023 (sync), ADR-027 (sources)

## Context

The roadmap item "Freshness: `verified_at` on pages" asked for when a fact was last confirmed, separate from when the page was last edited. A page's update time says nothing about whether its facts still hold: a typo fix moves it, and a page nobody has touched in a year may still be right. ADR-027 records where a fact came from; this records when someone last checked it.

The owner said "done, do next" and was asked four questions. They chose the recommended answer each time:

1. **How a page gets marked verified: a flag on a write.** `update_page`, the CLI's writes and the console editor take `verified: true`. A check that changes nothing else is an append with no text and the flag, with a change note saying what was checked. Rejected: a separate `verify_page` tool, which adds to the tool list every session loads for something an existing tool can carry; and counting every edit as a verification, which would make the field another update time.
2. **What a new page starts with: verified when created with sources.** A page created with at least one source counts as checked at creation, since whoever wrote it just read the source. One created without sources starts never verified. Rejected: every new page verified, which makes the field mean nothing for pages written from memory; and every new page unverified, which marks a freshly cited page as stale.
3. **Where freshness shows, and how old is stale: the age everywhere, no threshold.** The console shows "Verified 3 months ago" or "Never verified" on each page and has a list of pages, least recently verified first. `get_page`, search hits and the REST views carry `verified_at`. Rejected: a staleness threshold, which would need a number that suits a price list and a peptide's mechanism alike, and a setting to hold it.
4. **What it applies to: pages only.** Rows keep their sources (ADR-027) but no verification time. Rejected: rows too, which adds a field to every row in every `query_table` result for something a table's page can say for the whole table.

## Decision

1. **`verified_at` is a nullable time on every page,** stored with it and part of every revision's snapshot. Null means never verified.
2. **A write sets it in one of three ways.** With `verified: true`, it becomes the write's own time, which is also the page's new update time and the revision's time. With an exact `verified_at`, it takes that value, which is what import, sync and restore need; the value must be an ISO 8601 time no more than a day ahead, and is stored normalised to UTC. With neither, an update keeps the page's value, and a create takes the write's time if the page has sources and null if it has none.
3. **History tells a verifying write from one that carries the time over.** A revision verified the page when its snapshot's `verified_at` equals the revision's own time. The console marks it with a "verified" chip in the timeline and a line on the revision; MCP `get_revision` and REST return `verified: true`; `cairn revision` prints "verified: the page's facts were re-checked". Restoring a revision brings back its `verified_at`, so restoring text from before a check also restores the older check. Revisions written before this ADR have no `verified_at`; restoring one keeps the page's current value.
4. **Agents mark it through `update_page`.** `verified` is an optional boolean, and works with empty content in append mode. The server instructions and the skill gain one sentence each: when you re-check a page and it still holds, pass `verified: true`. MCP search hits carry `verified_at` only when it is set, so an unverified hit costs what it did.
5. **REST:** `PATCH` on a page takes `verified: true`; `PUT` takes `verified_at` as an exact time or null. Page responses and search hits carry `verified_at`, and the Markdown view has a `verified:` line, "never" when null.
6. **CLI:** `--verified` on `append`, `replace-section` and `write`. `cairn append <page-id> --verified --note "why"` needs no text.
7. **Console:** the page's meta line says "Verified 3 months ago", with the exact time on hover, or "Never verified". The editor has a checkbox, "I re-checked this page's facts and they still hold", unticked each time. A Freshness screen lists every page, never verified first (oldest update first), then by verification time, oldest first, with its collection and update time.
8. **It travels with the content.** Export writes a `verified` line in a page's front matter only when set; the format stays at version 2. Import sets the value exactly, null included. Sync hashes `verified_at` only when set, so pages never verified hash as they did before this ADR and the first sync after upgrading copies nothing; every page write sends the value, null included, so a change on one side reaches the other.
9. **SQLite stores it** in a nullable `verified_at` column on `pages`, added to an existing database on start with null for every page already there.

## Consequences

1. The owner can see which facts have gone longest unchecked, and an agent reading a page can see how recently it was confirmed.
2. Verification is a claim, like a source. Cairn does not check that anything was re-read; the change note on the verifying revision says what was.
3. Pages that existed before this ADR all start never verified, even those with sources. The Freshness screen lists them first, which is the honest state.
4. Two writes in the same millisecond, a verify and then an edit, would make the edit look like a verification in history. No person or agent writes that fast; the in-memory test database does, and its test leaves a gap.
5. Context cost, measured with `pnpm context-cost` on this repository's database: MCP from about 3,091 tokens a session to 3,138 (one boolean on `update_page`, one sentence in the instructions, now 1,618 of 2,000 characters). The skill description is unchanged, at about 115 tokens.
6. Rows have no verification time. If one is wanted later, it needs a new ADR, and its cost in `query_table` results is the question to answer.
