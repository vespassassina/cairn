# ADR-051: Cairn climbs down a ladder before it starts, and stops when it runs out of rungs

Status: accepted
Date: 2026-09-16
Relates to: ADR-018, ADR-046, ADR-048, ADR-049, ADR-050

## Context

ADR-046 settled the rule that matters most here: never serve, and never replicate, a database Cairn cannot vouch for. It gave that rule exactly one answer, which was to stop the container.

Stopping is right when the alternative is overwriting the only good copy. It is a poor answer once a good copy exists somewhere else, and since ADR-049 and ADR-050 one does. On 2026-09-15 the Azure Cairn met the case this ADR is about: a truncated transaction reached the replica, `litestream restore` failed to decode it, and the container stopped. There was nothing behind the replica at that point, so stopping was the only honest thing to do. There is now.

The owner had already set the shape, in the direction that started this work:

> "also when starting and db corrupted, catch the error, log, then move the broken version (rename) then check for backup (are we doing backups right?), ingest last good backed up version (by cloning the backup into the current filename), then log the broken one position and what happened."

One rung was missing from that description, and it is the cheapest one. Litestream can restore the replica as it stood at an earlier transaction. A truncated upload is always at the tail, so the transaction before the damage is usually intact, and walking back one transaction costs seconds where a backup costs up to `CAIRN_BACKUP_AFTER_HOURS`.

The rung that is deliberately absent is Litestream's own `auto-recover`. It answers a damaged replica by resetting it from the local database, and on a container that has scaled to zero there is no local database, so it would answer damage by replacing the replica with nothing.

## Decision

1. **There is a ladder, and the order is the whole point.** Each rung loses more than the one above it, so a rung is tried only when the one above it has failed:
   1. The local database, if it is there and passes `integrity_check`. Nothing lost.
   2. A plain restore from the replica. Seconds behind at most.
   3. The newest point in the replica that both restores and passes `integrity_check`. Usually one transaction.
   4. The newest backup that passes `integrity_check`. Up to `CAIRN_BACKUP_AFTER_HOURS` of work.
   5. Stop, and say what was tried and what to do about it.
2. **A restore is not a success until SQLite has read it back.** Every rung ends in `integrity_check` on the file that rung produced. A restore that exits zero and hands back damage is a failure, which is the whole of ADR-046 restated at each rung.
3. **An unreachable replica stops Cairn; it never falls through to a backup.** A network error or a role Azure has granted but not yet propagated says nothing about whether the replica is healthy, and the replica usually is. Recovering from a backup there would throw away good work to route around a firewall rule, and would then replicate the older database over the newer one. Only a replica that answers, and answers with damage, opens the rungs below.
4. **Damage is never retried; everything else is.** A restore that failed on decode, corruption, a checksum or an unexpected end of file cannot pass on the next try, and retrying only burns the platform's restarts and buries the reason. Anything else is retried `CAIRN_RESTORE_TRIES` times, `CAIRN_RESTORE_WAIT_MS` apart, which by default gives a first deploy two minutes for its identity to be granted access to storage.
5. **A database that will not open is moved aside, never deleted,** the moment Cairn decides not to use it, before any rung below writes to that path. It becomes `<database>.broken-<timestamp>`, its write-ahead log and shared memory go with it, and both the log and the final message say where it is and that nothing removes it but the owner. It is evidence, and rows can still be pulled out of it by hand.
6. **The whole replica listing is printed when a plain restore fails.** On Azure the container log is the only place the owner can see what the replica actually held, and when recovery fails that listing is the record they will need.
7. **Recovering from a backup is said loudly, not logged quietly.** It is the one outcome that silently changes what the replica will hold: Cairn starts, Litestream replicates the recovered database, and the replica's own history is replaced by it. That is the intended outcome when the replica could not be read back at all, and the owner is told it happened.
8. **Stopping prints the next steps in the order worth trying**, with the exact `litestream restore -timestamp` command, then export and import from another Cairn, then starting empty, with the warning that the first write overwrites the replica.
9. **The decision lives in `packages/api/src/recovery/ladder.ts` and knows nothing about Litestream, clouds or filesystems.** It is written against an interface of eleven methods. Everything platform specific is in `packages/api/src/entry/recover.ts`, which is where hard rule 13 puts it, and the ladder is therefore tested without a litestream binary, a cloud account or a container.
10. **Recovery runs as its own process before the server,** bundled to `dist/server/recover.mjs` and run by `docker/start.sh`. It needs the replica, the archive and SQLite, none of which belong in a shell script, and it exits non-zero when it has nothing to vouch for, which stops the container as ADR-046 requires.

## Consequences

1. The failure of 2026-09-15 now has three answers before it has none. That case, a replica whose tail will not decode, is exactly rung 3, and rung 3 costs one transaction.
2. Rung 4 is a fork. The recovered database is older than what the replica held, and once Cairn starts, Litestream replaces the replica's history with it. This is why rung 4 is last, why rung 3 exists to usually avoid it, and why it is announced rather than logged.
3. **The `litestream ltx` output format is not verified against the real binary.** Litestream is not installed on the development machine, so rung 3's parser was written against the documented shape rather than against real output. It is deliberately loose: it takes every RFC3339 timestamp from anywhere in the output rather than depending on a column order, so a layout change costs nothing and a wrong guess costs one failed restore. The first real run of rung 3 goes in the changelog.
4. Rungs 1, 2, 4 and 5 are covered by tests against a fake ladder, and the wiring was run end to end against a stub litestream and a folder archive: a truncated local database was set aside, a decode failure walked to rung 3, rung 3 failed, and rung 4 recovered from a real backup file. What has not been run is any of this against a real Azure replica.
5. `check_db` in `docker/start.sh` now applies only to the local-only path, where there is no replica and nothing to recover from. The replica path's own checks all live in the ladder, so the integrity rule is stated once per path rather than twice per path.
6. Three settings are added: `CAIRN_RESTORE_TRIES`, `CAIRN_RESTORE_WAIT_MS`, and `CAIRN_APP_DIR`, which exists so the start script can be tested outside the image.
