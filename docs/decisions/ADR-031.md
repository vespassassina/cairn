# ADR-031: Agents run Cairn from a guide written for them, checked against the code, and the code guides them too

Status: accepted
Date: 2026-09-14
Relates to: ADR-013 (three surfaces), ADR-019 (agent-first install), ADR-029 (instances)

## Context

ADR-019 made installation something an agent does, from `docs/AGENT-INSTALL.md`. Everything after installation had no agent guide: changing a setting, updating, syncing several Cairns, backups, access, troubleshooting. An agent asked to do those had to piece them together from four guides written for people.

The install guide had also drifted. It numbered a step wrongly, still showed a bare `CAIRN_URL=<address> cairn login` where registered instances are now the easier path, and knew nothing of `cairn sync install` or `cairn start`. Nothing checked it.

The same day, `cairn login` failed for the owner with a message that described localhost without saying the CLI had chosen localhost because no Cairn was named (`docs/LESSONS.md`). The owner asked for two things:

1. "we always try to write the best possible useful errors. user needs to be guided as much as possible by the code (hence sensible defaults) even when the user is an agent."
2. "we need to make sure that there is an agent first deployment, configuration and operation guide and that it is up to date."

## Decision

1. **`docs/AGENT-OPERATE.md` is the agent's guide to a running Cairn:** what is running and where its settings and logs are, every setting with its default, health checks, updates, sync, backups and restore, access and secrets, cost, troubleshooting and the hand-over. `docs/AGENT-INSTALL.md` stays the guide to installing, and each points to the other. The rules of ADR-019 carry over: ask before changing anything, credentials stay with the person, never read the private settings files.
2. **A test checks both guides against the code** (`packages/cli/test/agent-guides.test.ts`):
   1. Every `CAIRN_` setting the server, the CLI, the image's start script or the deploy files read is described in the operation guide.
   2. Every `CAIRN_` setting either guide names is read by something.
   3. Every `cairn` command either guide names is one `cairn --help` lists.

   So a new setting cannot ship undocumented, and a renamed command or setting fails the build until the guides follow.
3. **Hard rule 19 widens:** an install, configuration or operation step changes in the person's guide and in the agent's guide in the same commit.
4. **The code guides its user, person or agent,** and this is part of the coding style in `CLAUDE.md` and PRD principle 7:
   1. Every error says what happened, why when it is not obvious, and the exact next step: the command, flag or setting that fixes it.
   2. When the code acted on a default the person did not choose, an error that follows says so, and how to choose.
   3. A sensible default beats a required setting. A setting is required only when no default is safe, and then the error names it.
   4. Messages are written so an agent can act on them without a person: the setting's exact name, a command it can run, no reliance on a screen the agent cannot see.
   5. An error that misled someone is a bug, with a `docs/LESSONS.md` entry.

## Consequences

1. An agent asked to do anything with a running Cairn has one page to follow, with the same safety rules as installing.
2. The test covers names, not meaning: a setting whose default changes, or a step that no longer works, still needs a person to notice. The guides ask the agent to report anything wrong or unclear in its hand-over, which is how those are found.
3. Settings read somewhere the test does not scan (a new deploy target) need adding to it; the test lists where it looks.
4. Existing error messages were written before point 4. They are brought up to it when touched, and when one misleads someone.
