# ADR-060: `cairn sync` never deletes a page it cannot prove was deleted

Status: accepted
Date: 2026-09-18

## Context

ADR-059 recorded the 2026-09-17 loss of eleven pages from Azure as data loss "at the replica level," with Litestream generation inconsistency as "the leading suspect, not confirmed." That diagnosis was wrong, or at least incomplete. On 2026-09-18, running `cairn sync` between the laptop and Azure (as part of redeploying the ADR-059 fix) deleted two more pages from the laptop, the one side that still had good copies of them. Investigating that deletion found the real mechanism, and found it had already happened once before, at the exact timestamp `cairn sync` recorded for all eleven of the original "vanished" pages: `2026-09-17T21:48:33`. The Litestream hypothesis in ADR-059 was never tested; the sync tool's own log was sitting right there.

`cairn sync`'s `plan()` (`packages/cli/src/sync.ts`) compares each record's current hash on both sides against the hash they last agreed on. When one side's hash still matches that agreed base and the other side's snapshot has no entry for the key at all, `plan` concludes the second side deleted it, and schedules a delete on the first side to match. This is right when the record really was deleted: a deleted page is genuinely absent from `readSide`'s enumeration (`GET /export/pages`, which reads only live pages). It is wrong when a page is absent from that enumeration for any other reason: lost through a bug, a bad replica, a `pnpm dev` process that had not picked up a code change (as found in this same investigation, see `docs/LESSONS.md`), or simply never received. `plan` cannot tell these apart, because it only ever sees "present with hash H" or "absent." Absence was treated as proof.

The eleven pages were recovered once already by writing them back to Azure with `cairn import`, per ADR-059. By 2026-09-18, checked directly, Azure again had zero revision history for all eleven: not soft-deleted, simply absent, the same state that prompted the original recovery. Whether that first `cairn import` never actually landed, or landed and was then lost again the same way the originals were, is not established; either way, `cairn sync`'s own saved state (the "last agreed" hash per record, kept per server pair) was never touched by the import, so as far as `cairn sync` was concerned nothing about those eleven records had changed: base still said "we agreed on hash H," Azure's snapshot still had no entry for them, and the laptop still matched hash H. Every run of `cairn sync` from then on would keep proposing the same delete, forever, until it was actually run and the laptop's copies were destroyed for real, which is what happened on 2026-09-18.

## Decision

1. **A delete is only ever applied when the side that appears to have made it can prove it.** After `plan` and `resolveMerges` produce a set of actions, a new step, `verifyDeletes`, checks every `op: "delete"` action against the side it attributes the deletion to: `GET /pages/:id/history?limit=1` on that side. A page's history survives its own deletion (ADR-059 decision 2: history starts from the deletion revision even once the page itself is gone), so any real, API-driven deletion leaves at least one revision behind. An empty history is not evidence of anything, deleted or otherwise: it is exactly what a page that was simply never received, or was lost some other way, also looks like.

2. **An unconfirmed "deletion" is turned into a recreation, not silently dropped.** When history comes back empty, `verifyDeletes` rewrites the action from a delete into a `put`: the content is copied from the side that still has it back onto the side that is missing it, the same direction `cairn import` would have gone. Nothing is destroyed; the run instead heals the gap it would otherwise have caused. This is deliberately biased toward keeping data over deleting it, matching CLAUDE.md's stance that a hard-to-reverse action needs stronger evidence than an easily reversible one, and a wrong "keep" costs a stray page, while a wrong "delete" costs the content.

3. **The run reports what it recreated and why**, one line per record: `<title> (<id>) is not deleted: it has no history at all on <url>, so its absence there is not proof it was deleted. Recreating it there from <url> instead of deleting the copy that still exists.` This is a warning, not silent: the person running `cairn sync` sees it in the command's own output (`report.warnings`) and in a dry run's output, both already-existing places a sync surfaces things worth a second look.

4. **This protection is pages only.** Rows have no history endpoint of their own to check a deletion against (ADR-005: history is a page concern; a table row's change log lives differently), so `verifyDeletes` leaves row deletions as `plan` found them. This is a real, accepted gap, narrower than the one just closed, not an oversight: closing it needs row history first, which is its own piece of work.

## Consequences

1. `cairn sync` can no longer turn "a page didn't make it to the other side" into "delete it everywhere." The eleven pages from ADR-059, and the two more lost on 2026-09-18, would all have been recreated instead of deleted, on every run, until whatever is actually causing the loss on Azure was found and fixed.

2. The real loss mechanism on Azure is still not identified. This ADR closes the sync tool's role in making that loss permanent and repeatable; it does not explain why Azure's copy of these pages had no history at all in the first place. ADR-059's "not confirmed" now applies to the original loss, not to the mechanism that kept repeating it.

3. A sync that recreates instead of deleting can, in principle, resurrect a page that one side genuinely meant to remove through some path other than `delete()` (there is none today, but a future one might exist) without ever writing a delete revision. This is an accepted trade: `delete()` is and remains the only supported way to remove a page, and anything that removes one without going through it is already a bug this ADR is designed to contain, not enable.

4. `docs/AGENT-OPERATE.md` and `skills/cairn/SKILL.md` now tell an agent to run `cairn sync --dry-run` and read its warnings before the first unattended sync against a Cairn that might have missing data, rather than trusting sync to be safe by default. Sync is safer after this change, but a dry run costs nothing and catches problems this fix cannot, such as a genuine conflict worth a human's judgment.

## Relates to

ADR-059 (undelete and the deleted-pages list this decision's proof check relies on), ADR-023 and ADR-030 (the original sync design this corrects), ADR-005 (search and history as a page-only concern, why rows are excluded).
