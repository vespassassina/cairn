# ADR-016: Export is a folder of Markdown and JSON that imports back without loss

Status: accepted
Date: 2026-09-12
Implements: PRD P0.7, product principle 5 ("your data leaves easily")

## Context

The owner's requirement: data is owned by its users and can be processed again, and export works for the whole workspace or from one page down.

"Owned" means readable without Cairn: a person with a text editor, Obsidian or GitHub's file view can read every page. "Processed again" means the same folder can go back into a Cairn, this one or another, and come out identical, so an export is also a backup, a migration and a way to edit offline.

Options for the format:

1. **One JSON file.** Exact, but unreadable to a person and awkward to edit.
2. **A zip built by the server.** Needs a zip writer on every runtime and holds the whole workspace in one response, which a serverless platform's response limits would cap (Lambda: 6 MB).
3. **A folder written by the CLI** from paged API calls: Markdown for pages, JSON for collections. Works the same against a local and a deployed server, has no response-size ceiling, and zipping it is one command anyone already has.

## Decision

1. **Format version 1:**
   1. `cairn-export.json`: the manifest, holding the format name and version, when, from where, the root if any, and counts.
   2. `pages/<slug>.md`: one page per file. A front matter block holds `id`, `title`, `parent`, `tags`, and informational `updated`, `updated_by` and `version`, each value written as JSON so any title round-trips exactly. The Markdown body follows unchanged.
   3. `pages/<slug>/`: a page's children, so folders mirror the page tree.
   4. `collections/<slug>.json`: one collection, its schema and every row with its id.
2. **Ids travel in the front matter, not in file names.** Links like `[[pg_bpc-157]]` stay valid after an import, and files can be renamed or moved freely.
3. **Derived data is not exported.** Links, backlinks and search chunks are rebuilt by the import, as ADR-005 requires of derived data.
4. **Export by root.** `--root <page-id>` writes that page and everything under it; the root becomes top level. Collections are included only with `--collections`, because they do not belong to a page.
5. **Import compares before it writes.** A missing record is created at its id, a changed one is updated with a version check, an identical one is skipped. Running it twice changes nothing, and an interrupted run can simply be repeated. `--dry-run` shows the plan.
6. **A page whose parent is neither in the export nor on the target becomes top level**, and the import says so, rather than failing.
7. **Import is a writer like any other.** Every change is a revision with a change note naming the export it came from (ADR-008).
8. **The REST API gains what this needs:** `GET /api/v1/export/pages` (full pages, parents first, paged), `PUT /api/v1/pages/:id` and `PUT /api/v1/collections/:id` (create at an id, or replace with `If-Match`).
9. **No MCP tool.** Export is bulk file output, and MCP returns text to a model. ADR-013 allows a surface to leave out what it cannot express; this is that case.
10. **History is not exported yet.** Current content is the part a person needs to leave with. Exporting revisions is on the roadmap.

## Consequences

1. Checked on the peptide wiki: 96 pages, 2 collections and 87 rows exported, imported into an empty database, and exported again produced identical files.
2. File names are readable and portable: lower case, dashes, accents removed, Windows' reserved names avoided, and a clash between siblings resolved by appending the id.
3. A format version in the manifest lets a later version change the layout while old exports stay readable; the CLI refuses a newer format than it knows.
4. Wiki links in the Markdown point at ids, not file names, so they do not click through in Obsidian. A link rewrite on export is possible later without changing the format.
