# ADR-037: A Cairn's trusted friends are rows in a table, not a registry

Status: accepted
Date: 2026-09-15
Relates to: ADR-023 (sync), ADR-024 and ADR-026 (tables in the tree), ADR-034 (self-description), ADR-036 (check-sources), PRD principle 6 (bridges between Cairns)

## Context

The owner's direction of 2026-09-15 rejected "A registry of public Cairns on GitHub", the roadmap item that would have made this project run or curate a shared list of public Cairns: "avoid the registry. not my place." In its place: "a cairn can keep references to other cairns and act as a local 'trusted friends' catalog." That answers who runs the list (nobody but the owner, for their own Cairn) but not what the list is, in code.

Two roadmap items still need a starting point once they are built: "'Cited by', across Cairns" needs to know which addresses to accept a notice from, and "Discovery by following citations" needs somewhere to start walking outward from instead of a registry's front page. Neither is built now. This ADR only gives them, and the owner, a place to read from and write to.

The obvious shapes are a new stored concept, with its own port, schema and endpoints, or reusing what Cairn already has. Cairn already has one: a table (ADR-024, ADR-026), with fields, rows, history, and the same read and write path as a page, exposed identically on MCP, REST and the CLI (ADR-013, hard rule 14). A trusted Cairn is a small, flat record, an address, a name, why it is trusted, when it was added, which is exactly what a table row already is.

## Decision

1. **A trusted Cairn is a row in an ordinary table**, named "Trusted cairns", with fields `url` (type `url`, required), `name` (type `text`), `note` (type `text`) and `added_at` (type `date`). No new port, no new schema, no new storage. It is created the first time it is needed, the same way any table is: by `POST /tables`, which `cairn trust` calls if the table does not exist yet.

2. **`cairn trust <url> [--note TEXT] [--timeout MS]`, a new CLI-only command.** Before adding a row, it confirms the address is a Cairn: it fetches `<url>/.well-known/cairn.json` (ADR-034) and checks the response is JSON with a `cairn` field. On success it upserts a row, keyed by `url`, filling `name` from the self-description when the owner did not name one and setting `added_at` on first add only. A failure names the address, what went wrong, and what to check, the same discipline `check-sources` follows (ADR-036).

   This mirrors `cairn sync` (ADR-023) and `cairn check-sources` (ADR-036): a client of the web, checking something outside Cairn itself before writing about it, which is not a server's job to do on anyone's behalf. No MCP or REST change; an agent or the console can still add a row directly through `upsert_row` or the review console without this check, the same way a page can be written without going through a CLI convenience command.

3. **Reading and managing the list needs no new surface.** `cairn tables`, `cairn rows`, `cairn row` and `cairn upsert`, already generic, work on this table exactly as they work on any other. So do the MCP tools and the REST endpoints. Hard rule 14 holds without writing anything to keep in parity, because nothing new was added to any one surface.

4. **The list stays local by default.** It is ordinary Cairn data: it appears in export, import and sync like any table, and it is visible to whoever can read this Cairn's data, but it is not on the published surface (`/w`, `/.well-known/cairn.json`) unless the owner deliberately publishes it, the same choice they make for any collection (ADR-032). Nothing here changes what `cairn.json`'s `cites` field means (ADR-034); that is a citation record for a Cairn's own content, still empty until citation tracking exists, and separate from this list of who the owner trusts.

5. **What reads this list is future work.** Neither "cited by" nor citation-following discovery is built by this ADR. Each still needs its own ADR when it is picked up, and each will read "Trusted cairns" as the boundary of who is trusted, rather than trusting every address that happens to notify or get cited.

## Consequences

1. Zero changes to `packages/core`, `packages/api`, or the MCP tool list. The catalog is exactly as durable, exportable and syncable as any other table, for free.
2. `cairn trust` is the only new code, and it is CLI-only, on the same reasoning ADR-023 and ADR-036 already established for a job that is a client of the web rather than a decision Cairn itself makes.
3. Verification is shallow: it confirms the address serves a well-formed Cairn self-description, not that the Cairn behind it deserves trust in any deeper sense. That judgement stays the owner's; the command only saves them from a typo or from trusting an address that answers with something other than a Cairn.
4. A Cairn that is not public, and so serves no `/.well-known/cairn.json`, cannot be trusted by `cairn trust` yet. That is acceptable for now: the two features this list exists for, "cited by" and citation-following discovery, both only make sense between Cairns that publish.
5. The roadmap's "A registry of public Cairns on GitHub" item is marked rejected rather than superseded, since no ADR ever accepted it; this ADR is what replaced the plan, not a reversal of a prior decision.
