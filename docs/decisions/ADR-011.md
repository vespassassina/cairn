# ADR-011: Cairn tells clients when to use it

Status: accepted, extended by ADR-012 (a live summary of the workspace follows the fixed text)
Date: 2026-09-12

## Context

An MCP client loads Cairn's tools with their descriptions, and the model calls one when a request plainly matches it: "search my notes for X", "save this". Tools are available, never required. So without more, Claude reaches for Cairn only when asked, does not check it before answering a question it could inform, and does not save what it learns. That is a document store, not memory, and it would fail the Phase 1 usage gate (PRD section 10) for the wrong reason.

Three places could carry the guidance:

1. **Tool descriptions.** They already say how to call each tool. They are read when choosing a tool, so they cannot make the model consider Cairn in the first place.
2. **The owner's own CLAUDE.md.** Works, but every user has to write it, and it only reaches Claude Code.
3. **Server instructions.** The MCP `initialize` result has an `instructions` field for guidance about the server as a whole. Claude Code puts it in the context of every session that has the server. It ships with Cairn and needs no setup.

## Decision

1. **Cairn sends server instructions at initialize.** They say:
   1. Search before answering when Cairn may hold the topic, and say which page an answer came from.
   2. Save durable knowledge without being asked: findings, decisions with their reasons, corrected facts.
   3. Search first and update an existing page rather than creating a duplicate. Link pages with `[[Page title]]`. Put structured records in collections.
   4. Give every write a change note. Writes apply at once and are revisions the owner can restore (ADR-008).
   5. On a version conflict, read again, merge, retry. Never overwrite blindly.
   6. Never store secrets, credentials or scratch work.
2. **The text lives in one module**, `packages/api/src/mcp/instructions.ts`, and stays at or under 2,000 characters, because it is sent into every session and competes with the user's own context. A contract test enforces the budget, and checks that every tool the text names exists.
3. **The text stays general.** Nothing about a particular dataset or owner. Owners add their own guidance, such as which topics live in Cairn, in their CLAUDE.md.
4. **Changing the text is a behaviour change.** It needs a changelog entry saying why. Once the eval set covers usage, a change is checked against it the way search changes are.

## Consequences

1. Agents will write more, and without being prompted. That is the point, and it is safe only because every write is a revision (ADR-008) and the review console shows agent writes first (ADR-009). If recent changes fill with noise, tighten rule 1.2 before adding anything else.
2. Clients that ignore server instructions still get the tool descriptions, and still work when asked directly.
3. Every Claude Code session with Cairn configured pays about 300 tokens for the text, whether or not it uses Cairn. That is the cost of the budget in rule 2.
4. Open: whether "without being asked" produces too many low-value pages. Watch it during the Phase 1 usage period, and record what is seen in `docs/LESSONS.md` or the changelog.
