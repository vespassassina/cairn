# ADR-082: A repeating sync refuses to keep Azure awake without being told

Status: accepted

Date: 2026-11-10

Relates to: ADR-018 (Azure Container Apps, scale to zero), ADR-023 and ADR-029 (sync), hard rule 14.

## Context

The owner got an Azure bill of about 7 EUR for October 2026, against an expectation of almost nothing. The cost breakdown: vCPU active usage 4.90 EUR, memory active usage 1.23 EUR, storage list operations 0.89 EUR. The container app is set to scale to zero after 30 minutes, and was.

The replica metric shows one replica up nearly 24 hours a day from 2026-10-10 to 2026-10-20 (the metrics' retention starts on the 10th), with 170 to 290 ingress requests a day, about one every six minutes. Nothing else changes the picture: from 2026-10-21 requests fall to zero on most days and the app sleeps. No logs exist to name the caller, because the deployment has no Log Analytics workspace by design. The pattern is that of `cairn sync <a> <b> --every 5m`, which `docs/CLI.md` and `docs/LOCAL.md` gave as their example, in the same pages that warn that syncing more often than the idle time keeps Cairn awake. The last sync state file on the laptop was written on 2026-10-15. This is the likeliest cause, an inference from timing and not a proof.

Options: (a) fix the examples only; (b) refuse short intervals against Azure unless the owner says so; (c) always warn, never refuse.

## Decision

1. `cairn sync --every` and `cairn sync install --every` refuse an interval under two hours when either server is on `*.azurecontainerapps.io`. The error says what it costs, names `--every 4h`, running `cairn sync` once, and `--keep-awake`.
2. `--keep-awake` is the owner's way past it, for someone who has chosen the cost (or `CAIRN_ALWAYS_ON`).
3. The examples in `docs/CLI.md`, `docs/LOCAL.md` and the CLI help use `--every 4h`.
4. The check is by address only. A custom domain on Azure is not detected; the docs still warn.

## Consequences

1. The mistake that cost the owner a month of free grant is now a refused command with the fix in the message.
2. A custom domain, or another host with the same billing shape, is not covered.
3. The CLI is a thin client (hard rule 15), so the guard lives there and nowhere else; MCP and REST have no repeat.
