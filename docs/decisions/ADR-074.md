# ADR-074: Publish and unpublish notify IndexNow, opt-in

Status: accepted

Date: 2026-09-23

Relates to: ADR-032 (collection publishing), ADR-034 (self-description, decision 4 named this as future work), hard rule 5 (optional services degrade, never run on the write path), hard rule 14 (a capability added to one surface is added to the others, or the ADR says why not)

## Context

`docs/ROADMAP.md` named "Tell search engines when publishing changes something: on a publish or unpublish, notify through IndexNow so a search engine recrawls without waiting for its own schedule." IndexNow is a shared API (`api.indexnow.org`) that Bing, Yandex and other participating engines read from; a site proves ownership with a key served as a plain-text file at its own origin, then POSTs a list of changed URLs.

Publishing today is `publishPage` in `packages/api/src/operations.ts`, reached only from the console and CLI (`cairn publish`/`cairn unpublish`), never MCP, by ADR-032 decision 5: an agent asked to publish tells the person to use the console or CLI. A page's `public` flag also governs its whole subtree, so one publish or unpublish can change the public status of many pages at once. The public URL of a page is `<origin>/w/<id>` (ADR-038), where `<origin>` is `CAIRN_PUBLIC_URL` or the request's own origin.

Two things needed a decision, checked with the owner: whether a publish notifies just the one page or every page in its subtree whose status actually changed, and whether the feature is on by default whenever a public origin is configured or requires its own opt-in. Chosen: the whole subtree (a search engine should hear about every URL that changed, not just the one the owner clicked), and explicit opt-in via a new `CAIRN_INDEXNOW_KEY` setting (an outbound call to a third party should be a separate choice from simply being reachable, matching the optional-service pattern `CAIRN_EMBEDDINGS`, `CAIRN_ATTACHMENTS_TO` and `CAIRN_BACKUP_TO` already use).

## Decision

1. **Config**: `CAIRN_INDEXNOW_KEY` (`packages/api/src/config.ts`), an opaque string the owner sets. Unset means the feature is off: no key file served, no submission ever attempted. `docs/AGENT-OPERATE.md` describes it per hard rule 19, including that the owner picks the key (any hex/opaque string IndexNow accepts) or generates one with `openssl rand -hex 16`.
2. **Key file**: when `CAIRN_INDEXNOW_KEY` is set, a public route serves `GET /<key>.txt` returning the key as `text/plain`, the exact proof IndexNow requires. No auth: the file is only ever useful to prove what the owner already configured.
3. **Notification is backgrounded, not on the write path**, per hard rule 5's principle for optional services: `publishPage` (operations.ts) finishes its own write and returns to the caller first; the IndexNow submission (walk the now-published-or-unpublished subtree via `context.store.listPages`, collect each page's `<origin>/w/<id>`, POST the batch to `https://api.indexnow.org/indexnow`) runs after, fire-and-forget, logged on failure, never thrown into the publish response. A slow or unreachable IndexNow never delays or fails a publish.
4. **No new MCP tool.** ADR-032 decision 5 already keeps publishing off MCP; this is a side effect of an existing console/CLI action, not a new capability an agent invokes, so hard rule 14 does not ask for a third surface here.
5. **Failure handling**: matches `citations.ts`'s existing outbound-fetch pattern for the fetch mechanics (bounded timeout via `AbortController`, typed error on failure) but not its synchronous-in-request placement; a non-2xx or network failure from IndexNow is logged (`console.error`, no owner-facing error) and does not retry. IndexNow's own spec tolerates missed submissions since search engines still crawl on their own schedule; this is a courtesy notification, not a guarantee.

## Consequences

1. A publish or unpublish reaches a participating search engine roughly as fast as the outbound request completes, instead of waiting for its next scheduled crawl, without slowing down or risking the publish itself.
2. Off by default: an owner who never sets `CAIRN_INDEXNOW_KEY` sees no behaviour change and no outbound call is ever made.
3. Unpublish submits the same URLs IndexNow already had; IndexNow has no "remove" semantics, only "recrawl", so the search engine finds the page gone (or gated, ADR-066) on its own next fetch. This is documented so it is not mistaken for guaranteed deindexing.
4. The gating-token case (ADR-066): a token-gated subtree's URLs are still submitted, since the page itself is still publicly routable and its gate is enforced on read, not at the URL level.
5. `docs/AGENT-OPERATE.md` needs the new setting (hard rule 19); the operate guide's test (`packages/cli/test/agent-guides.test.ts`) enforces this.
