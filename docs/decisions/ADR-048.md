# ADR-048: Cairn stops on purpose, inside the time the platform allows

Status: accepted
Date: 2026-09-16
Relates to: ADR-018, ADR-020, ADR-046

## Context

ADR-046 settled what Cairn does when it starts on a database it cannot vouch for. It left the other end alone, and the other end is where the damage came from.

Cairn had no signal handler at all. A grep of `packages/api/src` for `SIGTERM`, `SIGINT` or `process.on` returned nothing. So Cairn wrote until the instant it was killed, and on Azure it is killed often: Container Apps scales to zero after the idle period, replaces a revision on every deploy, and in all cases sends SIGTERM and then SIGKILL thirty seconds later.

That is the setting in which the outage of 2026-09-15 happened. The evidence is in `docs/LESSONS.md`: revision `cairn--0000015` was created at 20:38:56, and a 206 byte transaction, txid 81, was written to the replica at 20:39:53. Two things follow from that pairing. Only a process that was replicating successfully could have appended to the replica, so the replica was healthy a minute earlier. And 206 bytes is an LTX header followed by the start of a page it never finished, so the writer did not choose to write a short file. It stopped existing. Litestream's own guidance is to stop it with SIGTERM and let it finish; being killed mid-upload is what leaves a truncated transaction behind.

The alternative causes were checked and do not fit. Litestream [#1309](https://github.com/benbjohnson/litestream/issues/1309) produces the same symptom from a torn page set, but needs a slow initial snapshot racing checkpoint writes: the reported case was 22 GB on a 12 MB/s disk taking 25 minutes. Cairn's database is 3.5 MB.

So the cause is one we built and one we can remove. SQLite checkpoints the write-ahead log and deletes it when the last connection to it closes. A Cairn that closes its database hands Litestream a finished file. A Cairn that is killed hands it a moving one.

## Decision

1. **Cairn handles SIGTERM and SIGINT,** and stops in a fixed order: stop listening, let the requests already in flight finish, run the shutdown steps, exit. The code lives in `packages/api/src/entry/shutdown.ts`, because signals and sockets are platform specific and by hard rule 13 that belongs under `entry/`.
2. **Closing the database is a shutdown step, and the last one.** Backing up will be a step before it, because a backup of a closed database is not possible. The step list is the extension point; nothing else about shutting down needs to change to add one.
3. **The whole sequence has one deadline,** `CAIRN_SHUTDOWN_SECONDS`, default 25. Running out of time is never a reason to hang. It is a reason to name the step that did not finish and exit anyway, because the platform will not wait and being killed silently is strictly worse.
4. **Draining requests may take at most half the budget.** A handler stuck on something outside Cairn's control must not be able to spend the time that closing the database needs. An abandoned request loses one answer; an unclosed database is the failure this ADR exists to prevent. This rule came from a test, which caught the opposite ordering.
5. **A failing step never stops the ones after it.** A backup that cannot reach blob storage must not be the reason the database is left open.
6. **A second signal exits at once.** Someone pressing Ctrl-C twice, or a platform escalating, is asking to stop now, and appearing hung instead is a worse answer.
7. **The platform is configured to allow it.** `terminationGracePeriodSeconds: 30` in the Bicep and `stop_grace_period: 30s` in the compose file, both stated rather than left to a default, and both above `CAIRN_SHUTDOWN_SECONDS`. `docker stop` allows ten seconds by default, which was not enough.
8. **An untidy stop exits non-zero,** so a platform that reports exit codes shows the difference between a clean stop and one that ran out of time.

## Consequences

1. The replica now receives a finished file on every ordinary stop: deploy, scale to zero, revision replacement. The specific mechanism that took the Azure Cairn down for four days is removed, not merely recovered from.
2. The shutdown backup the owner asked for has somewhere to go. It is one entry in the step list, ordered before the close.
3. Two numbers must now be kept in agreement, in three files: `CAIRN_SHUTDOWN_SECONDS`, the Bicep grace period and the compose grace period. The setting's description in `docs/AGENT-OPERATE.md` says so, and the defaults leave five seconds of margin.
4. Shutting down is tested against a real process and a real signal, not a stub. `packages/api/test/shutdown-signal.test.ts` asserts that no write-ahead log survives, which is the property Litestream depends on. With the handler removed the test fails with exit code 143, killed by the signal, which is exactly the behaviour being replaced.
5. This reduces the chance of a truncated transaction. It does not reach zero, because a node can always vanish without warning. That is why the recovery ladder on the start-up side, and real backups, are still owed.
6. **Deliberately not adopted:** Litestream's `auto-recover`, which resets on LTX errors. Reset takes a fresh snapshot from the local database ([reference](https://litestream.io/reference/reset/)). On a scale-to-zero container the local database is usually absent, so auto-recover would answer a 206 byte problem by replacing the whole replica with nothing, silently, on the first restart. It is the ADR-046 hazard with a friendly name.
