# ADR-059: Undelete, a deleted-pages list, and per-page vacuum

Status: accepted, cause of the 2026-09-17 loss corrected by ADR-060
Date: 2026-09-18

## Context

On 2026-09-17 the owner found eleven pages missing from the live Azure Cairn, with no deletion showing in `cairn changes` or in any page's history. They asked for the pages back, for a delete to always show up in history, for a way to undo a delete from that history, for a "deleted" list on every surface, and for a `vacuum` command that removes a document's older revisions and compacts the database.

The eleven pages were recovered from the local laptop's `cairn.sqlite` revision history (kept in sync via `cairn sync`) and re-created on Azure at their original ids with `cairn import`, so `[[wiki-links]]` and parent/child structure between them kept working. That recovery needed no code change; it used the existing `PUT /pages/:id` create-or-replace-by-id endpoint from ADR-016.

The "does a delete show up in history" question needed an answer before anything else, because it decides whether this is a bug fix or a new feature. A local end-to-end test — delete a page, read its history and the changes feed — showed the existing code path already records a deletion revision and surfaces it correctly. The Azure gap is best explained by those eleven pages never having gone through `delete()` at all: real data loss at the replica level (Litestream generation inconsistency is the leading suspect, not confirmed), not a bug in how deletions are recorded. So this ADR is scoped to the three still-open asks: undelete, a deleted-pages list, and vacuum.

## Decision

1. **Undelete keeps the page's id and its full pre-deletion history.** `PageService.undelete` reconstructs a `PageInput` from the deletion revision's snapshot and writes it back with `expectedVersion: null` (there is no current row, so this is a create) but `parentVersion` set to the deletion revision's own version, so `readHistory` keeps walking back through everything written before the delete instead of starting a new, disconnected chain. `writeWithRevision`'s `target` gained an optional `parentVersion` override for this: every other caller still uses `expectedVersion` for both concurrency and chaining, since only undelete needs them to disagree.

2. **`listDeletedPages` reports a page only while its newest revision is the deletion.** The SQLite query selects each revision that is `deleted = 1`, has no current page row, and has no newer revision for the same record. That last condition is what makes a page disappear from the deleted list again the moment it is undeleted, without a separate "undeleted" flag: the newest revision is no longer a deletion, so the row no longer matches. A conformance test simulates exactly this (delete, then a manual continuation revision standing in for undelete) and checks the page drops out of the list.

3. **`vacuum` is scoped to one page, not the whole workspace.** The owner's phrasing ("delete all older versions of a document and compact the db") names a document. A workspace-wide history wipe is a much larger, harder-to-reverse action that was never asked for, and CLAUDE.md's guidance on hard-to-reverse operations argues for the narrower reading when the phrasing is ambiguous. If a workspace-wide sweep turns out to be wanted, it is a new ADR and a new command, not a hidden second mode of this one.

4. **Vacuum requires the page's current version, checked, even though vacuum does not change it.** Every other destructive write in Cairn (delete, restore, move) takes a version token and fails loudly on a mismatch, per hard rule 3. Vacuum prunes revisions permanently and cannot be undone, so it gets the same read-then-confirm gate as an ordinary optimistic-concurrency write, even though there is no new version to move to. `PageService.vacuum` throws `VersionConflictError` on a mismatch, reusing the existing error rather than inventing new semantics.

5. **Vacuum refuses a page that is currently deleted.** It calls `PageService.get`, which throws `NotFoundError` for a deleted page. This keeps a deletion revision from ever being pruned out from under `undelete`: you can only vacuum a page that exists, and its deletion (if it has one further back in history) is never the thing being removed.

6. **All three capabilities reach MCP, REST and the CLI**, per hard rule 14: `list_deleted_pages` / `GET /pages/deleted` / `cairn deleted`, `undelete_page` / `POST /pages/:id/undelete` / `cairn undelete`, `vacuum_page` / `POST /pages/:id/vacuum` / `cairn vacuum`. `GET /pages/deleted` is declared before `POST /pages` and `GET /pages/:id` in route source order so the literal string "deleted" is never captured by the `:id` param route. All three are added to the parity allow list's capability table (`packages/api/test/parity.test.ts`, ADR-058) with no exceptions.

7. **A new error, `PageNotDeletedError`,** distinguishes calling undelete on a page that still exists ("use restore instead") from calling it on an id with no deletion in its history at all ("check the id with `cairn deleted`"), per the coding-style rule that every error names the exact next step.

## Consequences

1. Undelete and delete together make deletion a reversible, in-app action with full history, closing the original gap between "a delete is recorded" and "a delete can be undone from that record."

2. The deleted-pages list gives an agent or the owner a way to find a page's id after a delete without already knowing it, which `cairn undelete <page-id>` otherwise requires.

3. Vacuum is a one-page, opt-in space reclaim, not a retention policy. Nothing in Cairn expires history on its own; a person or agent has to ask for it, one page at a time, and confirm the version first.

4. The 2026-09-17 data loss itself remains only partly explained. The replica-inconsistency hypothesis is not proven, so no fix landed for it here; see `docs/LESSONS.md` for what is known and what to watch for. **Correction, 2026-09-18 (ADR-060):** the hypothesis in this section's Context was wrong, or at least beside the point. `cairn sync` itself was found to be what made this loss permanent and repeated it on more pages; see ADR-060.
