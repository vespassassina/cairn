# ADR-018: The first Azure deployment is a container on Azure Container Apps, with Litestream

Status: accepted. Decision 6 is superseded by ADR-020: the container is the path everywhere, not a stopgap before Functions.
Date: 2026-09-12
Relates to: ADR-005, ADR-006, PRD section 7 and P0.8

## Context

The owner asked for instructions to deploy on Azure. The PRD's Azure plan is Functions (Flex Consumption) with the Cosmos adapter. Neither is ready: the Cosmos adapter is not written, and spike S1 (Hono on Azure Functions) has not run. Waiting for both would leave Cairn with no cloud deployment at all.

What exists and works is the Node server with SQLite. The PRD already names "a single container" as a target. The question was where to run that container on Azure within the free grants, and how to keep its SQLite file safe.

Options:

1. **App Service, free tier.** Its persistent storage is a network file share, where SQLite's locking is unreliable, and the free tier sleeps and caps CPU time per day.
2. **Container Apps with an Azure Files volume.** The same network file share problem.
3. **Container Apps, a local disk, and Litestream.** The database lives on the container's own disk. Litestream streams every change to Blob Storage within about a second, and restores from there when a container starts. With one replica at most and zero when idle, the consumption plan's free grant covers personal use.
4. **A virtual machine.** Free for twelve months only, and something to patch.

## Decision

1. **Run the server image on Azure Container Apps, consumption plan**, with at most one replica and scale to zero. The free grant is 180,000 vCPU-seconds, 360,000 GiB-seconds and 2 million requests per subscription per month. At 0.25 vCPU, that is about 200 hours of activity a month before any charge.
2. **Keep the database with Litestream in Blob Storage.** The container restores on start and replicates while it runs. Access is through the app's managed identity with the Storage Blob Data Contributor role on that one account: no storage key exists anywhere in the deployment.
3. **No Log Analytics workspace**, which bills per gigabyte. Logs stream live with `az containerapp logs show`.
4. **One image, published by CI** to `ghcr.io/vespassassina/cairn` for amd64 and arm64: `edge` from `main`, the version and `latest` from a release tag. It holds the server bundled into one file by esbuild, Node, and Litestream pinned by version and checksum. Deploying needs no build.
5. **Deploy with one Bicep template and one script, in two passes.** The first creates storage and the environment and reports the app's address. The OAuth app is created at the provider with that address. The second pass, with the OAuth settings, creates the app. The script keeps the generated signing secret in a git-ignored file only its user can read, and passes secrets through a temporary parameters file, never on the command line.
6. **This does not replace the Functions and Cosmos plan.** That remains the path to scaling out and to a database that is not a single file. The container path is the one that works now, and the adapter boundary (ADR-005) means moving later is a configuration change for the application.

## Consequences

1. Anyone with an Azure subscription can deploy in about fifteen minutes, and an agent can do it for them (ADR-019).
2. Expected cost for one person: nothing for compute and requests within the grant, and cents for Blob Storage. To be confirmed with a month of real billing before any claim goes in the README (PRD Q7, R4).
3. Writes in the last second before a container stops may be lost, because Litestream replicates about once a second. Acceptable for personal use; recorded here so nobody is surprised.
4. A cold start restores the database before the first request is answered. For a small workspace that is a few seconds; it grows with the database. Measure it. Measured on 2026-09-13: about 30 seconds in all, of which the restore and start took 3; pulling the 340 MB image took 19 (docs/CHANGELOG.md).
5. One replica means one region and no failover. Also acceptable for personal use.
6. The template and scripts are checked in CI (Bicep compile, shellcheck), and the image is built and smoke-tested there. A real deployment has not been made yet from this repository; the first one will be recorded in the changelog.
7. The published image must be made public once in the GitHub package settings, or Container Apps cannot pull it without registry credentials.
