# ADR-077: Per-collection search synonyms, a dedicated store, expanded workspace-wide at query time

Status: accepted

Date: 2026-09-24

Relates to: ADR-024 ("Collections sit in the page tree"), ADR-021 (keyword search rules, requiredMatches), ADR-042 (negation-aware matching), ADR-013 (MCP, REST and the CLI translate; they never decide), ADR-005 (search is a separate adapter from the document store), ADR-076 (NEAR phrases, built in the same change)

## Context

The owner asked for "a small synonyms table for domain terms, each collection has its own, each collection is a domain", visible in Cairn and editable by a person, and reachable from MCP, the skill, the CLI and the REST API, with a hint to agents to store synonyms per domain when they notice one. The workspace this serves is heavy with abbreviations and jargon a keyword search cannot bridge on its own: "GLP-1" and "glucagon-like peptide 1" share no common token family under FTS5's Porter stemmer, so a search for one never finds a page written with only the other.

Two questions needed the owner's own call before design could proceed, and were asked directly rather than guessed:

1. **Where do synonyms live in the data model?** Options were a dedicated new core concept, or rows in the existing generic table mechanism (ADR-024's `Table`/`Row`). The owner chose a dedicated new concept.
2. **How does NEAR apply?** Answered in ADR-076, decided together with this ADR since the owner raised both in one request.
3. **Where does the table sit under each collection, for a person to see and edit?** The owner chose "one fixed child page per collection, named Synonyms." Building that literally (an actual wiki page with generic-table content) would have meant using the generic-table mechanism after all, which the first answer explicitly ruled out. Resolved by treating "visible in Cairn and editable by a person" as the requirement the owner actually needs met, and satisfying it with a screen in the review console instead, `/p/:id/synonyms`, one per top-level page, within the scope ADR-009 already allows the console: a plain table view, no rich editor. This substitution was not put back to the owner as a fourth question; it follows directly from combining their first two answers, and the console remains the one place a person edits anything in Cairn today.

A further ambiguity, not asked because it resolves from the codebase's own existing (if inconsistent) usage rather than needing a judgment call: "collection" is used two different ways already. ADR-024 calls a `Table` a "collection". The MCP workspace summary (`packages/api/src/mcp/summary.ts`) calls top-level pages "Collections (top-level pages)", and lists the owner's actual roots: Peptides, Projects, Home Assistant & Homelab. The owner's framing, "each collection is a domain", matches the second sense: Peptides is a domain of jargon, a `Table` inside it (like the "Peptides Index" table) is not. This ADR uses "collection" to mean a top-level page throughout, and the summary's existing wording is the one kept; ADR-024's use of the word for `Table` is unaffected by this decision but is worth noting as the source of the ambiguity, should it cause confusion again.

## Decision

1. A new core port, `SynonymsStore` (`packages/core/src/ports/synonyms.ts`): `list(workspaceId, collectionId)`, `add(workspaceId, collectionId, term, synonym, by)`, `remove(...)`, and `listAll(workspaceId)` for the union across every collection. A `SynonymPair` carries `id`, `workspaceId`, `collectionId`, `term`, `synonym`, `createdAt`. No version token: a pair is either present or not, and `add`/`remove` are naturally idempotent, so there is nothing to conflict over (unlike a page, ADR hard rule 3 does not apply here).
2. Backed by a new SQLite table, `synonyms`, in the same adapter package as everything else FTS5-related, one row per pair, `UNIQUE (workspace_id, collection_id, term, synonym)`. `term` and `synonym` are folded (`foldTerm`: lowercased, diacritics stripped) on write, so `"GLP-1"` and `"glp-1"` are the same stored pair.
3. Curated per collection, for a person's or agent's own organization, but **expanded workspace-wide at query time**: `SearchIndex.search()` has no collection-scoping parameter, because a search query is asked of the whole workspace, not one collection, so `operations.ts`'s `resolveSynonyms()` calls `listAll()` and unions every pair regardless of which collection it was added under. Which collection a pair sits in shapes only where a person finds it to edit, never which searches it affects.
4. Bidirectional: a pair `{term, synonym}` expands a search for either side to also match the other. `resolveSynonyms()` tokenizes both sides of every pair the same way the query itself is tokenized (`tokenize()`, the same function FTS5-equivalent word-splitting uses elsewhere in this codebase), and attaches the *other* side as an alternate to every one of a matched side's own token slots, only when all of that side's tokens are already present among the query's terms. This is deliberate: a naive string-equality check between a query term and a stored pair's raw term breaks for any term with internal punctuation or spaces, since `"GLP-1"` tokenizes to two terms, `"glp"` and `"1"`, never the single string `"glp-1"` (see `docs/LESSONS.md`, 2026-09-24, for how this was caught).
5. The SQLite adapter's `SearchIndex.search()` gained one optional field, `synonyms?: Record<string, string[]>`, keyed by folded query term, each value a list of alternate phrases to OR into that term's MATCH clause (`altQuery`). A page matches a term slot if it contains the term or any of its synonyms; `requiredMatches` still counts term slots, not alternates, so a synonym never loosens how many distinct concepts a query is asking for, only which words can satisfy each one.
6. Negation-awareness (ADR-042) applies per alternate, not just the literal term: a page is not treated as covering a term if every occurrence of it, or of its synonyms, is negated.
7. **MCP**: `list_synonyms(collection_id)`, `add_synonym(collection_id, term, synonym, change_note?)`, `remove_synonym(collection_id, term, synonym)`. `add_synonym`'s description carries the owner's hint directly: store domain jargon here when you notice it, in whichever collection the word belongs to.
8. **REST**: `GET/POST/DELETE /collections/:id/synonyms`, matching the shape of every other paginated list-plus-write route in `packages/api/src/rest/routes.ts`.
9. **CLI**: `cairn synonyms list/add/remove <collection-id> [term] [synonym]`.
10. **Console**: `/p/:id/synonyms`, a plain table plus an add form, linked from a top-level page's own view (`page.parentId === null`). Within ADR-009's console scope: no rich editor, no drag-and-drop, a form post and a redirect, the same pattern `/t/:cid/new` already uses.
11. One shared function set in `operations.ts` (`listSynonyms`, `addSynonym`, `removeSynonym`, `synonymPairJson`) is the only place the capability is decided; all four surfaces translate, per ADR-013 and hard rule 14.

## Consequences

1. A search for an abbreviation now finds a page written with only the spelled-out term, and back again, once a person or an agent has recorded the pair, closing a real gap in a jargon-heavy workspace that plain stemming cannot close on its own.
2. The synonyms table has no version token and no revision history the way a page does; editing or deleting a pair leaves no trace of what it used to be, unlike every other write in Cairn. Acceptable here because a synonym pair is metadata about the index, not a record of knowledge itself, and the change is small and always visible in the console's current state. If synonym history is ever wanted, that is a new ADR, not reopened here.
3. `pnpm eval` before and after this change, recorded in `docs/CHANGELOG.md`, shows recall@5 unaffected for the existing eval set, which has no synonym pairs defined and so exercises the mechanism as a no-op; a real signal on whether synonym expansion improves recall needs eval queries paired with real synonym data, not added in this change.
4. Every backend implementing `SynonymsStore` must pass the shared conformance suite (`packages/core/src/testing/synonyms-conformance.ts`), per hard rule 2; only the SQLite adapter exists today.
5. "Collection" now has a load-bearing meaning in this feature's own name and every surface's field (`collection_id`), matching the workspace summary's usage and not ADR-024's. A future reader hitting both usages should treat this ADR and the summary as the one to follow for "collection" meaning "top-level page", and ADR-024 as the one exception, not evidence of a wider inconsistency to fix.
