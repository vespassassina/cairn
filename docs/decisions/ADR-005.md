# ADR-005: Adapter boundary

Status: accepted
Date: 2026-09-11

## Context

The PRD promises one codebase that deploys to Azure, AWS or a container by changing configuration only (goal 4). The first cut of the design paired each concern with a cloud in a table, which hid four portability problems.

1. DynamoDB has no full-text search, while Cosmos has BM25 built into the document store. Pairing search with the document store makes AWS impossible without a redesign.
2. A page save also writes edges and chunks. In the planned partition layout those live in different partitions, and Cosmos transactions only cover a single partition key. DynamoDB and SQLite can do it. The interface cannot promise what Cosmos cannot deliver.
3. A DynamoDB backlinks query through a secondary index is eventually consistent. SQLite is immediately consistent. A conformance suite that assumes the SQLite behaviour passes locally and fails on AWS.
4. Cosmos filters and sorts on any field. DynamoDB needs a scan. Business logic written against Cosmos query power does not port.

## Decision

Five rules define the adapter boundary.

### 1. Search is its own adapter

`SearchIndex` is separate from `DocumentStore`. A deployment pairs them freely.

| Deployment | DocumentStore | SearchIndex |
|---|---|---|
| Azure | Cosmos DB NoSQL | Cosmos full-text (BM25) |
| AWS | DynamoDB | Serialized BM25 index in S3, built by the indexer |
| Self-hosted | SQLite | SQLite FTS5 |

`VectorIndex` is a third, optional adapter on the same footing.

### 2. Derived data can always be rebuilt

Pages and collection rows are the source of truth. Edges and chunks are derived from them and can be discarded and rebuilt from the source at any time.

Every derived-data write is idempotent and scoped to one source: `replaceForSource(sourceId, items)`. No incremental patching of derived state.

A rebuild command that walks every page and regenerates all edges and chunks is part of P0. It is the recovery path for a bad index, a changed chunking strategy or a half-applied write.

### 3. No transactions across documents

The adapter interface exposes no multi-document transaction. Adapters that support one may use it internally as an optimisation, but no business logic may depend on it.

The write path is therefore ordered so that a failure leaves the system recoverable, not corrupt.

1. Write the page with its version token. This either succeeds or conflicts.
2. Then replace its edges and chunks.

A crash between the two leaves the page correct and its derived data stale. The rebuild in rule 2 fixes it, and the indexer retries on its own.

### 4. Consistency is stated per operation, not assumed

Every read operation in the interface declares whether it is immediately consistent or eventually consistent.

1. Point reads of a page or row by id: immediately consistent everywhere.
2. Anything derived (backlinks, neighbours, search results): eventually consistent, with a stated bound of 10 seconds (PRD P0.3).

The conformance suite asserts eventual results by polling until the bound, never by reading once straight after a write. An adapter that happens to be immediate still passes.

### 5. Collection filtering runs in core

The filter and sort grammar from PRD section 8 is executed in `core`, in memory, over the rows of one collection. This is the DynamoDB-shaped lowest common denominator and it is fine at the target scale of a few thousand rows per collection.

An adapter may declare a `pushdown` capability and implement part of the grammar natively. The conformance suite runs the same query set against the adapter with pushdown on and off and requires identical results. This is the only sanctioned form of adapter variation, and it is invisible to business logic.

## Consequences

1. Q2 (full-text on AWS) stops blocking P1.3. The AWS answer is an index artefact in S3, built by the indexer Lambda at concurrency 1 and loaded by query Lambdas with ETag caching. Still to prove at 5,000 pages.
2. BM25 scoring differs between Cosmos, FTS5 and a JavaScript index. Recall@5 (PRD section 10) is therefore reported per backend. One number for the project is meaningless.
3. The queue leaves P0. Edge and chunk extraction is cheap enough to run inline on write. The queue comes back in P1 for embeddings, which are slow and external.
4. The conformance suite needs a clock-aware helper for eventual assertions, and a capability matrix so an adapter can skip what it does not claim.
5. PRD section 7's storage table is replaced by the table in rule 1.
