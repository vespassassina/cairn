# ADR-046: Cairn never starts on a database it cannot vouch for

Status: accepted
Date: 2026-09-16
Relates to: ADR-018, ADR-020

## Context

On 2026-09-16 the Azure Cairn had been unreachable for some time. The container app reported itself healthy, its address answered nothing, and `cairn --instance azure overview` returned `error: http_504: stream timeout`. The container log held the real story:

```
restoring /data/cairn.sqlite from abs://...@cairn/cairn.sqlite, if it has a copy
level=ERROR msg="failed to run" error="decode database: decode page 1460: EOF"
restore attempt 1 failed; retrying in 10 seconds
```

Litestream's copy of the database in Blob Storage was truncated. Four things then combined into a total outage that said nothing about itself:

1. **The start script retried a failure that retrying cannot fix.** The retry loop was written for the first deploy, when access to storage takes a minute to arrive while Azure grants the app's identity its role. A snapshot that cannot be decoded is not that kind of failure. The script tried twelve times over two minutes, exited, and Container Apps restarted it, forever.
2. **Litestream was pinned at 0.5.7 while upstream was at 0.5.17.** The 0.5 line is a rewrite, and its patch releases have carried a run of restore and corruption fixes, including "validate LTX file size before restore" in 0.5.3 and "remove release-blocking SQLite WAL-reset corruption exposure" in 0.5.17.
3. **Nothing checked the database before serving it.** Had the restore half-succeeded rather than failed outright, Cairn would have opened a damaged database and streamed it back over the replica.
4. **The reason was unreachable.** By ADR-018 only the app's managed identity can read the storage account, so the owner could not list the replica's contents from their own machine to see what was there. The one place the answer could appear was the container log, and the log did not carry it.

## Decision

1. **The database is verified before it is served.** The start script runs SQLite's `integrity_check` on the database, through Node's built-in `node:sqlite` so the image gains nothing, on both the mounted-volume path and the replica path. A database that does not pass is never opened.
2. **A database that fails is never replicated.** This is the rule the others serve. Starting empty or half-read and then letting Litestream stream that state back would overwrite the only good copy, turning a recoverable outage into lost data. Refusing to start is the safe failure.
3. **Failures that retrying cannot fix stop at the first one.** A restore error naming a decode, corruption, malformed file, checksum or EOF is permanent, and the script stops. Everything else is a network or permission problem and keeps its twelve attempts.
4. **The container logs what it could not read.** On a damaged replica the script prints `litestream ltx` for that replica and the exact commands for the three ways out: a deliberate point-in-time restore, an export and import from another Cairn that holds the workspace, or a redeploy from empty. The diagnosis lands in the log, which is the one place the owner can reach without data-plane access to the storage account.
5. **Litestream is kept current**, pinned by version and checksum as before, at 0.5.17.
6. **The CLI names a gateway failure as one.** A 502, 503 or 504 that does not carry one of Cairn's own JSON errors never reached Cairn, so the CLI says that, and says the reason is in the server's log rather than in the response.

## Consequences

1. A damaged replica is now a fast stop with its reason in the log, instead of a crash loop that says nothing. The container still refuses to serve, which is the intent: an explained outage is better than silent data loss.
2. Diagnosing a replica no longer needs a role assignment on the storage account. What the replica holds is printed by the container that failed to read it.
3. Litestream now has to be watched rather than pinned and forgotten. A stale pin on a young rewrite is a liability, and this incident is the evidence.
4. Startup costs one integrity check. On a personal wiki this is milliseconds, and it runs while the container is starting anyway.
5. **Still open:** nothing notices a replica going bad while the container runs. The damage is found on the next start, which on a scale-to-zero deployment can be long after the writes that mattered. A periodic verification of the replica, or an alert on it, is not built.
