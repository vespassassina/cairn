# ADR-007: Auth is one small OAuth server in front of any OIDC provider

Status: accepted
Date: 2026-09-11

## Context

This answers Q3 and is the highest-risk item in the PRD (R1).

Claude custom connectors expect an OAuth 2.1 authorization server. The obvious per-cloud options each tie auth to one cloud: Static Web Apps built-in auth on Azure, Cognito on AWS, something else self-hosted. Three code paths for one feature, in the part of the system most likely to stall the project.

## Decision

Cairn contains one small OAuth 2.1 authorization server. It never handles passwords. Logging in is delegated to any OIDC provider the owner configures: GitHub, Entra ID, Google, or anything else with a discovery document.

The deployment difference shrinks to configuration: issuer URL, client id, client secret.

### Scope, deliberately small

1. Authorization code flow with PKCE. No other grant types.
2. Dynamic client registration, because Claude expects it. Registrations are stored in the document store like any other record.
3. Refresh tokens, rotated on use.
4. Access tokens are signed JWTs, verified locally by the API with no network call.
5. One workspace, one owner, plus an allowlist of permitted identities from the upstream provider. No roles, no scopes beyond a single `cairn` audience, no consent screen beyond the provider's own.

### Explicitly not in v1

1. No user database. Identity is whatever the upstream provider asserts, keyed by issuer plus subject.
2. No password reset, email verification or account recovery. The provider owns all of that.
3. No per-page permissions. That is PRD P2.6.

### Dev mode

A static bearer token, localhost only. The server refuses to start if that mode is enabled on a non-loopback bind address. This already exists as a rule in PRD section 7 and stays.

## Consequences

1. Auth becomes ordinary application code covered by ordinary tests, running on all three targets without change. No cloud identity service is a dependency.
2. Signing keys become a secret to manage. They go through the secrets adapter, and key rotation is supported by publishing a JWKS endpoint with more than one key.
3. Implementing an authorization server is real work and it is where the project is most likely to stall. The PRD's 3-day time box (R1) stands. If it is blown, the fallback is a hosted identity provider on a free tier, and the interface here is narrow enough to swap.
4. Newer revisions of the MCP specification allow a client to identify itself with a metadata document instead of registering dynamically. Worth checking at implementation time. It could remove the registration endpoint entirely.
