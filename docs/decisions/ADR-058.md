# ADR-058: An agent can walk the tree, and MCP catches up with the other two surfaces

Status: accepted, extends ADR-013
Date: 2026-09-16

## Context

ADR-024 and ADR-026 put collections in the page tree: a collection is a top-level page and everything beneath it. The tree is how the workspace is organised and how a person navigates the console. An agent cannot see it.

There is no way to ask what is under a page except one: `GET /api/v1/pages?parent=` on REST. MCP has no tool for it. The CLI has `collections`, which lists top-level pages only, and `read`, which shows a page's text and says nothing about its children. So an agent that knows a collection exists has no move from there except to search inside it and hope. Cairn's own structure is invisible to its primary client, which ADR-001 says is MCP.

Counting the tools registered in `packages/api/src/mcp/tools.ts` against what REST and the CLI can do shows the same gap in three more places. MCP has no delete for a page, while REST has `DELETE /pages/:id` and the CLI has `cairn delete`. MCP has no changes feed, while REST has `GET /changes` and the CLI has `cairn changes`. MCP cannot change a table's schema. And `create_table` takes no change note, although every other write does and the instructions tell the agent a note is required.

Hard rule 14 says a capability added to one surface is added to the others, or the ADR says why not. Four capabilities went to two surfaces and no ADR says why not. That is a drift, and this ADR closes it and says how to stop it recurring.

Delete needs more thought than the others. The reason it was never given to MCP was almost certainly caution, which is a good instinct badly executed: leaving it out does not prevent deletion, it just means an agent asked to tidy up will do it through the CLI instead, unsupervised by anything MCP knows about. Cairn already keeps every revision, so a delete is recoverable, and restore already reaches REST and the CLI by ADR-045.

## Decision

1. **A `list_children` capability exists on all three surfaces.** Given a page, it returns its immediate children, each with its identifier, title, whether it has children of its own, and when it was last changed. Given nothing, it returns the top-level pages, which are the collections. It pages with a cursor like every other list.

2. **It is immediate children only, never a whole subtree.** A tool that can return a whole tree can return a workspace, and hard rule 6 would then have it truncate at an arbitrary depth, which is worse than making the caller ask twice. Depth is the caller's business.

3. **Reading a page says what is under it.** `get_page` on MCP, `GET /pages/:id` on REST and `cairn read` all report the page's children, capped at a small number with a count of the rest and a pointer to the listing capability. Almost every time a page is read, the next question is what else is in there.

4. **MCP gains delete, the changes feed, and the ability to change a table's schema.** `delete_page` deletes one page by identifier, requires a version token like every other write per hard rule 3, requires a change note, refuses a page that still has children and says how many there are, and its description states plainly that history is kept and `get_revision` can bring the page back.

5. **`create_table` takes a change note, like every other write.** The instructions have always said a note is required. One tool quietly not requiring one is the kind of small inconsistency that teaches an agent the rule is soft.

6. **The three surfaces are checked against each other by a test, not by attention.** A test enumerates the operations exposed by MCP, by REST and by the CLI and fails when one surface has an operation the others do not, unless the operation is named in an allow list whose every entry carries the ADR that explains the exception. ADR-045's decision that restore reaches REST and the CLI while MCP keeps its own way is the first entry. Hard rule 14 has been a rule people were asked to remember, and this is what makes it a rule the build enforces.

7. **A table carries a description.** One short line saying what its rows are for, returned by `list_tables` and shown in the console and the workspace summary. A table named `peptides` tells an agent almost nothing about when to query it.

## Consequences

1. An agent can navigate rather than only search. That matters most on the questions search is worst at, such as what is in this collection, or what has been written about this project, where the answer is a structure and not a passage.

2. The workspace summary of ADR-012 and ADR-055 becomes the entry point to a walk rather than the whole of what an agent can know about the shape of the workspace. The two decisions work together: the summary names the collections, and this lets the agent open one.

3. MCP gains a destructive operation. That is the point of decision 4 requiring a version token, a change note, and an empty child list, and of the tool description saying how to undo it. An agent that can delete under those conditions is safer than one that reaches for the CLI because the tool it needed was missing.

4. Harder: the parity test in decision 6 will fail the first time somebody adds a capability to one surface, which is exactly what it is for, and it will occasionally fail for a capability that genuinely belongs on one surface only. The allow list handles that, and requiring an ADR reference in each entry keeps it from becoming a place to hide things.

5. Still open: whether `list_children` should be able to sort by something other than title, for instance by when a page last changed. Title order is chosen first because it matches the console's tree, and a sort argument can be added without changing the shape of the answer.

## Relates to

ADR-013 (one core, three surfaces, and hard rule 14), ADR-024 and ADR-026 (collections in the page tree), ADR-001 (MCP is the primary interface), ADR-045 (restore, the existing and only recorded exception to parity), ADR-008 (every write is a revision, which is what makes delete recoverable).
