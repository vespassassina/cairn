# ADR-030: Sync orders edits by when they were made, and merges both sides the way git does

Status: accepted
Date: 2026-09-14
Relates to: ADR-008 (history), ADR-013 (three surfaces), ADR-023 (sync), ADR-027 (sources), ADR-028 (freshness), ADR-029 (instances)

## Context

The owner asked: "for sync to work we need to use very granular timestamps. no doc shall conflict and order should always be maintained. also in case of conflicts, how do we solve ? take the newest and merge ? newest and link the older keeping the chain in order ? how does git do it we could do the same".

Sync as ADR-023 built it had three faults:

1. **Order was lost across hops.** A record copied by sync took the time of the copy as its `updated_at`. With three Cairns, an old edit on A relayed through B looked newer on B than a later edit made on C, so the older edit could win.
2. **A clock could repeat.** Two writes in the same millisecond on one server had the same time, and a tie went to whichever server was named first.
3. **A conflict kept one whole record.** When both sides changed a page, the newer edit replaced the other entirely, even when they had changed different paragraphs. The other stayed in history, but nobody would know to look.

Git orders commits by their parent links, not by clocks, and merges a file three ways: against the common ancestor, a part only one side changed takes that change, and only a part both changed differently is a conflict. The roadmap item written from the owner's direction proposed a hybrid logical clock, revisions linked across instances, and a merge by section.

The owner then said "then keep building" without choosing among these. **The agent chose the defaults below**, and they can be revisited.

## Decision

1. **Pages and rows carry `editedAt`,** when their content was last edited, at the place it was edited. `updatedAt` stays the time this server stored the write, and the revision keeps that time too, so the changes feed and history are unchanged.
2. **This server's clock never repeats.** Each edit time is at least a millisecond after the last one this server handed out, and at least a millisecond after the record's previous `editedAt`, so a later edit of a record never looks older, even when its previous time came from a server whose clock runs ahead. Times are ISO 8601 with milliseconds. Core's `editTime` does this for every write, including restore, which is an edit.
3. **A write can give an exact `edited_at`,** on `PUT` for pages and rows over REST. Sync uses it; import does not, since the export folder does not keep it (decision 9). It must be a time no more than a day ahead of this server's clock (the same bound as `verified_at`, ADR-028), and it is still raised to a millisecond past the record's previous time. It cannot be combined with `add_sources` on a row, which is an edit made here.
4. **Sync copies a record with the time it was edited,** so `editedAt` stays the time of the edit however many hops it takes. It orders two versions of a record by `editedAt`, and on a tie by the larger content hash, so both directions of a sync agree.
5. **When both sides changed a page or a row, sync merges them three ways,** as git does. The base is the version both agreed on at the last sync. The sync state keeps only its hash, so sync looks for it in the record's history on each side, up to 50 revisions back, rebuilding each revision's content and comparing hashes.
   1. A page's body merges line by line with diff3, git's algorithm. Lines are finer than sections: two edits to one section that touch different lines both survive.
   2. The title and parent merge as whole values. Tags and sources merge as sets: what either side added is kept, what either side removed is dropped, never a conflict. `verified_at` takes the later time.
   3. A row merges field by field, and its sources as a set.
   4. A part both sides changed differently is a conflict, and takes the newer edit. The version it replaced stays in that record's history (ADR-008), and the change note says "Sync conflict", how many parts, and which server's edit was kept.
   5. The merged record is written to each side it differs from, with an edit time a millisecond after the later of the two, so it orders after both edits. The report lists it as merged, or as a conflict when any part took the newer edit.
6. **The newer edit wins whole, as before,** when there is no base (a first sync, or a lost state file), when the base is not in either side's recent history, for tables, whose schemas keep no history (ADR-008), for an edit against a deletion (the edit wins, ADR-023), and for a body too large to compare in memory: more than 4,000,000 line pairs once the lines shared at the start and end are set aside.
7. **A write that fails leaves the base where it was.** A merge is two writes. If one is refused because the record changed in the meantime, the base for that record goes back to its previous value, so the next run sees both sides changed and merges again, instead of taking the half-written state as agreed and copying the unmerged side over the merged one.
8. **`edited_at` is in REST, where sync reads and writes it, and not in MCP or in what the CLI prints.** Agents read `updated_at` through either, and the two differ only for records that came through sync. Adding a field to every MCP read costs tokens in every session (ADR-011), and to the CLI's output the same for the agents that use it (ADR-013), and helps no task of theirs; MCP has no way to set it either, since only sync does. ADR-013 asks the ADR to say why a capability is on one surface and not another: this is why.
9. **`editedAt` is not content.** It is not in revisions' snapshots, not in the sync hash, and not in the files `cairn export` writes (ADR-016), though the export endpoint reports it. Two sides with the same content but different edit times are the same.
10. **Older data needs no migration.** A record written before this has no stored edit time and reads its `updatedAt` as one, and so does a server on an older version, whose REST output has no `edited_at`: sync falls back to `updated_at`, which is ADR-023's behaviour.

## What was not built, and why

1. **A hybrid logical clock with an instance id.** Its purpose is that an edit made after seeing another orders after it, whatever the clocks say. Decision 2 gives that for the only case sync compares, two versions of one record. Two edits made without seeing each other are concurrent; either order is legitimate, and the merge makes the order matter only for a part both changed. The hash breaks exact ties, so no instance id is needed.
2. **Revisions linked to the revision they replaced, across instances.** Each server's history is still its own chain; a merged revision's note names the other server. Links would let sync find the base without searching by hash, and would show one chain across instances as git does. It needs a revision id that travels with sync, and stays on the roadmap.
3. **Flagging conflicts for review in the console.** The change note says "Sync conflict", so they show in each record's history, and the sync report lists them. A console list of them stays on the roadmap.

## Consequences

1. Two edits to different parts of a page, made on different Cairns between syncs, both survive. An edit is lost from the current version only when both sides changed the same lines, and then it is in history with a note that says so.
2. Order holds across any number of hops and servers, as long as clocks are within a day. A clock that runs fast on one machine can still make its concurrent edit win a conflicting part; it can no longer make an older edit win over a newer one of the same record.
3. A merge writes a revision on each side it changed, so a merged record's history shows the merge wherever the merged version differs from what was there.
4. Finding the base reads up to 50 revisions of a record on each side, only for records both sides changed, which is rare between hourly syncs.
5. Comparing bodies uses memory in proportion to the lines that differ, up to about 16 MB at the limit. Wiki pages are far below it.
6. The merge runs in the CLI, as the rest of sync does (ADR-023): no server knows it is being synced, and a server on an older version still syncs, with the newer edit winning.
7. The Azure copy needs the image built from this change to keep edit times; until then it syncs as before.
