# ADR-023: Two Cairns sync through the cairn command, by comparing each record with the last sync

Status: accepted, decision 5 amended by ADR-024 (pages are written before collections); decision 2.3 extended by ADR-030 (edits ordered by when they were made, and both sides merged three ways)
Date: 2026-09-13
Relates to: ADR-008, ADR-013, ADR-016, ROADMAP "Sync design on the revision log"

## Context

The owner moved their Cairn from their laptop to Azure and asked for "an automigration feature to allow 2 cairns to be synced": a laptop and a cloud copy, or later a Proxmox server and Azure, kept as one.

Export and import (ADR-016) already copy one Cairn into another, keeping ids, and skip what is already the same. They go one way, though, and cannot tell a record deleted on one side from one created on the other, or a change here from a change there.

The owner decided two things:

1. **Where it runs: the `cairn` command.** `cairn sync <a> <b>` once, and `--every 5m` to keep going, on any machine that stays on. It uses the sign-ins the CLI already holds for each server, and needs no server settings. Rejected for now: a server that syncs with a peer by itself, which would keep the peer's token in the server's settings, and on Azure would only sync while awake.
2. **Conflicts: the newest edit wins, and the other is kept.** When a record changed on both sides, the more recent change goes to both, and the one it replaces stays in that record's history on its side, restorable in the console like any other old version (ADR-008).

Options for telling what changed:

1. **The changes feed** (`/api/v1/changes`). Cheap, but ordered by each server's clock, blind to what happened before it was first read, and it needs the revision history on both sides to line up, which it cannot: an import writes new versions.
2. **Version tokens.** Each server mints its own, so a record synced to both sides has two unrelated versions.
3. **Content, compared with the last sync.** Read every record from both sides, and remember, per record, a hash of the content both sides agreed on at the last sync. A side whose content differs from that hash changed it.

## Decision

1. **Sync compares content with the last sync.** For each page, collection and row, by id, with `A` and `B` the hashes of the two sides (absent when the record does not exist) and `base` the hash both had at the last sync:
   1. `A = B`: nothing to do.
   2. Only one side differs from `base`: that side changed, and its content (or its deletion) is copied to the other.
   3. Both differ from `base`, or there is no `base` and both have the record: a conflict. The side with the newer `updated_at` wins. An edit always wins over a deletion, so nothing is lost silently.
   4. No `base` and only one side has the record: it is copied to the other.
2. **The hash covers what a person wrote,** never what a server derives: a page's title, parent, tags and body; a collection's name and fields; a row's values. Versions, times and actors are not in it, so copying a record never makes it look changed on the next run.
3. **The state lives with the CLI,** in a file per pair of servers next to its credentials: `sync/<hash of the two addresses>.json`, holding the base hash of every record. Losing it loses no content: the next run treats every difference as a conflict and resolves it by time. A record deleted on one side since the last sync comes back from the other, since without a base a deletion looks like a record the other side never had.
4. **Writes go through the REST API like any other client,** with `If-Match` on every update and delete, and a change note naming the other server. A conflict's note says so, and says that the replaced version is in the history. A record that changed between the read and the write is skipped with a warning and picked up by the next run.
5. **Order:** collections, then pages parents first, then rows; then deletions, rows before pages, and children before parents. A page whose parent will not exist on the other side moves to top level, as an import does.
6. **Collections are never deleted by sync.** The API has no way to delete a collection; a collection missing on one side is reported instead.
7. **`--every <interval>`** repeats the sync, at least 30 seconds apart. A failed run is reported and the next one tries again. `--dry-run` prints the plan and writes nothing.
8. **Rows and collections now report `updated_at`,** which the conflict rule needs; pages already did.
9. **No MCP tool and no REST endpoint.** Sync is a client of two servers, and neither server can do it alone; ADR-013 allows a surface to leave out what it cannot express.

## Consequences

1. Migration is the first sync into an empty Cairn: `cairn sync <old> <new>`. Nothing is needed beyond being signed in to both.
2. Every run reads everything from both sides. For a personal wiki of hundreds of pages that is a few hundred kilobytes and seconds; at tens of thousands of records the changes feed could narrow what is read, without changing the rules above.
3. The newest-wins rule trusts each server's clock. Servers keep real time, so the rule only matters for two edits minutes apart, and the loser is kept either way.
4. Two machines syncing the same pair each keep their own state file. That loses no content, because a missing or stale base only turns differences into conflicts, resolved the same way on both; at worst a deletion comes back.
5. History is not synced: each side keeps the revisions written on it. A synced record's history on the other side starts with the sync, and names the server it came from.
6. Not done: a server syncing by itself (rejected above), syncing more than two Cairns in a ring, and merging two concurrent edits line by line.
