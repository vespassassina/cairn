# ADR-017: The OAuth server as built

Status: accepted, amended by ADR-032 (the published wiki needs no sign-in) and ADR-033 (a refresh token answers a repeat for one minute)
Date: 2026-09-12
Amends: ADR-007 (what changed on the way from design to code, and why)

## Context

ADR-007 set the shape: one small OAuth 2.1 server in Cairn, sign-in delegated to an upstream provider, an allowlist, tokens checked locally. Building it against the MCP authorization specification and its security guidance showed five places where the design needed to change.

## Decision

1. **A consent page, against ADR-007's "no consent screen beyond the provider's own".** Dynamic client registration lets anyone register a client with their own redirect address. Without a consent step, a malicious page could start a sign-in while the owner is already signed in to GitHub, which approves silently, and receive a token for the owner's Cairn: the "confused deputy" attack in the MCP security guidance. The page names the client and where the code will go, and needs one click. Clicking it from another site is refused by an Origin check, and the page cannot be framed.
2. **A separate auth store, not the document store.** Clients, pending sign-ins, codes and refresh tokens live in their own small port, `AuthStore`, with a shared conformance suite. None of it is content, so it never appears in history, search or an export. Its one hard requirement is `takeAuth`: read and delete in one step, so a code or refresh token can be used exactly once. SQLite does it with `DELETE ... RETURNING`; Cosmos and DynamoDB have conditional deletes.
3. **GitHub is supported as plain OAuth 2.0.** GitHub is not an OpenID Connect provider for user sign-in. It gets its own small adapter that reads the user from GitHub's API. Any OpenID Connect provider (Entra ID, Google, Auth0, Keycloak) uses discovery and the userinfo endpoint, with PKCE to the provider as well.
4. **HS256 with a shared secret, not a JWKS endpoint.** The only party that checks tokens is the server that signs them, so an asymmetric key and a published key set add nothing. Rotation works by keeping the previous secret in `CAIRN_AUTH_SECRET_PREVIOUS`, which is still accepted for checking.
5. **Public deployment is now allowed, with OAuth.** The server refuses a non-loopback bind unless OAuth is fully configured, and local trust (ADR-010) is forced off on any non-loopback bind, because there the `Host` header is whatever a caller sends.

What stays as ADR-007 set it:

1. Authorization code with PKCE, S256 only. Dynamic client registration, for public clients only. Refresh tokens, single use and rotated.
2. The allowlist: `github:<login>`, `oidc:<subject>`, or `email:<address>` when the provider marks it verified.
3. No passwords, no user database, no roles.

Details worth recording:

1. **Refresh token reuse ends the sign-in.** A refresh token presented a second time was probably stolen, so its whole family is revoked. The legitimate client then signs in again, which is the right cost. Amended by ADR-033: the cost turned out not to be right when the second use was a lost response or a concurrent refresh, so a used token answers with what it was already given for 60 seconds before this applies.
2. **Access tokens last an hour and are not checked against revocation.** That keeps the check free of store reads; revoking a sign-in stops new tokens, and the last one expires within the hour.
3. **One audience set.** A token for `/mcp`, `/api/v1` or the server itself is good for all three: one owner, one server, and separate audiences would add nothing.
4. **Attribution.** An OAuth write is recorded as `oauth:<client id>`, labelled with the client's name and the person, such as "Claude for owner". A person signed in to the console is recorded under their own identity instead of "Owner".
5. **The static token stays, as a service token** for scripts that cannot sign in, at least 32 characters on a public server.
6. **The CLI signs in like a native app** (RFC 8252): a one-off listener on 127.0.0.1, the browser for the sign-in, tokens kept per server in a file only the user can read, refreshed before they expire.
7. **Behind a proxy that ends TLS**, the server sees plain HTTP, so form Origin checks and cookie security use the configured public URL rather than the request's own.
8. **Client ID metadata documents**, the newer alternative to registration in the MCP specification (ADR-007 consequence 4), are not implemented yet. Claude and the other clients checked still register dynamically.

## Consequences

1. Claude, Claude Code, other MCP clients and the CLI can all reach a deployed Cairn. PRD P0.5 is implementable end to end; it becomes proven when a deployed instance is connected from claude.ai.
2. 18 end-to-end tests cover the flow and its attacks, with a fake provider standing in for GitHub; 5 more cover `cairn login`. The GitHub and OpenID Connect adapters are checked by tests of their requests, not yet against the real services.
3. The time box in PRD R1 held: this took one working session, not three days.
