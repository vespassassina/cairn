# ADR-053: Cairn makes itself present, or it is not memory

Status: accepted
Date: 2026-09-16

## Context

A review on 2026-09-16 looked at Cairn the way its owner would use it, on the owner's own machine, and found that on that day nothing could reach it. The laptop copy was not running. No `cairn` MCP server was registered in Claude Code. The stored Azure sign-in had been deleted by the CLI. No sync job was installed, and the last sync was two days old. The last write to the workspace was 2026-09-14, while two days of substantial work on the recovery ladder, the shutdown fix and ADR-052 left no trace in it.

None of that is a missing feature. Every one of those pieces exists and works. `cairn login` signs in, `cairn sync install` installs a job, the MCP server registers with one command, the server starts with one more. The problem is that all of them are one-time acts of setup that decay silently, and nothing notices. A memory that has to be remembered is not a memory.

The PRD's kill criterion for Phase 1 is that Claude reaches for Cairn four days a week. The review shows the criterion is being measured against an instrument that is switched off. Before deciding whether the idea works, the instrument has to be on by default.

Three separate causes were found, and they need separate answers.

1. The agent does not know Cairn is there. An MCP server only speaks when a tool is called, and a tool is only called when the agent already suspects there is something to find. Nothing in a fresh session says what this workspace holds.
2. The local copy is not running. `cairn sync install` schedules a sync, and a sync against a Cairn that is not listening fails. The job was designed to keep two Cairns the same, not to keep either of them alive.
3. Nothing reports the state of any of it. There is no single command that says which Cairn answered, whether it is signed in, when it last synced, how many embeddings are pending, and whether a job is installed. Each of those is discoverable with effort, which means none of them is discovered.

Options considered for the first cause. A background daemon that injects context was rejected: it is invisible, it cannot be audited, and it spends tokens the person did not agree to. Making the MCP server instructions longer was rejected because they are already at their budget, which is ADR-055's subject. A Claude Code SessionStart hook was chosen because it is explicit, it lives in the person's own settings where they can read and remove it, it runs a command they can run themselves, and its cost is visible and small.

Options considered for the second cause. Making the API server a login item on its own was rejected as too large a claim on the person's machine for a tool still proving itself. Reusing the job that ADR-029 and ADR-052 already install costs nothing new: the job already runs on a schedule, already has the person's consent, and already knows where Cairn lives.

## Decision

1. **`cairn hook install` writes a Claude Code SessionStart hook that runs `cairn overview`.** The hook is written into the user's Claude Code settings, is named, and is removable with `cairn hook uninstall`. `cairn hook status` says whether it is installed and what it will run. The command prints the exact lines it is about to write and asks before writing, the same shape `cairn sync install` already uses.

2. **The hook's output is bounded to roughly 200 tokens and never fails a session.** `cairn overview` already truncates. When Cairn cannot be reached, the hook prints one line saying so and the command to fix it, and exits zero. A memory tool that breaks the session it is meant to help has earned its removal.

3. **The scheduled job runs `cairn start` rather than `cairn sync`.** `cairn start` already starts the first registered instance when it is not answering, waits for it, and then syncs every instance. It is already idempotent: against a Cairn that is running it prints that it is running and goes straight on to the sync. The job that ADR-029 installs and ADR-052 offers therefore needs no new code, only the right command, and it becomes responsible for presence as well as agreement. That is what the owner meant on 2026-09-16 when they asked for a paired Cairn to keep itself in step.

4. **`cairn status` reports presence in one screen.** Which instance answered and at which address, whether the caller is signed in and when the token expires, when the last sync ran and in which direction, how many embeddings are pending, whether the scheduled job is installed, and whether the session hook is installed. Each line that reports a problem also carries the command that fixes it, per the coding style rule that every error names the next step.

5. **`cairn status` is the one command the guides point at first.** `docs/AGENT-OPERATE.md` and the person's guide both open their troubleshooting with it, so that an agent asked "is Cairn working" has one thing to run rather than five.

6. **None of this installs itself.** Every step above is a command the person runs, or an offer made once at a moment that already has their attention, as ADR-052 established for the sync job. Cairn does not write to a person's settings, shell profile or login items without being asked in that moment.

## Consequences

1. A session that starts with the hook installed begins knowing what Cairn holds, which is the condition ADR-011 and ADR-012 were written to create and have not achieved, because they only speak once a tool is already being called.

2. The Phase 1 gate becomes measurable. Until now a failure to reach for Cairn could not be told apart from a failure to reach Cairn. After this, the kill criterion in the PRD measures what it claims to measure, and the two week clock should be restarted from the day the hook and the job are both in place.

3. Cairn now writes into a file that is not its own, the Claude Code settings. That is a new kind of reach and it is why decisions 1 and 6 are as strict as they are: named, printed before writing, confirmed, and removable by a command that exists from the first release.

4. The job change costs one line, because `cairn start` was already written to be safe to run against a Cairn that is up. Hard rule 15 still holds: starting the server spawns a process through `node:child_process`, which hard rule 16 already allows, and the CLI never touches the database file.

5. Harder: the hook fires on every session in every project, including ones that have nothing to do with Cairn. The 200 token bound is what makes that acceptable, and it is a bound to defend rather than a starting point.

6. Still open: whether the hook should be per project rather than per user. Per user is chosen first because the owner's Cairn is their memory across everything they work on, not a project artefact. If the overview turns out to be noise in unrelated projects, a per project variant is the next step and needs its own ADR.
