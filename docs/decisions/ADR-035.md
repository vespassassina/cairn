# ADR-035: cairn export can write a static site, no server required

Status: accepted
Date: 2026-09-14
Relates to: ADR-016 (export format), ADR-013 (CLI is a thin client, but formatting stays in it), hard rule 16

## Context

The owner asked for `cairn export` to gain a site format: HTML pages with links rewritten to relative paths, an index per collection, and a sitemap, so the export can be put on GitHub Pages, an Azure Blob Storage static website, Amazon S3, Google Cloud Storage or Dropbox, at no hosting cost and with no Cairn running. Today's Markdown export already works inside a GitHub repository, which renders Markdown on its own, but its wiki links point at page ids and do not click through: `[[pg_bpc-157|TB-500]]` is not a link GitHub's renderer resolves, since GitHub does not know Cairn's id scheme (ADR-016, consequence 4). Rewriting those links to real, working ones is the first thing a site export has to do; keeping every source as a visible, clickable citation is the second.

Two ways to render the HTML were considered. One is a new REST endpoint, `packages/api` doing the rendering server-side, the CLI just saving what it returns. The other is rendering entirely inside the CLI. Hard rule 14 says MCP, REST and the CLI translate, they never decide, and that shared logic lives in `api/src/operations.ts` — but this is not decision logic two surfaces need; it is one surface's file format, exactly like `packages/cli/src/export-format.ts` already is for the Markdown export. Nothing about MCP or the REST API needs to know a static site exists. A REST endpoint would also mean streaming a whole site's worth of HTML over one request or paginating a new kind of response, for a feature that already has all its data through the existing `/export/pages` endpoint.

Hard rule 16 lists exactly what the CLI's own code may import, and `markdown-it`, the renderer `packages/api/src/web/markdown.ts` already uses, is not on that list; adding it would mean checking it on both Node and the Bun-compiled executable, and it pulls in more Markdown than this wiki uses. `examples/peptide-wiki/seed.ts` was read to check what the content actually contains: headings, paragraphs, bold, italic, inline code, fenced code blocks, lists, ordinary links and wiki links. Nothing more exotic turned up.

## Decision

1. **`cairn export <folder> --format site`** writes a folder of plain HTML instead of Markdown and front matter. `--format cairn`, the default, is unchanged and keeps writing what it always has. `--format` accepts only `cairn` or `site`; anything else is a `UsageError` naming the two valid values.

2. **A new CLI-only module, `packages/cli/src/site-format.ts`**, renders it. It reuses `assignPaths` from `export-format.ts` for the folder layout (`sitePaths` is the same tree with `.html` instead of `.md`), so a page's place in a site export mirrors its place in a Markdown export exactly. It is not a new export format of its own: `GET /export/pages` still supplies the data, unchanged.

3. **A small, self-written Markdown-to-HTML subset**, not `markdown-it` and not the console's renderer. It covers headings, paragraphs, bold, italic, inline code, fenced code blocks, bullet and numbered lists, `[text](url)` links restricted to `http(s):` and `mailto:`, and `[[id]]` / `[[id|label]]` wiki links. Anything else in a page's body is shown escaped, as plain text, rather than guessed at.

4. **Wiki links become real relative hyperlinks.** A `[[pg_bpc-157|TB-500]]` resolves, through the same `pathOf` map `assignPaths` produces, to the other page's `.html` file, expressed as a relative path from the page doing the linking (`relativeHref`), so the folder works unmodified from any base path or host. A wiki link naming a page or row not in the export renders as its label text, not a broken link.

5. **Each page's file carries a breadcrumb trail to the root, its rendered body, its sources as a visible list of citations (linked when they are `http(s):`, shown as text otherwise), and its own children**, so a reader can browse the whole export by clicking, the way the console's page view works, without JavaScript. `index.html` lists the top-level collections. `--site-url` is optional; when given, a `sitemap.xml` is written with absolute URLs under it, since a sitemap of relative paths is not valid and there is no way to guess where the folder will be hosted otherwise.

6. **Tables are out of scope for this format.** The Markdown export's `--tables` writes JSON files a Cairn can import; there is nothing a static HTML page usefully does with that shape yet. `--format site` never writes a `tables` folder. This can be revisited if the owner wants tables rendered as plain HTML tables.

## Consequences

1. A wiki exported this way is readable by double-clicking a file, or by uploading the folder to any static host, with no Cairn running and no dependency beyond a browser.
2. The Markdown export's long-standing limitation, wiki links that do not click through on GitHub (ADR-016, consequence 4), gets a real fix for the case that matters most, sharing a wiki as a browsable site, without changing the Markdown format itself; GitHub's own Markdown rendering is unaffected.
3. Rendering lives entirely in the CLI, so it costs no REST endpoint, no MCP tool, and no server-side change, consistent with treating export's file layout as a CLI-only formatting concern.
4. The Markdown subset is deliberately narrower than the console's renderer. A page using Markdown the subset does not cover shows that part as escaped plain text rather than broken HTML; this is judged an acceptable, visible degradation, not a silent one, for a v1.
5. Table rendering for the site format is deferred. A user who wants tables in the export still has `--tables` under the default format, or can keep it as future work.
