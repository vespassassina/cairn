# ADR-006: Hono plus stateless MCP transport, written to the lowest common denominator

Status: accepted. The runtime targets (Azure Functions, AWS Lambda) and spike S1 are superseded by ADR-020; Hono, web-standard handlers and the stateless transport stand.
Date: 2026-09-11

## Context

The same API has to run on Azure Functions, AWS Lambda and plain Node. Two things decide whether that is actually possible: the HTTP framework and the MCP transport.

Hono runs on all three. Lambda and Node have first-party adapters. Azure Functions has a community adapter, which is the weak link and needs proving before Phase 1.

The MCP streamable HTTP transport can run in two modes. Session mode keeps a long-lived server-sent-events stream and in-memory state per client. Stateless mode answers each request with a single JSON response. Serverless functions are billed per second of execution, can be recycled at any time and do not share memory between instances, so session mode does not fit.

## Decision

1. Hono is the HTTP framework everywhere. Route handlers are written against the web standard `Request` and `Response`, never against a platform-specific request object.
2. The MCP server runs in stateless streamable HTTP mode. No session ids, no server-sent-events stream, no server-initiated messages.
3. Where the platforms differ, the code targets the lowest common denominator rather than branching. Anything platform-specific lives in a thin entry point per platform (`api/src/entry/{node,lambda,azure}.ts`) that does nothing but adapt the handler.
4. Two consequences of stateless mode are accepted rather than worked around:
   1. No server-to-client notifications, so no progress reporting or subscriptions in v1.
   2. Long operations must fit in one request or be split into a call plus a poll. Export is the likely case, and it returns a job id.

## Open spikes, Phase 0

These decide whether the plan survives. Both are cheap.

1. **S1: Azure Functions.** Open. Get a Hono app returning JSON on Flex Consumption through the community adapter. Record the version pinned and the cold start time.
2. **S2: MCP transport shape.** Done, 11 September 2026. SDK 1.30.0 ships `WebStandardStreamableHTTPServerTransport`, whose `handleRequest(Request)` returns a `Response`. It takes Hono's `c.req.raw` directly, so `@hono/mcp` is not needed.

   One thing S2 turned up that changes the design: in stateless mode a transport cannot be reused. It throws "Stateless transport cannot be reused across requests" on the second call. So the server and transport are constructed per request in `api/src/app.ts`. This suits the target runtimes, where instances are recycled between calls and share no memory, and it is why the API holds no per-connection state at all.

If S1 fails, the fallback is a container on Azure Container Apps, which has a monthly free allowance, and the free-tier goal is re-examined. This does not affect the AWS or self-hosted paths.

## Consequences

1. Cold starts dominate the latency picture. At the PRD's usage pattern of a few days a week, most first calls in a session are cold. The 800 ms p95 target (PRD P0.2) is therefore measured and reported warm and cold separately.
2. No shared in-process cache can be assumed between requests. Caches are best-effort per instance, keyed by ETag, and never required for correctness.
3. The API stays free of framework-specific middleware that only exists on one platform, including platform auth headers. See ADR-007.
