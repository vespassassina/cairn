# ADR-070: A sync conflicts list in the console, derived from history

Status: accepted

Date: 2026-09-23

Relates to: ADR-030 (sync's three-way merge), ADR-009 (the review console), ADR-060 (delete protection)

## Context

`docs/ROADMAP.md` names a gap ADR-030 left out: a console list of records where a sync conflict took the newer edit for some part, with the version it replaced one click away. Today that fact only shows up in two ephemeral places: the `cairn sync` command's own stdout report, gone once the terminal scrolls, and the change note `apply()` in `packages/cli/src/sync.ts` writes onto the winning revision (always containing the literal substring `Sync conflict:`, in one of three fixed shapes, whether the whole record, a merged document with N parts, or a deleted-and-recreated record).

The console (ADR-009) already has a `/changes` page: every write, newest first, from `context.store.listRecentRevisions`, with a toolbar of chips that filter by actor kind (`who=agent`/`who=person`). Filtering that same list to only the writes carrying a sync-conflict note is a small extension of an existing capability, not a new one.

Two decisions, made with the owner:

1. **Where the list's data comes from.** Sync could write a new structured conflict record at sync time (a table, or a structured field alongside the note), or the console could derive the list from the note text sync already writes. Chosen: derive from history. It needs no new write path, no new storage, and no migration; `Sync conflict:` is already a stable, deliberate marker in every one of the three note shapes `apply()` writes, not an incidental string. The cost is that the marker lives in prose rather than a typed field, which the port method below makes explicit rather than hiding.
2. **Scope of the list.** A report of just the last `cairn sync` run, or a standing list across all history. Chosen: standing list, all history. Sync runs over the CLI, against whichever two Cairns were named, not through the console's own process, so there is no single process boundary a "last run" could mean inside the console; a standing list needs no handoff between the CLI and the API and behaves like the console's other lists (deleted pages, publish tokens): durable state, queried fresh each visit.

## Decision

1. `DocumentStore.listRecentRevisions` (`packages/core/src/ports/document-store.ts`) gains an optional filter, `syncConflict?: boolean`, alongside the existing `actorKind`. When true, only revisions whose `note` contains the literal substring `Sync conflict:` are returned. Every adapter implements it and the shared conformance suite (`packages/core/test/conformance`) covers it, per this project's hard rule 2. `adapter-sqlite` implements it as a `LIKE` predicate on the note column, in the same query `actorKind` already filters, no new column and no index beyond what full-table scans of a `/changes`-sized workspace already tolerate today.
2. The console's `/changes` route gains a third toolbar chip, "Sync conflicts", alongside "Everyone" / "Agents only" / "People only", combinable with the actor filter (`/changes?conflict=1&who=agent`). It reuses the exact same table, pagination and per-row link to `.../v/{version}` that `/changes` already renders; no new page, no new component. This stays inside ADR-009's limits: still a plain table, no client-side application, rendered on the server.
3. "The version it replaced, one click away": for a sync-conflict revision, its immediately preceding revision in that record's own history is the replaced version (confirmed directly against `apply()`'s behaviour by `packages/cli/test/sync-system.test.ts`'s chained-conflict scenario, added 2026-09-23). The existing per-record history/diff view already resolves this: the `/changes` row's link goes straight to the conflict revision's own page, and that page's existing "previous version" or diff-vs-previous control (wherever the per-page history view already puts it) reaches the replaced content in one click from there. No new UI element is added for this; it was already true of every revision, sync conflict or not.
4. The three note shapes stay free text. The list does not parse `parts` or `kept_from` out of the note into structured columns; the note itself, already written for a person to read, is shown as the row's description, the same way any other change note is shown on `/changes` today.

## Consequences

1. No new REST endpoint, MCP tool or CLI command. The console route and the store method are the only surface. The one new port method still needs a contract test with a realistic payload, per this project's own verification checklist.
2. Because the filter matches note text, a future rewrite of the three note strings in `sync.ts` that drops or changes `Sync conflict:` would silently break this list. That coupling is accepted as the cost of decision 1 above; a comment at both the note-writing site and the port method's implementation cross-references the other, so a change to one is visible from the other.
3. `docs/decisions/README.md`'s scope note for the review console (from ADR-009: "no table views beyond a plain table") is unaffected. This is the same plain table with one more filter.
4. If a future need arises for something the note text cannot answer (which specific parts conflicted, machine-readable `kept_from`), that is a new decision, not assumed here.
