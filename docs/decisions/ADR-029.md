# ADR-029: The CLI keeps several named Cairns as one

Status: accepted
Date: 2026-09-14
Relates to: ADR-013 (three surfaces), ADR-014 (CLI runtimes), ADR-018 (Azure), ADR-020 (one container), ADR-023 (sync)

## Context

ADR-023 syncs two Cairns, named by address on each run. The owner asked for more: "use sync as a backup/ha strategy, allow cairn cli to register multiple instances and keep them synced regularly, for example work local and sync remote every x minutes (or hours to keep cost low) so we have a hybrid service running cross cloud using the same atomic unit". Then: "allow cli to know all the endpoints and use the best. when starting check for sync from cloud if someone has changed something. and sync local".

"The same atomic unit" is the one container every deployment runs (ADR-020). Nothing on the server needs to change: each copy is an ordinary Cairn, and the CLI does the rest.

The owner was asked four questions and chose the recommended answer each time:

1. **Which instance is the best: the first that answers, in the owner's order.** The CLI tries them in the registered order and stops at the first that answers `/health`. Rejected: the fastest to answer, which probes every instance on every command and so wakes a cloud copy that is asleep, costing money and up to 30 seconds (ADR-018); and the most recently synced, which needs state no command should have to read before it runs.
2. **What "on starting" means: a `cairn start` command.** It starts the local copy if it is down and then syncs. Rejected: a check before every command, which adds a round trip to every one; and doing it only in the scheduled job, which leaves the laptop behind until the job next runs.
3. **How it syncs regularly: a background job the CLI installs.** `cairn sync install` writes a launchd agent on macOS, a systemd user timer on Linux, or a scheduled task on Windows. Rejected: leaving `cairn sync --every` running in a terminal, which stops when the terminal closes; and a server-side scheduler, which would make one server a client of the others and break "no server knows it is being synced" (ADR-023).
4. **How several instances connect: a hub.** The first instance that answers syncs with each of the others in turn. Rejected: every pair, which grows as the square of the count and wakes every cloud copy for each; and a ring, where one copy down cuts the chain.

## Decision

1. **Instances are registered by name** in `instances.json`, next to the CLI's credentials, in the order the owner prefers them. Each has a name (lowercase letters, digits and dashes, up to 32), an address, and optionally a shell command that starts it. The file holds no token: sign-ins stay in the credentials file, one per address, and `cairn login --instance <name>` signs in to one.
2. **Commands:** `cairn instances` lists them with each one's last sync with the first; `cairn instances add <name> <url> [--first] [--start "command"]` adds one, at the end or first; `cairn instances remove <name>` removes one. A name or address already registered is refused.
3. **Routing.** `--instance NAME` picks one. Otherwise `CAIRN_URL` wins, so everything that set it before still works. Otherwise, with instances registered, a command goes to the first that answers `/health`, and says on stderr which it used when it skipped any. With none answering it fails with exit code 1 and lists them. Without instances or `CAIRN_URL`, it is `http://localhost:8787`, as before. `login` and `logout` need `--instance` when instances are registered, since signing in to whichever answered is rarely what was meant.
4. **The probe waits 2 seconds for an address on this machine and 60 for any other,** long enough for a cloud copy starting from zero. It stops at the first that answers, so a cloud copy is not woken while an earlier one is up.
5. **`cairn sync` with no addresses syncs every instance through a hub.** It probes them all at once, says which it skipped, and takes the first that answers as the hub. The hub syncs with each other instance in turn, each an ordinary ADR-023 pair with its own state file. If the hub took changes from one of them, the ones before it are synced once more, so a change made anywhere reaches everywhere in one run. `cairn sync <a> <b>` still syncs one pair, and accepts registered names as well as addresses. `--every` and `--dry-run` work with both.
6. **`cairn start`** checks the first instance. If it is down and has a start command, the CLI runs that command in the background, with its output in a log beside the credentials, and waits up to 90 seconds for it to answer. Then it syncs every instance, which brings in anything changed in the cloud since the laptop was last on, and suggests `cairn sync install` if no job is installed.
7. **`cairn sync install [--every 1h]`** installs a job that runs `cairn sync` every interval, one hour unless given. It needs two or more instances. The job runs this same CLI by its absolute path, so a CLI run from source (`pnpm cairn`) refuses and says to install it first. The job carries only `CAIRN_CREDENTIALS` and `XDG_CONFIG_HOME` when set, so it finds the same instances and sign-ins; never a token. Its output goes to `logs/sync.log` beside the credentials.
   1. macOS: `~/Library/LaunchAgents/dev.cairn.sync.plist`, loaded with `launchctl bootstrap`, run at login and every interval.
   2. Linux: `cairn-sync.service` and `cairn-sync.timer` in `~/.config/systemd/user`, enabled with `systemctl --user`, run a minute after boot and every interval.
   3. Windows: the scheduled task "Cairn sync", made with `schtasks`, every interval in minutes or whole hours.
8. **`cairn sync install --dry-run`** prints the files or command it would use and changes nothing. **`cairn sync uninstall`** removes the job and keeps instances, sign-ins and sync state.
9. **The CLI still uses only what ADR-014 allows.** Starting a program and running `launchctl`, `systemctl` or `schtasks` use `node:child_process`, which the CLI already used to open a browser.

## Consequences

1. Any copy can serve when another is down, and each is a full backup of the others as of its last sync. It is not high availability in the strict sense: an edit made on one copy reaches the others only at the next sync, and two edits to the same record between syncs are a conflict that ADR-023 settles by keeping the newer and the other in history.
2. Only the CLI picks the best instance. An MCP client such as Claude Code or claude.ai is set up with one address and keeps using it; if that copy is down, the client reconnects to another only when its address is changed. A local proxy that forwarded MCP to the best instance would close this, and is not built.
3. **Cost.** Every sync wakes each cloud copy that has scaled to zero, and Azure then stays up for about 30 minutes (ADR-018). A job every hour keeps it up about half the time; one every 30 minutes or less keeps it up all the time and costs what an always-on copy does. One hour is the default for that reason.
4. The hub is whichever answers first, usually the laptop. When the laptop is off, the job does not run, and the cloud copies are not synced with each other until it runs again; with the laptop's job as the only scheduler, two cloud copies edited while the laptop is off drift apart until then. Running the job on an always-on machine as well closes that gap.
5. **Windows limits.** A scheduled task cannot carry environment variables, so a job installed with `XDG_CONFIG_HOME` or `CAIRN_CREDENTIALS` set uses the default folders instead, and the CLI says so. It has no log file, since `schtasks` cannot redirect output, and it does not run at login, only on the interval.
6. **Linux limit.** A systemd user timer runs only while the user is logged in, unless lingering is enabled (`loginctl enable-linger`). The docs say so; the CLI does not change it, since it is a system setting.
7. The instances file and sync state live beside the credentials, so the owner's other machines each have their own list. That is intended: a machine lists what it can reach.
8. The tests use three real Cairns behind an injected fetch that can take any of them down, and a fake for starting programs and running `launchctl`, `systemctl` and `schtasks`. Nothing in the tests installs a job.
