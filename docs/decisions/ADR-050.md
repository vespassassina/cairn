# ADR-050: Backups go to the platform's own object storage, named by one setting

Status: accepted
Date: 2026-09-16
Relates to: ADR-017, ADR-018, ADR-020, ADR-043, ADR-049

## Context

ADR-049 built the backup engine and left one thing unfinished. The only archive was a folder, and on Azure a folder is the container's own disk, which does not outlive the container. Cairn warned about this at startup, which was honest and useless: a warning tells the owner their backups are worthless, it does not give them one.

The owner's direction closed it:

> "on azure the backup must go to blob, on aws on s3 and so on."

So the archive has to reach the object storage each platform already gives Cairn. The shape of the answer was already in the repository. `CAIRN_REPLICA_URL` is one URL whose scheme says where Litestream writes, `abs://` on Azure and `s3://` elsewhere, and both are already provisioned, credentialled and reachable wherever Cairn runs.

Two ways to talk to them. The vendor SDKs, `@azure/storage-blob` and `@aws-sdk/client-s3`, are the ordinary choice and both are large: the AWS client alone pulls in tens of megabytes for four operations, into an image ADR-020 keeps deliberately small and ADR-018 keeps free of storage keys. Or REST, by hand. Azure blob operations are a bearer token from the platform's identity endpoint and four HTTP calls. S3 is four HTTP calls plus Signature Version 4, which is about eighty lines of Web Crypto and is the only part with any real risk in it, because a signature is either exactly right or completely rejected.

## Decision

1. **One setting names the destination, and its scheme chooses the implementation.** `CAIRN_BACKUP_TO` takes a folder path, `abs://<account>@<container>/<prefix>`, `s3://<bucket>/<prefix>`, or `off`. The Azure form is deliberately identical to `CAIRN_REPLICA_URL`, so neither has to be learned separately.
2. **`CAIRN_BACKUP_DIR` is renamed to `CAIRN_BACKUP_TO`.** A setting called `DIR` that accepts `s3://bucket` is the kind of misleading name CLAUDE.md counts as a bug. It was introduced one commit earlier and has never been in a release, so the rename costs nothing but this sentence.
3. **No cloud SDK.** Both archives are written against the REST APIs, so the server keeps zero cloud dependencies and the same image still runs everywhere (ADR-020). This extends hard rule 1's spirit past `core`: the container has no vendor SDK in it at all.
4. **Azure authenticates as the managed identity, never with a key.** The token comes from `IDENTITY_ENDPOINT` where the platform injects one, and from the instance metadata service otherwise, so the same code works on Container Apps and on a VM. ADR-018's promise that no storage key exists anywhere in the deployment still holds.
5. **S3 takes credentials from where AWS itself looks:** the environment, then the ECS or App Runner credentials endpoint, then the EC2 instance metadata service with IMDSv2. Never from a config file, per hard rule 18.
6. **An upload is not visible as a backup until it is complete.** Azure stages blocks and commits a block list; S3 does a single streamed PUT. Both give the same guarantee the folder archive gets from renaming into place: a failed upload leaves nothing that looks like a backup.
7. **Uploads stream rather than buffer.** Azure reads the file in eight megabyte blocks; S3 signs the payload as `UNSIGNED-PAYLOAD`, which is allowed over HTTPS and is what lets the bytes go from the file to the socket without being held in memory to be hashed first. A personal wiki would survive buffering; a rule the code silently depends on is worse than the twenty lines that avoid it.
8. **Anything in the container that is not one of our backups is left alone,** never listed, never counted towards retention, never deleted. The name pattern from ADR-049 is the test.
9. **The Azure template creates a second blob container,** `cairn-backups`, separate from the replica's, per ADR-049 decision 10.
10. **An `s3://` destination with no region stops Cairn at startup** naming `CAIRN_BACKUP_REGION`, rather than guessing a region and failing every signature later.

## Consequences

1. Backups on Azure now survive the container, which is what ADR-049 was missing. The startup warning stays for the case it still describes: a local folder on a machine whose disk is not durable.
2. `CAIRN_BACKUP_ENDPOINT` makes any S3-compatible store work, so MinIO, Backblaze and others need no further code. This is also the honest path for GCP, whose interoperability endpoint speaks S3 and which ADR-043 left unverified; it stays unverified until someone runs it.
3. Signature Version 4 is ours to maintain and ours to get wrong. It is checked against AWS's published `get-vanilla` test vector, so the signature is verified byte for byte against a value AWS defines, not merely accepted by a stub of our own design. A second test proves the signer is not returning a constant.
4. **Neither archive has been run against a real Azure or a real AWS account.** They are tested against strict local stubs, which check that requests are authenticated, versioned and correctly shaped, and that a file goes up and comes back byte for byte. What a stub cannot prove is that the real service agrees. The first real run goes in the changelog.
5. The four archive operations are now implemented three times, once per backend. That is the cost of not taking the SDKs, and it is bounded: the `Archive` interface is five members, and the engine above it knows nothing about any of them.
