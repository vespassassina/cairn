# ADR-020: One container everywhere, as small as it can be

Status: accepted
Date: 2026-09-12
Supersedes: the runtime targets in ADR-006 (Azure Functions, AWS Lambda) and consequence 6 of ADR-018
Relates to: ADR-005, ADR-018, PRD sections 2 and 7

## Context

The PRD planned Azure Functions with Cosmos DB on Azure, and Lambda with DynamoDB on AWS. ADR-018 put Cairn on Azure as a single container with SQLite and Litestream instead, as the path that worked first, and kept Functions with Cosmos as "the path to scaling out".

The owner asked whether Functions and Cosmos would be better on Azure, and whether the container path throws good capabilities away. The comparison:

1. **Functions adds little over a container for Cairn.** Container Apps also scales to zero, has a free grant that covers personal use, and gives HTTPS and a managed identity. Functions bills per execution rather than per active minute, which does not matter inside the free grants, and probably starts faster, because a container restores its database before the first request. Against that: an Azure-only entry point and deploy, spike S1 never run, and no local disk, so Functions forces a network database.
2. **Cosmos adds real things**: no write-loss window, several instances and regions, no restore on start, native vectors and a change feed. It costs real things too: full-text search without Dutch and with multi-language in preview (PRD Q1), vectors needing dedicated throughput inside the free tier's 1,000 RU/s (Q7), an emulator that may not do full-text (Q8), and a second search backend to evaluate on every search change.
3. **SQLite already has vectors (sqlite-vec) and point-in-time restore (Litestream)**, so neither is lost by staying on it.
4. **What the container path gives up today**: up to about a second of writes if the container dies, a cold start that grows with the database, and one instance in one region. None of these matters for one person or a small team.

The owner's direction: "ok, let's go with containers", "keep it as compact as possible, not a fleet of containers", and "i am going to run on proxmox later, add local mounted storage".

## Decision

1. **Cairn runs as one container, on every target.** The same image runs on a person's own server (Proxmox, a NAS, any Docker host), on Azure Container Apps, and on whatever AWS service is chosen for containers. Plain Node without a container stays the local development path.
2. **One deployment is one container.** It holds the server, the indexer and Litestream, and nothing runs beside it: no sidecars, no separate search, indexer, queue or database services, no gateway. The only other resource, where there is one, is the object storage Litestream writes to. A feature that seems to need a second container needs an ADR saying why it cannot live in this one.
3. **SQLite with FTS5 is the default store on every target,** kept in one of two ways, which can be combined:
   1. **A mounted local volume at `/data`,** on a person's own server. The database lives on that disk and survives the container. `deploy/docker/compose.yaml` and `docs/DEPLOY-DOCKER.md`. The volume must be a local disk, never NFS or SMB, where SQLite's locking is unreliable.
   2. **A Litestream replica** in object storage: required where the container's disk is temporary (Azure, ADR-018), optional elsewhere as a copy off the machine.

   The start script says which applies, and stops with the fix when `/data` is not writable.
4. **Azure Functions and AWS Lambda are no longer targets.** Spike S1 is closed without running. No `entry/azure.ts` or `entry/lambda.ts` is written. The server still uses web-standard `Request` and `Response` and the stateless MCP transport (ADR-006), because both are simpler and suit scale to zero; they are no longer requirements for a platform.
5. **Cosmos DB and DynamoDB become optional storage adapters for the same container,** chosen by configuration, and built only when one of these happens:
   1. someone needs more than one instance;
   2. the restore on cold start becomes too slow, once measured;
   3. the write-loss window turns out to matter.

   The adapter boundary (ADR-005) is kept exactly as it is, so this stays one adapter's work. A middle option, recorded for then: documents in Cosmos and search in SQLite, rebuilt from Cosmos, which keeps FTS5 search and gains Cosmos durability.
6. **The first real Azure deployment measures the cold start and the write-loss window**, including whether Litestream syncs on a normal shutdown, which would limit the loss to crashes. The numbers go in the changelog and decide whether trigger 2 or 3 has fired.

## Consequences

1. One image, one deploy shape, one search backend to evaluate. A problem seen in the cloud can be reproduced on a laptop with `docker run`.
2. The PRD's promise that switching platforms is only configuration now means switching where the one container runs, not rewriting entry points.
3. The AWS free-tier question reopens. Lambda and DynamoDB were the always-free path; a single container on AWS may not have a free grant as generous as Container Apps. To be answered when the AWS target is chosen (PRD Q7).
4. Scaling beyond one instance is not possible until a network store is added. That is accepted: Cairn is for a person or a small team.
5. The Cosmos questions (PRD Q1, Q8, and the Cosmos part of Q7) no longer block anything. They matter again only when a trigger in decision 5 fires.
