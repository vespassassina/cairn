# ADR-045: Restore reaches REST and the CLI, MCP keeps its own way

Status: accepted
Date: 2026-09-15
Relates to: ADR-008, ADR-013

## Context

`pages.restore` has existed in core since ADR-008: it reads an old revision's snapshot and writes it back as an ordinary update, so restoring is itself just another revision that can be undone the same way. The review console has called it since the same commit, behind "Restore this version" on a page's history screen. Neither REST nor the CLI ever exposed it: a person without the console, or an agent working only from a shell, had no way to undo a bad edit short of retyping the old text by hand.

ADR-013 rule 14 (CLAUDE.md hard rules) says a capability added to one surface is added to the others, or an ADR says why not. Checking the third surface, MCP, found it already covers both halves of what was missing:

1. **Viewing an old version without changing anything** ("peek"): `get_revision` already returns the full snapshot (title, tags, sources, body) alongside its diff. An agent calling it changes nothing.
2. **Undoing a change**: `get_revision`'s own description already tells an agent how: "read the version you want back and write it with `update_page` mode `replace_body`." This composes two tools an agent already has, rather than a third that would do the same write with less visible reasoning.

So MCP's gap was documentation, not capability, and REST and the CLI were the two surfaces genuinely missing something.

## Decision

1. **REST gets `POST /pages/:id/revisions/:version/restore`**, taking `If-Match` on the page's current version (ADR-008 rule 3's usual optimistic concurrency) and an optional `change_note`. It calls `pages.restore` exactly as the console does, and returns the updated page the same shape as `PATCH /pages/:id`.
2. **The CLI gets two commands:**
   - `cairn peek <page-id> <version>` prints an old revision in full, as Markdown, changing nothing. It is `cairn revision` without the diff framing, for someone who wants to read the old page rather than compare it.
   - `cairn restore <page-id> <version> --version V` calls the new REST endpoint. `--version` is the page's current version, the same optimistic-concurrency argument `move`, `publish` and `delete` already take, so a stale restore fails with `version_conflict` rather than silently overwriting a newer edit.
3. **MCP is not changed.** `get_revision` already serves as peek, and its description already documents the `get_revision` then `update_page` route to a restore. A dedicated `restore_page` tool would take the same core path with less of the reasoning visible in the transcript; nothing here forecloses adding one later if that composition proves error-prone in practice.

## Consequences

1. A person with only the CLI, or an agent with only a shell, can now undo a bad edit as a single command, matching what the console could already do.
2. `cairn peek` and `cairn restore` are read-then-write, like every other CLI write command: `peek` needs no version, `restore` needs the current one from `cairn read`.
3. The three surfaces are not identical here, and that is fine per ADR-013: REST and the CLI get a dedicated verb because there was no other way to reach the capability; MCP already had one, through composition rather than a single tool.
