# ADR-068: jSquash is the WASM codec for attachment thumbnails

Status: accepted, GIF part superseded by ADR-069 (the named `@jsquash/gif` package does not exist)

Date: 2026-09-23

Relates to: ADR-064 (attachments, decision 6)

## Context

ADR-064's decision 6, added at acceptance, commits to a best-effort WebP thumbnail for the four raster attachment types (PNG, JPEG, WebP, GIF), generated by a WASM codec in the API process rather than a native library, so the container stays the one small image ADR-020 asks for. It named the constraint but not the library: that is a real dependency decision on its own, per this project's stated rule that dependencies are decisions, stdlib first, log the rest.

The candidates considered:

- **jSquash** (`@jsquash/png`, `@jsquash/jpeg`, `@jsquash/webp`, one package per codec): WASM builds of the same codecs Squoosh (Google's own image-compression tool) uses, MIT licensed, no native OS dependency, actively maintained, each package small and single-purpose. Needs one decode package per input format plus the WebP encode package; a GIF input decodes its first frame only, which is enough for a thumbnail.
- **wasm-vips**: libvips compiled to WASM. Handles far more formats and is faster for bulk work, but it is a much larger dependency, on the order of five to ten times the size, built for a general image pipeline. This feature only ever does one thing, decode one of four formats and encode a small WebP; the extra surface bought nothing here.
- **sharp**: the common choice for image work in Node, but it wraps native libvips through node-gyp, a native OS-level dependency. Excluded outright: it is exactly what ADR-064 decision 6 already ruled out ("no new OS-level dependency is added to the Dockerfile").

## Decision

Thumbnail generation uses `@jsquash/png`, `@jsquash/jpeg` and `@jsquash/webp` (decode the uploaded bytes with the package matching the sniffed content type from ADR-064 decision 5, encode the result with the WebP package). One package per format actually used, not a bundled all-formats install. `@jsquash/gif`'s decoder is used for a GIF input's first frame; there is no separate thumbnail encoder for GIF, since the output is WebP regardless of input.

## Consequences

1. Four small, focused packages instead of one large image-processing dependency, matching what ADR-064 decision 6 already asked for: no native OS dependency, no growth in the Dockerfile.
2. If a fifth raster type is ever added to the attachments never-refused list, it needs its own jSquash decode package (or an ADR explaining why a different codec is used for it instead) — this is not a general-purpose image pipeline, it stays scoped to what decision 6 named.
3. jSquash's WASM modules run inside the same Node process as the rest of the API; thumbnail generation is already queued off the write path per decision 6, so a slow decode does not block a confirmed upload, only delays when the thumbnail becomes available.
