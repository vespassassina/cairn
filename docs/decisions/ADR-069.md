# ADR-069: GIF is dropped from attachment thumbnails; `@jsquash/gif` does not exist

Status: accepted

Date: 2026-09-23

Relates to: ADR-064 (decision 6), ADR-068 (superseded in part by this one)

## Context

ADR-068 named `@jsquash/gif` as the fourth decoder for ADR-064 decision 6's four raster thumbnail types (PNG, JPEG, WebP, GIF). Building decision 6 against that choice, the package turned out not to exist: checked against the npm registry (`npm view @jsquash/gif` answers 404) and against the jSquash project's own published package list on 2026-09-23. Only a third-party fork republishes a GIF decoder under an unrelated scope, unreviewed and not what ADR-068 named.

ADR-068 was accepted the same day this was found, on the strength of research that missed this one package. The choice for PNG, JPEG and WebP stands unchanged; only the GIF piece was wrong.

The options: substitute an unreviewed third-party package for the one ADR-068 actually named (exactly the shortcut ADR-068's own reasoning about "no new OS-level dependency" and "log the rest" argues against taking without a decision), or drop GIF from decision 6's thumbnail set until a real candidate is reviewed.

## Decision

GIF is dropped from ADR-064 decision 6's thumbnail set. A GIF attachment is still accepted as content exactly as before (decision 5 is unchanged); it simply never gets a thumbnail, the same "not an error" path decision 6 already defines for a failed or unsupported case; the console falls back to its generic file icon for one, same as any other thumbnail-less attachment.

PNG, JPEG and WebP thumbnails still use `@jsquash/png`, `@jsquash/jpeg` and `@jsquash/webp`, exactly as ADR-068 decided; that part of ADR-068 is unchanged and not superseded.

Adding GIF back is a smaller, separate decision, once a real GIF decoder is found and reviewed the way jSquash's other three packages already have been; nothing here rules that out, it's just not decided yet.

## Consequences

1. `docs/decisions/ADR-064.md` decision 6 describes four raster types; read together with this ADR, three of the four get a generated thumbnail today, GIF does not.
2. `ThumbnailUnavailableError` in `packages/api/src/attachments-thumbnail.ts` covers this case already, since "no decoder wired up for this content type" was already a defined failure path, not a new one added for this correction.
3. A future ADR that adds a GIF decoder supersedes only this ADR's third-format gap, not ADR-068's PNG/JPEG/WebP choice or ADR-064 decision 6 itself.
