# ADR-062: mitigate the Litestream stall with a tighter backup cooldown and a source build of the unmerged fix

Status: the backup cooldown stands; the source build is superseded by ADR-063, which found it corrupts snapshots

Date: 2026-09-18

## Context

ADR-061 confirmed the Azure data losses as Litestream issue #1515, a bug in every released 0.5.x build (0.5.14 through 0.5.17, what Cairn ran) where the follower's gap-bridging logic never consults the L9 snapshot, so a stall it cannot bridge is silent and a restart does not clear it. No fix is released. ADR-061 left four mitigation options as the owner's call, since none is a Cairn code fix: wait for a release, build against an unreleased fix, add a watchdog, or lean harder on Cairn's own independent backups. The owner chose to do both the backup change and the source build now, and to test the result.

## Decision

1. **`CAIRN_BACKUP_AFTER_HOURS` defaults to `0.5` on Azure**, down from the app's own built-in default of `3`, set in `deploy/azure/deploy.sh` and `deploy/azure/main.bicep`. This path (ADR-049) does `VACUUM INTO` copies straight from the local database and never touches Litestream's replica, so it is unaffected by issue #1515. It bounds what the bug can lose to at most thirty minutes of writes, at the cost of a `VACUUM INTO` running more often. This is a stopgap: it does not fix the replica, it only shortens the worst case while it stays broken.

2. **The Dockerfile builds Litestream from source** at a pinned commit on [PR #1514](https://github.com/benbjohnson/litestream/pull/1514) (`darkgnotic/litestream`, branch `snapshot_compaction_coordination`, commit `9dad482c64a0d156fea1ff8c07b56cd288b07035`), replacing the pinned-release-tarball-and-checksum install. That PR adds `fillFollowGapFromSnapshot`, letting the follower consult the L9 snapshot when the ladder cannot bridge a gap; issue #1515's own reporter confirmed it resolves the bug when tested. This trades a checksummed official release for an unmerged, unreleased branch: real trust is extended to code that has not gone through Litestream's own release process, and the pin needs to be watched by hand, since the branch can move without anyone here noticing. Revert to the release-tarball model (see git history on `Dockerfile` before this commit) once a tagged Litestream release carries the fix, and drop this ADR's mitigation once that happens.

3. **This is not decided as permanent.** Both changes exist only because #1515 is unfixed upstream. When a release ships with the fix: bump `LITESTREAM_VERSION` back to a source-build-free Dockerfile, and raise `CAIRN_BACKUP_AFTER_HOURS` back to `3` (or leave it low, if the owner prefers the cheaper recovery point regardless).

## Consequences

1. Azure now takes a full database backup roughly every half hour of active writing, more often than the general 3-hour default, at negligible cost for a personal wiki's size.
2. The production image runs Litestream built from an unmerged, unreleased upstream branch rather than a numbered release. If that branch changes behaviour before merging, Cairn's replica would change behaviour on the next image build without a new Litestream version number to signal it. The pinned commit SHA is the only guard; changing it is a deliberate, reviewed edit to the Dockerfile.
3. Verification standard, same as ADR-061: this mitigation is confirmed working only once a live test shows fresh writes reflected in Litestream's L1 and L2 compaction files in Azure Blob Storage, sustained past L0's five-minute retention window, not just that the build succeeded or the container started. **Met on 2026-09-18**, after deploying `ghcr.io/vespassassina/cairn:edge` (digest `8fee46d`): a fresh L9 snapshot appeared at 12:35 UTC on startup, then a transaction flowed through L0 (12:36) and L1 (12:36) into L2 (12:40), the level that had stalled before. This is the first Azure deploy where L2 advanced without a manual intervention.

## Relates to

ADR-061 (the confirmed root cause this ADR mitigates), ADR-049 and ADR-050 (the independent backup path this ADR leans on harder), ADR-018 and ADR-020 (the Litestream replica architecture), ADR-046 (why Litestream's version is normally kept current and pinned deliberately).
