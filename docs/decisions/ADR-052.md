# ADR-052: A pair of Cairns is offered a schedule the moment it becomes a pair

Status: accepted
Date: 2026-09-16
Relates to: ADR-020, ADR-023, ADR-029

## Context

ADR-029 made several Cairns usable as one: registered by name, a command going to the first that answers, and `cairn sync` reconciling them. It also added `cairn sync install`, which writes a launchd agent, a systemd user timer or a Windows scheduled task so the copies stay together with no terminal open.

That command existed for some time and went unrun, including on the owner's own two Cairns. Nothing was broken about it. It was mentioned in `cairn --help` and in `docs/CLI.md`, in a list of other things, and a person who has just registered a second Cairn has no reason to read further. The result is the worst version of this feature: two Cairns that a person believes are paired, drifting apart at whatever rate they are edited, and a sync that happens when somebody remembers.

The owner's direction was short:

> "paired instance should sync every few hours automatically"

Two questions had to be answered before that could be built, and both are decisions rather than details.

The first is the interval. Every sync run reaches the cloud copy, and on Azure that wakes a container that has scaled to zero, which then stays up for its idle timeout of about thirty minutes. The interval is therefore not a freshness setting, it is a choice about how much of the day the cloud copy is billed as awake. The default was an hour, which leaves it awake roughly half the time and quietly works against ADR-020's premise that Cairn lives inside a free grant.

The second is consent. Installing the job is not a change to Cairn's own state. It writes a file into the person's login agents and asks their operating system to run a program every few hours, for as long as the machine exists. That is their machine, not Cairn's.

## Decision

1. **The default interval is four hours,** raised from one. Six wakes a day, with the cloud copy asleep for about three hours in every four. `--every` still takes anything, and the documentation states the cost in wakes rather than in abstract terms.
2. **Registering the second Cairn offers the schedule.** The offer is made once, at the moment a pair comes into being, which is the only moment the person is certainly thinking about the pair. It is not made when the first is registered, because one Cairn has nothing to sync with, and not again once a job is installed.
3. **It is an offer, never an action.** Anything but an explicit yes installs nothing and prints the command to run later. A background job that appears on somebody's machine because a wiki command decided it should is not something Cairn does, whatever the direction said, and the difference between offering and doing is one keystroke for the person and a large difference in what Cairn is allowed to assume about them.
4. **With nobody there to answer, it says how and carries on.** No terminal, or input being piped, which covers every script and every agent: the registration succeeds and a line on stderr names the command. Cairn never blocks waiting for an answer that cannot come.
5. **A failed install never costs the registration.** The instances are saved first. If the job cannot be installed, that is reported with the command to retry, and the exit code still says the registration worked, because it did.
6. **Asking is a capability on the CLI's `Io`,** like opening a browser or running a program, so it is injected and the tests drive it. The implementation reads one line from the controlling terminal through `node:fs/promises`, which hard rule 16 already allows, rather than through `node:readline`.

## Consequences

1. Two registered Cairns now converge on their own, which is what a person who registered two of them meant. A change made on the laptop reaches Azure within four hours without anyone remembering anything.
2. Freshness is worse than it was for anyone who had installed the job at the old default, and deliberately so. Four hours is long enough that `cairn sync` by hand remains the right move when someone wants a change across now, and the guides say so.
3. The offer is one more thing on screen during setup, at the one moment when it is the thing being set up.
4. Cairn can now ask the person a question, which it could not before. That is a capability worth being careful with: it is one question, in one place, and the answer is optional. A CLI that asks things is a CLI that hangs when nobody is there, so the null case is the tested one.
5. Not decided here: whether the schedule should also be offered by `cairn start` or by `cairn login`, both of which see the same situation. They print the command, as before.
