# ADR-047: A deploy names the image by digest, and says when it changes nothing

Status: accepted
Date: 2026-09-16
Relates to: ADR-018, ADR-046

## Context

Recovering from the outage in ADR-046 needed a container carrying the fix. The owner ran `deploy/azure/deploy.sh` three times. Each run printed "deploying (a few minutes)", then "waiting for the new version to start", then hung for five minutes and failed with "the new version did not start". No new revision was ever created, and the container carried on running the image it had been running since before the incident.

Three separate faults produced that:

1. **The template named a mutable tag.** `main.bicep` took `ghcr.io/vespassassina/cairn:latest` and passed that string to the container. Container Apps makes a new revision only when the template changes, and a tag is the same string however often the image behind it moves. So a redeploy after a new build compared identical templates, created no revision, and never re-pulled. The deploy was a no-op by construction, not by accident.
2. **The default tag is one that only a release moves.** CI publishes `edge` from `main`, and the version and `latest` from a release tag (ADR-018). The script defaulted to `latest`, so nothing committed to `main` could ever reach a deployment, however many times the script was run. On the day, `latest` was still v0.1.5.
3. **The wait misread the result.** The readiness loop compared `latestReadyRevisionName` with `latestRevisionName` and waited for them to agree. When no revision had been created it waited for something that would never appear, then reported "the new version did not start". The new version had not failed to start. It had never been asked to exist. An error that describes the wrong failure is worse than no error, because it sends the reader somewhere there is nothing to find.

The cost was not the twenty minutes. It was that the owner reasonably believed the fix had been deployed and had not worked, when in truth it had never been deployed at all.

## Decision

1. **The image is resolved to a digest before it reaches the template.** The script asks the registry what the tag points at now and deploys `repo@sha256:...`. A moved tag then always produces a different template and a real rollout, and an unmoved one always produces an identical template and no rollout. Both outcomes become honest.
2. **Resolution needs nothing but curl.** An anonymous pull token and a manifest `HEAD` against ghcr.io, which is where Cairn publishes. Docker is not required, because the machine deploying Cairn is not required to be able to run it.
3. **A tag the registry does not have stops the run.** The script says the registry has no such tag and names `:latest` and `:edge`, rather than letting Azure fail to pull it minutes later with an error about a container image.
4. **A registry that cannot be reached is a warning, not a failure.** The tag goes into the template as it is, and the warning says exactly what that costs: a moved tag will not be picked up, and a digest can be given instead.
5. **A deploy that changes nothing says so.** The script compares the newest revision before and after. When they are the same it reports "no change to deploy", names the running image, and says how to deploy a different one. It does not wait for a revision that was never created.
6. **A deploy that does change something says what it replaced.** The running image and the new one are both printed, and a running image deployed by tag rather than digest is called out, because that is the state in which earlier redeploys were silently ineffective.
7. **The health-check failure points at the container's own log,** and says that a healthy revision is not the same as a Cairn able to serve, because by ADR-046 a Cairn that cannot vouch for its database stops on purpose.

`latest` stays the default. Someone deploying Cairn for the first time should get the newest release, not the newest commit. What changes is that `edge` is documented as the way to deploy `main`, and that deploying `edge` warns it is not a release.

## Consequences

1. A redeploy now does what it appears to do, or says plainly that there is nothing to do. The failure mode that cost this incident an afternoon cannot recur in the same shape.
2. Deployments become reproducible. A digest in the template is a record of exactly what is running, which a tag never was.
3. Fixes on `main` can be deployed without cutting a release, by asking for `:edge`. This matters for a project whose stated workflow is to commit straight to `main` (CLAUDE.md), where waiting for a release tag to deploy a fix is a contradiction.
4. The script now depends on reaching ghcr.io before it can deploy. That dependency degrades to a warning rather than a failure, so an offline or firewalled deploy still works, with less certainty about what it deployed.
5. Only ghcr.io is resolved. A fork publishing elsewhere gets the pass-through warning and should deploy by digest. Adding other registries is a matter of another token endpoint, not another design.
6. **Still open:** nothing checks that the digest which was deployed is the digest that ends up running. Container Apps is trusted to pull what the template names.
