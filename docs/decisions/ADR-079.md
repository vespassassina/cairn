# ADR-079: The dropbox is an Inbox collection fed by one endpoint and scoped drop tokens

Status: proposed

Date: 2026-09-24

Relates to: ADR-064 (attachments: files need `CAIRN_ATTACHMENTS_TO`), ADR-066 (publish tokens, the pattern for drop tokens), ADR-075 (well-known root collections), ADR-017 (auth on a non-loopback bind), hard rules 14, 15, 16, 18, 19. Spec: `docs/specs/dropbox.md`.

## Context

The owner wants to throw text, photos and files at Cairn from anywhere, a phone, a shell, a script, and have an agent file them later. Agents without the CLI or MCP must be able to drop too, with auth. The roadmap's "Quick capture" item described this without a design.

Options for where a drop lives: (a) a new record type with its own store, rejected as a second source of truth that would need its own history, search and sync; (b) an ordinary page under a well-known root collection, the ADR-075 pattern, chosen. Options for auth without CLI or MCP: (a) reuse OAuth tokens, rejected because a phone share sheet or a `curl` line cannot run the flow and a full-scope token in a Shortcut is too much to leak; (b) a token scoped to one endpoint, hashed at rest, shown once, modelled on ADR-066, chosen.

## Decision

1. **Inbox.** `INBOX_COLLECTION_NAME = "Inbox"` in `packages/api/src/templates.ts`, a root page found by title and created on first use. A drop is an ordinary page under it: title from the `title` field, else the first line of the text cut at 80 characters, else the first filename, else the timestamp; body as given with each file appended as an `attachment:<id>` link; tags as given plus `drop`; `url` as a source.
2. **One operation, `createDrop`**, in `operations.ts`, behind `POST /api/v1/drops` (multipart or JSON: `text`, `title`, `tags`, `url`, `files[]`), the console's `/inbox/new`, the mobile app's `/m` and `cairn drop`. Limits: 25 MB per file, 10 files, 64 KB of text. The server uploads files to the blob store itself (ADR-064's signed-URL dance is not something a share sheet can do), streaming, at most two drops in flight. With attachments off, a drop with files fails with `attachments_off` naming `CAIRN_ATTACHMENTS_TO`; text-only drops always work.
3. **Drop tokens.** A well-known table `Drop tokens` (`packages/api/src/drop-tokens.ts`, the shape of `publish-tokens.ts`): `name`, `description`, `kind` (`person` or `agent`, chosen at creation), `token_hash`, `created_at`, `last_used_at`, `revoked_at`. The token is `cairn_drop_` plus 32 random bytes base64url, shown once, SHA-256 at rest. Accepted only on `POST /api/v1/drops`; any other route answers `403 drop_token_scope`. A revoked token answers `401` naming revocation. `last_used_at` moves on every use. Managed in the console at `/settings/drop-tokens` and by `cairn drop-token create|list|revoke`; never through MCP.
4. **Actor.** A drop made with a session or OAuth token is written by that actor. A drop made with a drop token is written as the token's `kind`, with the label `token "<name>"`, so the changes feed and the ADR-078 review queue tell a phone from a script.
5. **No processing state.** A drop is unprocessed while it sits under Inbox. Processing it means moving it under the page it now belongs to, or deleting it once absorbed; the revision history keeps that it was a drop. Agents are told this in the instructions and the skill, and the workspace summary reports `Inbox: N drops waiting`. No new MCP tool: `list_children`, `get_page`, `update_page`, `move` and `delete_page` do the work.
6. **Console.** `/inbox` lists drops newest first with thumbnails and a file-away form per row; the home page shows the count. Within ADR-009.

## Consequences

1. Drops are pages from the first byte: searchable, versioned, synced and exported with no new machinery. The Inbox is just a collection that should be empty.
2. A third kind of token exists beside OAuth and publish tokens, with a one-endpoint scope. `docs/AGENT-OPERATE.md` gains a section; the guide test enforces it.
3. Server-side upload puts bytes through the container for the first time (ADR-064 kept them out of the API). Bounded by the limits in decision 2; a large drop is the phone's problem, not the wiki's.
4. HEIC from an iPhone arrives as a file link, not a thumbnail (ADR-064 thumbnails cover PNG, JPEG and WebP). Documented; conversion is a later item.
5. Email-to-Cairn is out: it needs an inbound mail provider outside the container.
