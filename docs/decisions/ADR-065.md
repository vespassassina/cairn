# ADR-065: Mermaid, Vega-Lite and Viz.js are the text-form visualizations; everything else is an attachment

Status: accepted

Date: 2026-09-19

Relates to: ADR-064 (attachments), the 2026-09-14 owner direction on the roadmap to keep diagrams as text

## Context

ADR-064 scoped attachments to binary files and left open what happens on the text side: which diagram and chart formats Cairn treats as first-class content, kept as text in a page body so history, search and the sync merge all work on them unchanged, same reasoning as the existing Mermaid direction on the roadmap.

The candidates considered:

- **Mermaid**: flowcharts, sequence, state, ER, Gantt, mind maps, and a rough C4-style architecture diagram, all as one small text grammar. Already the project's committed choice for diagrams.
- **Vega-Lite**: a declarative JSON spec for charts driven by data. The spec itself, not rendered pixels, is the diffable artifact, which matters when a chart is built from a table's rows rather than hand-drawn.
- **Viz.js** (Graphviz/DOT compiled to run in the browser): auto-laid-out node/edge graphs at a scale Mermaid's layout engine does not handle well. The wiki's own page graph, backlinks and neighbours, is exactly this shape: an arbitrary, growing node/edge graph that needs a real layout algorithm, not a diagram someone composed by hand.
- **D3**: a library for binding data to SVG, not a text format. Rejected as a content format because its output is code, not a diffable spec; nothing about it fits a page body.
- **Structurizr DSL** for stricter C4 modeling: rejected as redundant with what Mermaid's flowchart and `C4Context` diagrams already cover, not worth a second grammar for the marginal rigor.
- Blueprints, floor plans, PCB-style layouts, and anything else spatial or drawn rather than data-shaped: not representable as a small text grammar at all. These go through attachments (ADR-064), not through a diagramming library.

## Decision

1. **Mermaid** is the format for diagrams an owner or agent composes by hand: flowcharts, sequence, state, ER, Gantt, mind maps, simple architecture views. Lives inline in the page body as a fenced code block, exactly as already established.
2. **Vega-Lite** is the format for charts generated from data already in Cairn, most directly a table's rows. The spec is stored as text (inline in the page, or as a table field), and rendering is deferred to view time; the spec is what history and sync operate on, never a pre-rendered image.
3. **Viz.js** renders the wiki's own graph views (backlinks, neighbours, the page tree) in the console. This is the one visualization in this decision that is not owner-authored content: it is generated at view time from data Cairn already holds, so there is nothing for it to store as text, and it does not appear in a page body.
4. **D3 is not used for content.** It stays out of scope entirely unless a future console feature needs bespoke, non-graph interactive visualization that none of the above covers, and that is a separate decision if it comes up, not a standing capability.
5. **Everything that is not one of these three** (spatial drawings, blueprints, floor plans, scanned documents, anything without a text-native representation) goes through the attachments capability in ADR-064, as a binary file linked from the page, not forced into a diagramming grammar it doesn't fit.

## Consequences

1. Three rendering libraries ship with the console, each solving a distinct problem (hand-authored diagrams, data-driven charts, auto-laid-out graphs); none overlaps another, so there is no ambiguity about which one a new page reaches for.
2. Every diagram and chart a page holds stays plain text, so it works with search, history and the sync merge without special-casing, matching the same reasoning already applied to Mermaid on the roadmap.
3. A future request for a diagram type none of the three cover (a genuinely spatial layout, for instance) is answered by attachments, not by adding a fourth library. Adding a fourth text format needs a new ADR that shows why an existing one does not fit, per the same bar Structurizr and D3 were held to here.
4. The wiki graph view depends on Viz.js being available client-side in the console; this is a console dependency, not a content format, and carries no export or sync implications since it renders derived data, not stored content.
