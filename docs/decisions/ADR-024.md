# ADR-024: Collections sit in the page tree, and relation fields are links

Status: accepted
Date: 2026-09-13
Amends: ADR-023 decision 5 (sync writes pages before collections)
Relates to: ADR-005, ADR-008, ADR-013, ADR-016

## Context

The owner's wiki has two collections, Peptides and Stacks, that belong together, and asked: "is it possible to add a new root/collection and move sub collections there by just adding a link? this should be a feature of cairn". Then: "what about crosslinking in the same collection? is it implemented?"

What Cairn had:

1. **Pages form a tree** through `parent_id`, and every page write extracts the page's links, mentions, parent and tags into edges, which backlinks and neighbours read (ADR-005).
2. **Collections were flat**, outside the tree, with no parent.
3. **A `relation` field held one page id**, unchecked, and produced no edge. So a row could not link to another row, in its own collection or another, and a page never learned that a row pointed at it. Stacks listed their components as the names of peptides, not links to the Peptides rows.

The owner chose three options, each the recommended one:

1. **Collections nest under a page,** as a page nests under a page. Rejected: collections inside collections, which mixes two kinds of child in one table; and links only, which leaves the tree and the agent's overview flat.
2. **In their wiki, only the two collections move,** under a new "Peptides" page; the category pages stay where they are.
3. **Rows link to rows now,** with backlinks, not later.

## Decision

1. **A collection has a `parentId`,** a page id or null. Moving one changes that field and nothing else: no row is copied or rewritten. A parent must be a page. A collection whose parent page is deleted shows at the top, as a page's child does.
2. **A relation field names its target:** `target: "pages"`, the default and the old behaviour, or a collection id, its own included. `multiple: true` holds a list of ids. Values are checked to be ids; whether the record exists is not, so a link can be written before its target, as page links can. A target collection must exist when the schema is saved, which fixes an order for creating collections that point at each other.
3. **Every relation value is an edge,** type `relation`, labelled with the field's name, from the row to the page or row it names. A row's id in the link graph is `collection-id/row-id`, the same form revisions use; page and collection ids never contain a slash. Edges are derived data (ADR-005): written after the row, replaced whole on each write, removed on delete, rebuilt by reindex, and re-derived for every row of a collection when its relation fields change.
4. **Pages can link to rows and collections** in text: `[[collection-id/row-id]]` and `[[collection-id]]`, as well as `[[page-id]]`.
5. **Backlinks and neighbours cover rows.** A link end is described as `page_id`, `collection_id`, or `collection_id` with `row_id`. REST adds `GET /collections/:cid/rows/:rid/links` and `GET /collections/:cid/backlinks`; MCP's `get_backlinks` and `get_neighbours` take a row or a collection as well as a page.
6. **One `move` operation** for pages and collections, in `api/src/operations.ts` (ADR-013 rule 14): REST `POST /api/v1/move`, the MCP tool `move`, `cairn move`, and a Move form on the console's collection page. It refuses a parent that is not a page, and a page moved inside itself.
7. **The console shows collections in the tree** under their page, and in the page itself below its text, each with its row count and fields; a "Put a collection here" form on every page promotes it to root of a collection. The Collections page groups collections under their root page. Tables and rails name linked rows, and each row shows its links and what links to it. (Amended the same day at the owner's request: the first version listed a page's collections in its side rail, next to the same links in its text, which read as a loop.)
8. **Rows written before this** have no edges. On start, Cairn looks at the first row with a relation value; if it has no edge, it derives links for every row, once. `pnpm reindex` also rebuilds them.
9. **Export, import and sync carry `parent_id`,** and create collections after the collections their relations point at. Sync now writes pages before collections, so a parent exists before a collection moves under it (amending ADR-023 decision 5).

## Consequences

1. Grouping is cheap: a new page, and one move per collection.
2. Links between rows are real links, so an agent can walk from a stack to its peptides and back with `get_neighbours`, and a page shows which rows point at it.
3. MCP costs about 3,000 tokens a session, up from about 2,725, for the `move` tool and the relation settings in `create_collection`'s schema (`pnpm context-cost`).
4. A row that links to many things costs one edge each; at personal scale that is nothing, and the edges table already holds page links the same way.
5. Not done: a collection under another collection, a relation's target checked for existence on every write, and two-way relation fields that edit both ends. Backlinks give the reverse direction without storing it twice.
