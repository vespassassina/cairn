# ADR-054: A sign-in survives a lost race and a slow start

Status: accepted, amends ADR-033
Date: 2026-09-16

## Context

The review of 2026-09-16 found the owner's stored Azure sign-in gone. The credentials file had no entry for the server at all, so the next command reported `unauthorized` and the only way forward was to sign in again by hand. Nothing had been revoked and the refresh token had 28 days left.

Two defects together destroy a sign-in, and each is harmless alone.

The first is on the server, in the refresh branch of `packages/api/src/oauth/server.ts`. The code reads:

```
const grant = await store.takeAuth<RefreshGrant>("refresh", hash);
...
const tokens = await this.issueTokens(rest, family);
// The replay record is written first, ...
await store.putAuth("refresh_replay", hash, { family, tokens }, ...);
```

`takeAuth` deletes the grant and returns it, which is what makes exactly one concurrent request the winner. But the replay record is not written until after `issueTokens` has run, and `issueTokens` itself writes the new refresh grant to the store. Between the delete and the replay write there is a window in which a second request presenting the same token finds no grant, no replay record and no used record, and is answered `invalid_grant`. The comment above the write says the replay record is written first. It is written first relative to the used record, which is what ADR-033 decision 4 asked for, and it is not written first relative to the answer it is meant to protect. The window is short on a warm server and long on a cold one, where the store write goes through Litestream on a container that started seconds ago.

This window is reached constantly in normal use, because an agent runs several `cairn` commands at once and each is a separate process with its own copy of the credentials file. Two of them noticing an expiring access token in the same second is the ordinary case, not the rare one.

The second defect is in the client, in `storedToken` in `packages/cli/src/login.ts`. It refreshes when the access token is within 60 seconds of expiry, and the whole refresh is wrapped in a `try` whose `catch` deletes the server's entry from the credentials file and writes the file back. Any failure at all lands there: a connection reset, a DNS hiccup, a 500, and above all a timeout against an Azure container that sleeps after 30 minutes and takes about 25 seconds to answer the first call. The comment says the refresh token expired or was revoked. The code cannot tell that apart from the network being slow.

The two compound in the worst way. The losing process of a race gets `invalid_grant` for a token that is perfectly good, and then deletes the credentials that the winning process has just refreshed and written. One process succeeds, the other erases its work, and the sign-in is gone.

ADR-033 decision 5 says access tokens stay at one hour, because a longer access token is the one change that genuinely weakens the system. Lengthening them would paper over this without fixing it, and is rejected here for the reason ADR-033 already gave.

An alternative server fix was considered: write a marker before `takeAuth` so a second request can recognise itself as the loser of a race rather than a stranger. It was rejected because it lets an unauthenticated caller cause a store write for any string they present.

## Decision

1. **A refresh that finds nothing waits for the answer another request may be writing.** When the grant is absent, the replay record is absent and there is no used record, the server polls for the replay record for up to one second before concluding the token is unknown. If the record appears, the request gets the same tokens as the winner, which is what ADR-033 promised. This replaces the assumption that a missing replay record means a missing token.

2. **The wait applies only to that one case.** A revoked family, a used record, a client mismatch and an expired token are all still refused immediately. The wait costs a caller presenting an unknown token up to one second, which is an acceptable brake on guessing and is bounded so it cannot be used to hold connections open.

3. **ADR-033 decision 4 is restated as an outcome rather than an ordering.** The rule is that a repeat arriving while the first request is still in flight is answered rather than treated as theft. Writing the replay record before the used record is not sufficient to achieve that, and the code must be checked against the outcome, not the ordering.

4. **The CLI forgets a sign-in only when the server says the grant is invalid.** Credentials are deleted on an OAuth error of `invalid_grant` from a response the CLI actually received and parsed. A timeout, a connection failure, a 5xx, a proxy page, or any response the CLI cannot parse leaves the credentials untouched and produces an error that says the server could not be reached, that the sign-in was kept, and what to run next.

5. **A process never overwrites credentials it has not just read.** Before writing the credentials file, the CLI re-reads it and merges its own server entry into whatever is there now. A slow process finishing after a fast one can no longer erase the fast one's fresh tokens.

6. **The refresh request gets a timeout that fits a cold start, and one retry.** Thirty seconds, because the Azure container takes about 25 to answer its first call, with a single retry on a connection level failure. The timeout is stated in the error when it is hit.

7. **Access tokens stay at one hour.** ADR-033 decision 5 stands unchanged. The cold start is handled by decision 6, not by weakening the token.

## Consequences

1. Two `cairn` commands started at the same moment both succeed, which is the case an agent creates every time it works in parallel. This is the defect's real cost and the reason it is treated as more than a race condition.

2. A Cairn that is asleep, unreachable or briefly broken no longer costs the person their sign-in. The worst case becomes a failed command with a clear message, which is what a failed command should cost.

3. The server does one extra read in the path that is about to fail anyway, and up to one second of waiting in that path. Nothing is added to the successful path.

4. Harder: the one second wait is a constant chosen to be comfortably larger than the window it covers on a cold container, and it is a guess. If a cold Litestream write is ever slower than that, the defect returns in a narrower form. The test that covers this drives both requests through a store whose write is artificially delayed, so the bound is exercised rather than assumed.

5. Still open: the credentials file is read and written without a lock, and decision 5 narrows the damage rather than removing it. Two processes writing entries for different servers in the same instant can still lose one of them. A lock file is the next step if it is ever observed.
