# ADR-026: A collection is a top-level page and its tree; typed tables are tables

Status: accepted. Step 1 (the web app) done; step 2 (API, MCP, CLI and export) to follow.
Date: 2026-09-13
Amends: ADR-024 (which called typed tables collections), ADR-009 (the console's entry point)
Relates to: ADR-013, ADR-016, ADR-023

## Context

After ADR-024, the owner asked what the Pages page meant: "why not just have collections and start the browsing from there? for a human that's the first entry point. home should just show available collections. a collection is kind of a database, tree shaped not table shaped." Then: "i open cairn web app, i see what collections are available each is a wiki. i navigate there".

Cairn had used "collection" for a typed table of rows since the PRD. The owner means something else: a wiki, tree shaped, that a person opens and browses. That also explains their first request, to put the peptide wiki's two tables "under peptides collection": the whole peptide wiki is one collection.

The owner decided:

1. **A collection is a top-level page and everything under it.** Its text is the wiki's front page; its pages and tables are inside. Rejected: a new kind of container record, which would add an entity to the model, the API, sync and export for what a root page already is.
2. **Rows sharing one set of fields are called tables,** everywhere: the web app, the CLI, the MCP tools and the API, so people and agents use the same words. The owner asked whether a table is a tree too, and whether "trunk" or "branch" would suit; a table is a node whose children share fields, but "branch" already describes any page with children, so the name says what sets it apart.
3. **The sidebar shows a table as one node;** opening it shows the rows.
4. **The peptide wiki becomes one collection, Peptides,** holding the category pages, the Stacks pages and both tables.

## Decision

1. **No new record.** A collection is any page with no parent, or whose parent is gone. Making a page a collection, or merging one into another, is the `move` of ADR-024.
2. **The web app opens on the collections:** a card per collection with its front page's first paragraph and how many pages and tables it holds, then any table that sits in no collection. Recent changes move to `/changes`, and Tables (`/t`) lists every table grouped by the page it sits under. "Pages" leaves the menu; `/pages` and the old `/c` addresses redirect.
3. **Inside a collection, the sidebar shows only that collection's tree,** headed by its front page, with tables as leaves marked "table".
4. **The word "collection" for a table leaves every surface.** Step 1 changes the web app. Step 2 changes the REST paths (`/api/v1/tables`), the MCP tools (`list_tables`, `create_table`, `query_table`) and fields (`table_id`), the CLI (`cairn tables`) and the export folder, keeping the old REST paths and CLI command working for a while so nothing already connected breaks. The code's own type names follow; the database keeps its table names, since they are not seen.

## Consequences

1. People and agents see the same shape: collections of pages and tables.
2. Until step 2 lands, agents still read "collection" for a table through MCP and the CLI, while the web app says table. The MCP instructions say so in one line until then.
3. A collection's front page is an ordinary page: agents write it like any other, and search finds it.
4. Renaming MCP tools changes the tool list every connected agent loads; that is a one-time change, and the context cost is measured again.
