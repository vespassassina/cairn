# ADR-042: A negated keyword match does not count

Status: accepted
Date: 2026-09-15
Relates to: ADR-021 (keyword ranking and term coverage), ADR-022 (vector search and hybrid fusion), ADR-025 (heading weighting)

## Context

The eval set carries one known miss, found while it was written on 2026-09-14: q17, "which peptide makes you really hungry", expects `pg_ghrp-6` (an appetite *stimulant*) but both keyword and hybrid search return `pg_semaglutide` (an appetite *suppressant*) instead. The roadmap recorded it as "search does not know direction": eighteen pages in the wiki mention appetite, and nothing in the ranking says which way an effect goes.

Reading both pages and the real similarity numbers narrows this to two separate causes, not one:

**Keyword search returns a page whose only matching word is negated.** Of the eighteen "appetite" pages, only five contain the literal word "hungry" or "hunger", and of those, only `pg_semaglutide` reaches `requiredMatches`' coverage bar for this four-term query. Its one occurrence of "hungry" is `"...more than simply feeling less hungry."` The word is there; its meaning is not. `pg_ghrp-6` never uses the word "hungry" at all, only "hunger" once, in "the intense hunger effect", and is otherwise dense with "appetite stimulation" (used seven times). Keyword search does not read past the word to the phrase around it, so it credits `pg_semaglutide` with a match `pg_ghrp-6` cannot even compete for.

**Vector search's own margin filter excludes the correct chunk by a hair's width.** Probing the real chunk embeddings for this query, `pg_ghrp-6`'s introductory chunk is the single closest chunk in the whole workspace, cosine similarity 0.7246. But the margin filter (ADR-022) requires a chunk to sit `margin` (0.065) above the typical similarity of ranks 10-50 of its own 50 nearest neighbours, and for this query that typical similarity is 0.6600, so the needed bar is 0.7250. `pg_ghrp-6`'s best chunk falls short by 0.0004. Every other chunk in the workspace, including `pg_semaglutide`'s, falls further short. Nothing clears the bar, because eighteen pages sharing "appetite" vocabulary pull the neighbourhood baseline itself up, the margin's whole assumption (a typical neighbour marks the noise floor) does not hold when the neighbourhood is not noise, it is a densely related topic.

These need different answers. The first is a real defect with a small, generic fix: a search backend that reads "less hungry" as a match for "hungry" is wrong regardless of this eval set. The second is a property of a global, previously-tuned constant (`DEFAULT_MARGIN`, ADR-022) that trades recall for precision across every query in every workspace; shrinking it to pass one eval query, by 0.0004, is overfitting to a test rather than fixing a defect, and could not be justified without a broader evaluation this session did not do.

## Decision

1. **A small, generic, English negation lexicon**: "not", "no", "never", "without", "non", "less", "least", "fewer", "lack"/"lacks"/"lacking", "reduce"/"reduces"/"reduced"/"reducing", "decrease"/"decreases"/"decreased"/"decreasing", "suppress"/"suppresses"/"suppressed"/"suppressing", "minus", "rarely", "hardly", "barely". It carries no topic and no domain: it is exactly the kind of word list `search/terms.ts` already keeps for stopwords (ADR-021), scoped to English only for the same reason the embedding model is (ADR-022), and it says nothing about peptides, appetite, or any other subject `search/terms.ts` might one day be used for.
2. **`isNegatedEverywhere(text, term, window = 4)`** (`packages/core/src/search/terms.ts`): true when every occurrence of `term` in `text` has one of these words within four tokens before it. A term that appears once plainly and once negated still counts; only a term that is never once stated plainly does not.
3. **`keywordRanking()`'s term-coverage count (`packages/adapter-sqlite/src/search-index.ts`) now reads chunk text, not just chunk presence.** A page's coverage of a query term only increases from a chunk where `isNegatedEverywhere` is false for that term in that chunk. A page whose only occurrence of a required term is negated no longer reaches `requiredMatches`, and drops out of keyword results entirely, the same way a page that never used the word at all always has.
4. **Vector search and the margin filter are unchanged.** The margin's own shortfall on this query (0.0004, described above) is recorded as a known limitation (roadmap), not patched here: correcting for topic-dense neighbourhoods needs its own before/after evaluation across more than one query, which this ADR's scope does not cover.

## Consequences

1. `pg_semaglutide` no longer wins q17. Keyword and hybrid search both now return nothing for it, instead of a confident, wrong answer. Recall@5 is unchanged at 0.97 (still one miss of 32 scored queries; before and after numbers below), but an honest empty result is the answer this project already prefers to a wrong one (`search/terms.ts`'s own opening comment: "An empty result is the honest answer there"). q17 remains a full miss, tracked as its own roadmap item now that its cause is precisely known: the vector margin, not direction-blindness in the ranking.
2. The fix is general, not q17-specific: any query whose only textual match to a page is inside a negated phrase now fails to match that page, in keyword mode and, through fusion, in hybrid mode. It costs one extra column (`text` instead of just `page_id`) in an already-small per-term lookup query, no new table, no schema change.
3. Word-for-word, not stemmed: `isNegatedEverywhere` checks the literal folded token a query asked for, not every inflection FTS5's Porter stemmer would also match. It is enough for the negation words themselves, and simpler than re-implementing SQLite's stemmer in JavaScript; a page that negates a *stemmed* variant of a term ("reduces hunger" against a query for "hungry") is not caught by this ADR.
4. This does not touch vector ranking, the margin, or fusion (ADR-022 stands as written). A future ADR can address the margin's sensitivity to topic-dense neighbourhoods on its own evidence, evaluated on its own, once there is more than one query to test it against.
