# ADR-067: a guest is an email address, proven against a provider Cairn already trusts

Status: accepted, design only, deferred (PRD P2 item 6, "design for, don't build")

Date: 2026-09-19

Relates to: ADR-017 (the OAuth server, "no passwords, no user database, no roles"), ADR-066 (token-gated publishing), PRD P2 item 6 (permissions beyond workspace membership: per-page sharing, read-only guests)

## Context

ADR-066 answered one kind of sharing: an anonymous bearer token gating an already-published subtree, deliberately identity-less, a share link. The owner now describes a different case: sharing a subtree, published or not, with one specific person, by their email address, where Cairn never manages a password or a user record for them, and eventually the grant carries a role.

ADR-017 already solved the harder half of this problem for the owner's own sign-in: any OpenID Connect provider (Google, Microsoft Entra ID, and by the same mechanism Apple and Facebook, both OIDC-compliant for sign-in), checked by discovery and PKCE, with an allowlist that already includes `email:<address>` "when the provider marks it verified" (ADR-017 decision, point 2 under "what stays as ADR-007 set it"). That allowlist today has exactly one member: the owner. What's missing is letting a second kind of entry exist in it, one scoped to a single subtree and a role, rather than to the whole workspace.

## Decision

1. **A guest grant is a row, not an account.** A new built-in table, `GuestGrants`: `page` (the subtree root, relation → pages), `email` (required, the identity being granted access), `role` (an enum, `reader` is the only value that exists for now, kept as an enum rather than a boolean specifically so a second role is a new enum value later, not a schema change), `note` (optional, who this is and why), `invitedAt`, `revokedAt` (optional, same "set once, kept for the record" shape as ADR-066's token revocation). Same reasoning as ADR-064 and ADR-066: a structured record belongs in a row, not a new store.

2. **No new sign-in mechanism. The guest authenticates through the exact same OAuth flow ADR-017 already built.** A guest visiting a shared subtree's address picks a provider (whichever ones are configured: Google, Microsoft, Apple, Facebook, all OpenID Connect), signs in there, and Cairn receives the same verified-email claim it already checks for the owner. The only new logic is what the claim is checked against: instead of (or in addition to) the workspace's owner allowlist, it's checked against `GuestGrants` for a page. A match with an unrevoked `reader` grant issues the guest a token scoped to read that subtree and nothing else; no match is refused the same way an un-allowlisted sign-in is refused today.

3. **This is the first role Cairn has.** ADR-017 was explicit: no roles, one owner, full access. This amends that only for guests: a guest's token carries `role: reader` and every route it can reach checks for it, refusing any write, any page outside the granted subtree, and every console feature that isn't reading a page (no search across the workspace, no tables, no history, matching the same narrowness ADR-032 gave the fully public `/w` surface, but here scoped per-guest instead of globally). The owner's own sign-in stays role-less exactly as ADR-017 left it.

4. **A guest grant works whether or not the subtree is published.** This is the difference from ADR-066: a token gates a subtree that's already on the open publish surface; a guest grant is how a subtree that is *not* published gets shown to exactly one person. The two are independent and can both apply to the same subtree, a published-with-a-token wiki and a private one shared with one named guest are both "this ADR plus ADR-066," not competing designs.

5. **Issuing, listing and revoking a grant is the owner's action, never an agent's**, same line ADR-032 and ADR-066 both drew: console and CLI, not MCP.

## Consequences

1. Nothing about ADR-017's core promise changes for the owner: no password, no user database, still one allowlisted owner identity. This only adds a second, narrower allowlist, per subtree, checked the same way.
2. A guest never has a Cairn account to manage, reset, or delete. Revoking the row is the entire off-boarding step, and it's immediate.
3. The email address is the whole trust boundary: whoever can currently prove that email to Google, Microsoft, Apple or Facebook has the grant, which is exactly what "share with an email address" means and exactly the risk that phrase already implies (the same risk "send the document to this address" always carries) — no new risk is introduced beyond what those providers already vouch for.
4. `reader` is the only role for now, deliberately: a role field this ADR does not use yet is cheaper to design with today than to retrofit once grants exist without one, but building a second role (comment, suggest, write) is real future work, not implied by this ADR.
5. This is a design decision, not a build order: the owner deferred implementation ("let's look at this later"). It exists so the shape is settled and doesn't drift before it's picked up, and so ADR-066 and this ADR are known to compose rather than compete when the time comes.
