# ADR-022: Vector search in SQLite with sqlite-vec, and a small English model inside the container

Status: accepted
Date: 2026-09-13
Supersedes: ADR-003 as the default (a bring-your-own endpoint remains possible later, behind the same port). Amends: ADR-004 rule on changing models.
Relates to: ADR-005, ADR-020, ADR-021, PRD section 7

## Context

After ADR-021, keyword search returns nothing when nothing matches, but it cannot bridge different words for the same thing. "Something to help me fall asleep" found nothing, because the DSIP page says "sleep"; "anything for wrinkles" missed Matrixyl for the same reason.

ADR-003 planned embeddings as opt-in, through an OpenAI-compatible endpoint the owner brings. The owner asked instead for vector search in SQLite through its extension, and embeddings computed inside the container with a small model. ADR-020 allows one container and nothing beside it, so the model has to run in the server's own process.

The owner chose bge-small-en-v1.5 over a multilingual model, trading Italian and Dutch for size, and asked that the documentation say plainly that semantic search works only for English.

## Decision

1. **Vectors live in SQLite, through sqlite-vec** (0.1.9), a loadable extension Node's built-in SQLite accepts with `allowExtension`. Loading is switched off again straight after. The tables are created only when embeddings are on (ADR-004): `chunk_vectors` (a `vec0` table, cosine distance, partitioned by workspace) and `vector_chunks`, which records which chunk and which text each vector belongs to.
2. **The model is bge-small-en-v1.5**, ONNX, quantized to 8 bits: 34 MB, 384 dimensions, MIT licence, **English only**. It runs in the server process through transformers.js and ONNX Runtime, behind a new `Embedder` port in core and the `adapter-embeddings-local` package. Text in other languages keeps keyword search, which is not affected.
3. **Embedding never blocks a write.** A write updates the keyword index at once; the chunk's vector follows in the background. Stale vectors are dropped in the same transaction as the write. When the model loads, every chunk is compared with the stored vectors by a hash of its text, so writes made while it was off or loading are caught up, and unchanged chunks are never embedded twice.
4. **Hybrid search** merges the keyword ranking (ADR-021's rules) with the 50 nearest vectors by reciprocal rank fusion (k = 60), then applies ADR-021's one-chunk-per-page ordering.
5. **A vector match counts only when it stands out from its neighbours:** its similarity must be at least 0.065 above the average of the 10th to 50th nearest chunks. A fixed similarity cannot separate a conversational question with an answer (0.657 to the DSIP page) from a question near the wiki's topic with none (0.654 for "insulin pump battery replacement"); the margin can, on the queries measured. A workspace with fewer than 20 chunks has no neighbourhood, and uses a fixed similarity of 0.70 instead. Both are configurable.
6. **One text per model call, one thread.** Memory grows with the batch, because every text is padded to the longest: embedding the wiki's 1,098 chunks peaked at 1.3 GB thirty-two at a time, 690 MB four at a time and 312 MB one at a time, which was also fastest. The bundled server with the model loaded and every chunk embedded holds 347 MB, inside Azure's 0.5 GiB.
7. **On by default,** `CAIRN_EMBEDDINGS=off` to turn it off. Local installs download the model once, to `~/.cache/cairn/models`. The container image ships it and never downloads (`CAIRN_MODEL_DOWNLOAD=false`). Tests and short-lived commands (import, reindex) run without the model; the server embeds what they wrote when it next starts.
8. **Everything degrades to keyword search.** If the extension or the model cannot load, or the model fails on a query, search runs in keyword mode and says so in `mode`; `/health` reports `semantic_search` with the reason (PRD principle 3, hard rule 5).
9. **Changing the model drops the old vectors and embeds everything again,** rather than ADR-004's build-a-new-container-then-swap. For one person's wiki this takes seconds to minutes, and hybrid search covers the chunks done so far meanwhile.

## Consequences

1. Measured on the 96-page peptide wiki, SQLite FTS5 plus sqlite-vec, eval of 18 queries with an answer and 9 without: keyword recall@5 0.83, hybrid 1.00; no-answer queries returning nothing, 9 of 9 in both modes. The difference is the four conversational questions (h01 to h04), three of which keyword search cannot answer.
2. The margin was chosen while looking at the same queries it is evaluated on, all written by the agent that built it. The numbers show what hybrid search adds; they do not prove the margin generalises. The owner's own queries, and real use, will.
3. Semantic search is English only. Italian or Dutch notes would need a multilingual model (multilingual-e5-small was the alternative: 118 MB, and likely more than 0.5 GiB on Azure).
4. The image grows by about 110 MB: 76 MB of packages for one platform and the 34 MB model. ONNX Runtime binaries for other platforms and the unused web runtime are removed in the build.
5. Memory: 347 MB measured on macOS with the 96-page wiki embedded. The first CI run on Linux measured 142.7 MiB for the container with the model loaded and one page embedded (`docker stats`, 2026-09-13); the peak during a large backfill on Linux is not measured yet. If a container runs out of memory, `CAIRN_EMBEDDINGS=off` or a larger size fixes it.
6. The server bundle cannot include sqlite-vec or transformers.js, which load native code from their own folders. The build writes a `package.json` pinning their exact versions, and the image installs them with npm.
7. The stock `sqlite3` command-line tool cannot touch `chunk_vectors` without the extension loaded. Backups at the file level, such as Litestream and `.backup`, are unaffected.
8. On Azure's 0.25 vCPU, embedding a large wiki after a first deploy or a model change takes minutes rather than seconds. Keyword search serves meanwhile.
