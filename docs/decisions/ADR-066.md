# ADR-066: a published subtree can be gated by a named token

Status: accepted

Date: 2026-09-19

Amends: ADR-032 (a collection can be published, read-only and without sign-in)

Relates to: ADR-017 (auth), ADR-034 (a Cairn describes itself), PRD P2 item 6 (per-page sharing, design for, don't build)

## Context

ADR-032 gave Cairn one publishing mode: a page marked `public`, and everything under it, served at `/w` to anyone, no sign-in, indexed by search engines. That is right for a wiki meant to be a free knowledge source, the peptide wiki being the example. It is wrong for a subtree the owner wants to hand to one or two specific people, a draft, a client's project notes, a family document, without either standing up a full account for them (ADR-017's sign-in, workspace membership) or putting it on the open internet.

The owner asked for the middle case directly: publish a subtree behind a token. No token issued for that subtree, no auth, exactly today's ADR-032 behaviour. A token issued, that subtree needs it. Multiple tokens can exist for the same subtree, each named and described, so the owner can tell "the token I gave my accountant" from "the token I gave my brother" and revoke one without touching the other.

This is a narrower thing than PRD P2 item 6's "per-page sharing, read-only guests", which implies named people, workspace membership, and per-page grants across the whole console. What's being asked for here sits entirely on the publish surface ADR-032 already built: no new sign-in system, no guest accounts, just a bearer credential that gates `/w` reads the same way `public` already does. It's a share link, not a permission system.

## Decision

1. **A token is a row in a built-in table, `PublishTokens`.** Same reasoning as ADR-064 decision 1: this is a structured record, not a new store. Fields:

   | Field | Type | Meaning |
   |---|---|---|
   | `id` | string | The row id |
   | `page` | relation → pages | The subtree root it gates. Must be a published (`public`) page or become one; a token on an unpublished page has nothing to guard yet |
   | `name` | string | Required. What the owner calls it, "accountant", "beta readers" |
   | `description` | string, optional | Why it exists, who holds it |
   | `tokenHash` | string | SHA-256 of the actual token. The token itself is never stored |
   | `createdAt` | timestamp | |
   | `revokedAt` | timestamp, optional | Set once, never cleared. A revoked token is not deleted, so the name and description stay legible in a list of "tokens I've ever issued" |

2. **The token value is shown once, at creation, and never again.** Issuing a token generates 32 random bytes, base64url-encoded, returns it once in the creation response, and stores only its hash, the same pattern a GitHub personal access token or an API key uses. Losing it means issuing a new one and revoking the old; Cairn cannot recover a lost token because it never kept it.

3. **A subtree with zero unrevoked tokens behaves exactly as ADR-032 describes: no auth.** This is the "no token = no auth" the owner asked for, and it is not a special case to implement, it is simply what happens when the `PublishTokens` lookup for a page's published root comes back empty. Existing published wikis are unaffected until the owner issues a token against them.

4. **A subtree with one or more unrevoked tokens requires one to read it.** `GET /w/<page-id>` and everything under it check, alongside the existing `public` walk up the ancestor chain (ADR-032 decision 1), whether any ancestor up to the published root has an unrevoked token. If so, the request must carry a valid, unrevoked token for the page's published root, as `?token=<value>` (so a plain link works for a person clicking it, matching the share-link use case) or `Authorization: Bearer <value>` (for a script or another Cairn fetching it programmatically). A missing or wrong token answers 404, the same non-committal answer ADR-032 decision 3 already gives an unpublished page, so a guess at the URL learns nothing about whether a token exists at all. **A token gates the whole subtree it was issued on, not one page**: issuing it on the published root is what "attached to the subtree published" means, matching how `public` itself cascades down from wherever it's set.

5. **Tokens are the owner's action, never an agent's, same as publishing itself.** ADR-032 decision 5 kept MCP out of publish/unpublish entirely. Token issuance and revocation follow the same line: the console has the control, the CLI gets `cairn publish-token create/list/revoke`, REST carries the endpoints, and MCP has none of it. An agent asked to share a subtree with someone tells the person to do it themselves.

6. **Tokens never travel with sync, export or import**, for the same reason `public` doesn't (ADR-032 decision 6): they belong to one server's public surface, not to the content. A laptop copy of a token-gated wiki is unpublished and untokened until told otherwise on that copy specifically.

7. **`/.well-known/cairn.json` (ADR-034) lists only fully open collections.** A collection gated by a token is not something a registry or a crawler should be able to discover and then fail to read; `collections` continues to name what `/w` serves with no token needed, exactly as it does today, and a token-gated subtree simply doesn't appear there. This keeps ADR-034's promise, "nothing here decides how a registry works," from accidentally advertising a gate.

## Consequences

1. No new sign-in system, no new auth pathway on the console, REST, CLI or MCP away from the publish surface: this only ever touches `/w` and the routes ADR-032 already carved an exception into ADR-017 for.
2. A token is a capability, not an identity. Cairn never learns who holds it, only that whoever presented it had it, which is a deliberate, much smaller promise than PRD P2 item 6's "read-only guests" and does not attempt to satisfy that item; that item is still design-for, not built.
3. Revoking a token is immediate and independent of the others on the same subtree: one leaked or no-longer-needed token doesn't force reissuing every other one.
4. A subtree can carry both an open path to it and a gated one if the owner is not careful: a page made `public` with no tokens is open by decision 3; adding a token to a *different* ancestor higher up does not retroactively gate a subtree already reachable a different way. This is the same shape of surprise ADR-032 already flags for sync (decision 5 there): the owner controls this from one place, the console's publish panel, which shows the whole picture per subtree rather than per page.
5. `PublishTokens` rows are ordinary table data for CRUD purposes (list, read by id) but the token value itself is a secret by construction: `tokenHash` is never returned by any read, matching hard rule 18's spirit even though this isn't an environment-sourced secret.
