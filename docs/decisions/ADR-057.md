# ADR-057: A search result names each page once

Status: accepted, amends ADR-021 and ADR-025
Date: 2026-09-16

## Context

A search on the owner's laptop copy for a common topic returned ten hits covering three pages. The same page appeared four times, with four chunks of its own text, before the fourth page was reached. Asked for ten results, Cairn answered with three answers and seven repetitions of them.

The cause is in `diversify` in `packages/adapter-sqlite/src/search-index.ts`:

```ts
function diversify(ranked: HitRecord[]): HitRecord[] {
  const seen = new Set<string>();
  const firsts: HitRecord[] = [];
  const rest: HitRecord[] = [];
  for (const record of ranked) {
    (seen.has(record.page_id) ? rest : firsts).push(record);
    seen.add(record.page_id);
  }
  return [...firsts, ...rest];
}
```

It does exactly what ADR-021 asked of it: one chunk per page first. What it then does is append every other chunk behind them, so on a workspace where few pages match the query, the tail of the list is made of repeats. On the eval set this is invisible, because the eval measures recall@5 and a repeat of a correct page does not lower recall. It is very visible to whoever reads the result, and most of all to an agent, which spends its context on the same page four times and may conclude the four hits are four pieces of evidence.

ADR-021 introduced the one chunk per page rule to stop a single page flooding the top of the list. This ADR finishes that job: a result is a list of pages, and a chunk is how a page explains why it matched.

Two options were considered. Truncating the list once every page has had its first chunk was rejected: it silently returns fewer results than asked for, and a page whose second chunk is genuinely a better match for a second part of the query loses it. Grouping was chosen instead, because it keeps the evidence and removes the repetition.

Hard rule 7 applies: no search change merges without running `pnpm eval` and recording before and after recall@5 per backend. Recall is expected to be unchanged, since no page enters or leaves the top five. That expectation is exactly the kind that has to be measured rather than assumed, and the before and after numbers belong in the changelog entry.

## Decision

1. **A search result is a list of pages, each carrying its matching passages.** A page appears once. Its best passage leads, and further passages from the same page are attached to it rather than occupying their own result slots.

2. **A limit counts pages, not chunks.** Asking for ten results asks for ten pages. If only three pages match, three come back, and the caller is told that is all there was rather than being padded.

3. **At most three passages are attached to a page, best first.** Beyond three, a page is explaining itself at the expense of the other results. The count of passages not shown is reported alongside them.

4. **Ranking is unchanged.** Reciprocal rank fusion of keyword and vector hits, the heading weight of ADR-025 and the title-first rule of ADR-025 all stay as they are. This decision changes how ranked results are shaped for the caller, not which pages win.

5. **The shape is the same on all three surfaces.** MCP, REST and the CLI return pages with passages, per hard rule 14. The MCP tool's token budget is spent on distinct pages first, so truncation removes a page's third passage before it removes a page.

6. **The evaluation reports distinct pages in the top five.** The eval already measures recall@5. It gains one number beside it, the mean count of distinct pages in the first five results, so that a future change which reintroduces repetition is caught by the harness rather than by a person reading a result.

## Consequences

1. An agent asking for ten results gets up to ten different pages to consider, which is what it was asking for, and its context is not spent three times on one page.

2. The result payload changes shape on every surface, which is a breaking change to the REST response and the MCP tool output. Both are pre-1.0 and have one consumer, so it is taken now rather than carried.

3. Harder: a caller that wants raw chunks, such as the rebuild and eval paths, now needs a way to ask for them. The internal index keeps returning chunk hits and the grouping happens above it, so those callers are unaffected.

4. Still open: whether the passage attached to a page should be the best matching chunk or the opening of the page. The best matching chunk is kept, because it answers why this page is here, which is the question a result list is asked. ADR-025 already makes an exact title match win on its own.

5. Hard rule 7 gate: this does not merge until `pnpm eval` has been run before and after, per backend, with both recall@5 and the new distinct page count recorded in `docs/CHANGELOG.md`.

## Relates to

ADR-021 (most of the query's words, one chunk per page first), ADR-025 (headings weigh more, exact title wins), ADR-022 (hybrid search), ADR-013 (the same capability on three surfaces).
