# ADR-076: A quoted phrase in a search query asks FTS5 for NEAR proximity, fixed at distance 10

Status: accepted

Date: 2026-09-24

Relates to: ADR-021 (keyword search rules, stemming, requiredMatches), ADR-025 (heading-weighted ranking), ADR-005 (search is a separate adapter from the document store)

## Context

The owner asked for "FTS5 NEAR" alongside per-collection synonyms, in one request. SQLite FTS5's `NEAR(...)` operator asks that a set of terms appear within some token distance of each other, closer to what a person means by putting words next to each other than plain keyword matching, which is satisfied by the words appearing anywhere at all on the page, in any order, arbitrarily far apart.

Cairn's query language has never had explicit phrase syntax; a query is a bag of words (ADR-021). Adding one is a small language change with two live questions: how a person or agent writes a phrase, and how far apart NEAR still counts as "together".

## Decision

1. A double-quoted span in a query is a phrase: `"appetite suppressant"` asks that those words appear within `NEAR_DISTANCE` tokens of each other, not just somewhere on the same page. `packages/core/src/search/terms.ts`'s `extractPhrases(query)` parses every quoted span into its folded, tokenized words; a one-word phrase is dropped, since a single word carries no proximity meaning and is already an ordinary term.
2. Distance is fixed at 10 tokens, unordered, and not a setting a person or agent chooses per query. The owner's direction on this point was explicit: NEAR/10, unordered, not configurable. A fixed value is one fewer thing an agent has to learn to write a working phrase query, and 10 is FTS5's own conventional default.
3. A phrase changes ranking, never membership. Which pages qualify as a match is decided exactly as before, by `requiredMatches` over the query's individual terms (ADR-021); a phrase's words still count toward that coverage individually. What changes is order: among already-qualifying pages, one whose matching chunk also satisfies the `NEAR` clause for every phrase in the query sorts ahead of one that only has the words scattered apart, ahead of ADR-025's per-word ranking, as a tiebreak. This keeps the change strictly additive: a query with no quotes computes an empty phrase list and behaves identically to before.
4. Implemented adapter-side (`packages/adapter-sqlite/src/search-index.ts`): one extra `NEAR(...)` MATCH query per phrase, over the same content the adapter already indexes, used only to collect which chunk ids satisfy it. No schema change, no new column, no new index. Another `SearchIndex` backend can ignore `extractPhrases`'s result entirely and remain correct, per ADR-005: proximity is a ranking refinement a backend may or may not offer, not part of what a match means.

## Consequences

1. A person or agent who wants "these words together" now has a way to ask for it, without it changing what "matches" means for anyone who does not use quotes.
2. `pnpm eval` before and after this change shows unchanged recall@5, since the eval set's queries carry no quotes and the mechanism is a no-op for them (hard rule 7). A future eval query written with quotes would be the first real signal on whether NEAR ranking actually helps; none is added here, since the eval set is decision-cost, not test-cost, and this change does not claim to move recall.
3. NEAR_DISTANCE is a constant, not a setting, so there is nothing to document for API consumers beyond "phrases use quotes". If a real query later shows 10 is wrong for Cairn's prose, that is a new ADR, not a config flag.
4. FTS5's own `NEAR` syntax has quirks (order-sensitivity by default, which this design turns off by quoting each word separately rather than relying on phrase-adjacency), so `nearQuery()` builds the clause explicitly rather than passing a person's quoted text straight through; see the negation-aware matching precedent in ADR-042 for why untrusted query text is never spliced directly into a MATCH clause.
