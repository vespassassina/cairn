# ADR-049: A backup is a whole database, taken because something changed

Status: accepted
Date: 2026-09-16
Relates to: ADR-018, ADR-020, ADR-046, ADR-048

## Context

Litestream gives Cairn a replica of its database in blob storage, seconds behind. That is the right first rung of the ladder and it is not enough, because of what kind of replication it is.

Litestream is physical replication: it ships SQLite's pages. It has no notion of a record, no timestamps, and no way to merge. The replica is not a second opinion about the data, it is a copy of the same bytes. So whatever happens to those bytes happens to the replica too, with perfect fidelity and within seconds. The outage of 2026-09-15 is the demonstration: one truncated transaction on the writing side became one unrestorable replica, and there was nothing else in blob storage to fall back to. Cairn's own sync (ADR-023, ADR-029) is the opposite kind, record-level and timestamped, but it is between Cairns and not a backup.

What was missing is a second artefact that does not share fate with the first: a complete database as it stood at a known moment, which is still readable when the live one is not.

The obvious mechanism was the CLI's export format, since one already exists. It was investigated and rejected. An export is a logical reconstruction into files and would need `packages/cli/src/export-format.ts` shared between the CLI and the server, and more importantly a logical export has no pages, so Litestream's physical LTX files can never be replayed onto it. It is a different kind of object than the thing being protected.

`VACUUM INTO` is the right kind of object, and was measured rather than assumed. On a 7 MB database with a 4 MB write-ahead log it produced a 7,127,040 byte file in 9 ms. It reads through the B-trees and writes a fresh file with a new page layout, so it is a logical reconstruction that comes out as a physical database. The WAL's contents are folded in and the result has no WAL of its own. And it refuses a corrupt source: scribbling on a page that the vacuum has to read gives "database disk image is malformed" rather than a neat copy of the damage. That refusal is the property that makes it a backup rather than a second victim.

One trap came out of the same measurement: on refusal it leaves the partial destination file behind.

## Decision

1. **A backup is a whole SQLite database, made with `VACUUM INTO`.** Not an export, not a file copy. Self-contained, WAL-inclusive, readable by any SQLite, and refuses to copy a database it cannot read through.
2. **Every backup is verified before it is accepted.** The vacuum writes to `<name>.partial`, that file is opened read-only and put through `PRAGMA integrity_check`, and only then is it renamed into place. A failure at any point deletes the partial. This is what the trap above forces: without it a refused vacuum would leave a half-written file sitting in the archive looking like a backup.
3. **Activity triggers a backup, not a timer.** After a write, if the newest backup is older than `CAIRN_BACKUP_AFTER_HOURS` (default 3), one is taken in the background. The owner's words: "every new write if last backup is older than 3 hours, we backup". A timer never fires in a container scaled to zero, which is the normal state of the Azure Cairn, so a schedule would have backed up a twice-a-day Cairn never. A Cairn nobody used needs no backup, because nothing changed.
4. **At launch Cairn reads the age of the newest backup from the archive.** Otherwise every cold start believes it has never backed up and takes one on its first request, which on a scale-to-zero platform means a backup per idle period rather than one every three hours.
5. **A backup is taken on the way down,** as a shutdown step before the database is closed (ADR-048 decision 2). A stop is the moment at which the last few hours of work would otherwise be exactly what is lost.
6. **A failed backup never fails anything else.** It does not throw into the request that triggered it, it does not stop shutdown, and it does not restart the clock, so the next write is still due rather than waiting three more hours. It logs what failed and where backups go.
7. **Retention is `CAIRN_BACKUP_KEEP_DAYS` (default 2), with a floor of `CAIRN_BACKUP_KEEP_AT_LEAST` (default 3).** Age alone would empty the archive for a Cairn nobody touched for a week, and that week is precisely when nobody would notice.
8. **Taking a snapshot is an optional capability of a store, not part of `DocumentStore`.** `Snapshotter` lives in `packages/core/src/ports/snapshotter.ts` with a `canSnapshot()` check. Hard rule 2 says every adapter passes the same conformance suite, and making this part of the store interface would force every future adapter to answer a question only a file-backed one can.
9. **The write trigger is one HTTP middleware,** in `packages/api/src/app.ts`, counting any non-GET request that did not return 4xx or 5xx. This is the one place MCP, REST and the CLI all pass through, so hard rule 14 is satisfied without three implementations. MCP reads arrive as POST and so count as writes; that over-triggers, and the cost of over-triggering is one 9 ms vacuum at most every three hours.
10. **Backups are separate from the Litestream replica,** a different container and a different prefix, so that nothing about restoring one can overwrite the other.

## Consequences

1. There is now a second, independently verified copy of the database that does not share fate with the replica. The middle and lower rungs of the recovery ladder have something to land on.
2. The archive is an interface, `Archive`, with `FolderArchive` as the first implementation. An Azure blob implementation is the next commit and needs no change to the engine.
3. **Until that exists, backups on Azure are written to the container's own disk and are lost when it stops.** This is worse than useless if it is believed, so Cairn now prints a warning at startup when `CAIRN_REPLICA_URL` is set and backups are going to a local path, saying the disk does not outlive the container and naming the two ways out.
4. Backup names are ISO 8601 with colons replaced, `cairn-2026-09-16T14-07-29Z.sqlite`, so string order is chronological order and no index file is needed to know what is newest.
5. The backup is a file the owner can read with any `sqlite3`. Nothing about recovering from it depends on Cairn running, or on this project existing.
6. Restoring from a backup loses up to three hours, where a Litestream restore loses seconds. That is why it is the third rung and not the first.
