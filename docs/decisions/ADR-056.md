# ADR-056: The console is readable on a phone

Status: accepted, extends ADR-009
Date: 2026-09-16

## Context

The review of 2026-09-16 opened the console at 375 by 812, the size of a phone held upright, and found a page tree taking the left column, a body of roughly 120 pixels beside it, and a search field forcing the whole page to scroll sideways.

The cause is one line. `packages/api/src/web/assets.ts` defines the page layout as a three column grid, 220 pixels of tree, the body, and a 240 pixel rail, with a single media query:

```css
@media (max-width: 1100px){ .cairn-page{ grid-template-columns:200px minmax(0,1fr) } .cairn-rail{ grid-column:2 } }
```

That is the only layout breakpoint in Cairn's own CSS. Below 1100 pixels the rail moves under the body and the tree keeps a fixed 200 pixel column all the way down to zero. At 375 pixels the tree therefore holds more than half the screen. Separately, `.cairn-top .ak-input` has `min-width:260px`, which together with the brand and the navigation is wider than the viewport, so the page scrolls horizontally.

The viewport meta tag is already present, and the tree is already built from native `details` elements, so the pieces needed to fix this are in place.

ADR-009 scoped the console deliberately: server rendered, artifactkit for styling, no rich editor, no table views beyond a plain table, no client side application. Nothing in that forbids working on a small screen, and a phone is where a wiki is most often read rather than written. The question this ADR settles is whether making the console usable on a phone counts as growing the console beyond the scope ADR-009 set. It does not, provided it is done with CSS and elements the browser already implements, and it is worth stating so the next reader does not have to relitigate it.

A separate mobile layout, a hamburger menu driven by script, or a client side drawer were all rejected. Each would be a client side application, which ADR-009 rules out, and none is necessary.

## Decision

1. **A single column breakpoint is added below 700 pixels.** The tree, the body and the rail stack in that order, each at full width. 700 is chosen because it is where the two column layout's body column becomes too narrow to read a paragraph in, not because it matches a particular device.

2. **The tree becomes a collapsed `details` element on a narrow screen, closed by default.** Its summary says how to read it, for example "Pages in this collection". The body of the page is what someone opened the page for, so it comes first and the tree is one tap away. This uses the same native element the tree already uses for its branches, so it needs no script.

3. **Nothing scrolls sideways at 320 pixels.** The header wraps, the search field drops its 260 pixel minimum below the breakpoint and takes the full width of its row, and long page titles and code blocks wrap or scroll within their own box rather than widening the page.

4. **The sticky positioning on the tree and the rail is switched off in the single column layout.** A sticky element that is as tall as the screen is a trap on a phone.

5. **Tap targets in the tree and the navigation are at least 44 pixels high below the breakpoint.** The tree's links are currently 2 pixels of padding around 13 pixel text, which is fine with a mouse and not with a thumb.

6. **This stays inside ADR-009's limits and does not reopen them.** CSS and native elements only. No script, no separate mobile template, no second route. If a future need cannot be met that way, it needs its own ADR rather than an exception here.

7. **Every console change is checked at 375 pixels as well as at a desktop width, with a screenshot.** The defect survived because the console was only ever looked at wide. The check is part of finishing a console change, not a separate task.

## Consequences

1. The console becomes usable for reading and light editing away from a desk, which is most of the reading a personal wiki gets.

2. Cairn's own CSS gains a second breakpoint. Two is still few enough to hold in the head, and the rule stays that Cairn adds layout only where artifactkit has no component for it.

3. Harder: there are now two layouts to check for every console screen, and the collections, recent, tables, freshness, search and page views each need looking at. The screenshot check in decision 7 is what keeps that honest.

4. Still open: tables on a phone. A wide table will scroll within its own box, which is correct but not pleasant. ADR-009 forbids table views beyond a plain table, so nothing more is done here, and if it becomes the thing that stops the console being useful on a phone it needs its own decision.

## Relates to

ADR-009 (the review console and its scope), ADR-026 (collections as top-level pages, which is what the tree shows), ADR-032 (a published collection, which is read by people who did not build it and are often on a phone).
