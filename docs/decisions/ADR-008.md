# ADR-008: Every write is a revision, and agents write directly

Status: accepted
Date: 2026-09-12

## Context

Claude is the primary client and writes to pages and rows without a human in the loop. Two ways to make that safe were on the table.

1. Agent writes land as proposals that the owner approves.
2. Agent writes apply at once, every write is kept, and any of them can be reverted.

Proposals are safer per write but put the owner on the critical path of every agent action. That works against the kill criterion in PRD section 10, which asks whether Cairn gets used four days a week. History with one-click revert gives most of the safety with none of the waiting.

## Decision

### 1. Agents write directly

No approval step. The review screen (ADR-009) makes every agent write visible, and history makes every one reversible. Approval can come back later as a per-collection setting if a real need appears.

### 2. Every write of a page or row creates an immutable revision

A revision is a full snapshot, not a diff. At personal scale (5,000 pages, a few KB each) snapshots cost little, keep reads to one document, and make restore trivial. Diffs are computed when someone looks at them.

A revision holds:

1. The record it belongs to, and its kind (`page` or `row`).
2. Its own version token, which is the version the record has after this write.
3. The version it replaced, or null for the first one. This links revisions into a chain.
4. The actor: who made the change (see rule 4).
5. An optional change note. MCP write tools accept one so an agent can say why.
6. The snapshot, and a deleted flag for the revision that records a deletion.

### 3. Revision first, then the record

This extends ADR-005 rule 3. No transaction spans the two, so the order decides what a crash leaves behind.

1. Write the revision. It is immutable and keyed by the new version, so writing it cannot conflict with anything.
2. Write the record with a check on the expected version, setting its version to the new revision's.
3. Write derived data, as before.

If step 2 fails on a version conflict, the service deletes the revision it just wrote. If the process dies between steps 1 and 2, the revision is left behind with nothing pointing to it. That is harmless: history is read by walking the chain back from the record's current version, so a revision off the chain is never shown. The rebuild command sweeps them.

The other order, record first, loses history on a crash. Silently losing history is worse than keeping a stray snapshot.

### 4. Every write names its actor

An actor is a kind (`user` or `agent`) plus an id and a display label.

1. Web edits are `user:owner` until auth lands.
2. MCP writes are `agent`. In stateless mode the client's name is only sent at initialize, never on a tool call, so the label comes from the request's user agent for now. Under ADR-007 it becomes the OAuth client registration, which is the right identity anyway.

The current record also carries the actor and time of its last write, so a page view does not need to read history to say who changed it last.

### 5. The service chooses version tokens

Adapters no longer invent version tokens. The service generates the next version and passes it in, so the record and its revision share it. Each adapter still enforces the check atomically in its own way: a conditional update in SQLite, a condition expression in DynamoDB, an ETag-guarded replace in Cosmos.

## Consequences

1. The document store port gains revision methods, and the conformance suite gains revision tests. Every adapter implements them.
2. MCP gains `get_history` and `get_revision`, and write tools gain `change_note`.
3. Restoring a revision is an ordinary update whose content comes from the old snapshot. It creates a new revision, so a restore can itself be undone.
4. Deleting a page records a deleted revision and keeps the history. Undeleting is not in v1.
5. Collection schemas are not versioned yet. Rows are. Schema history can follow the same pattern when a schema change first hurts.
6. Storage grows with every write. At personal scale that is fine for a long time. A retention setting can come later without changing the model.
