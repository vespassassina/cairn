# ADR-061: the Azure losses were Litestream issue #1515, a confirmed upstream bug with no fix released

Status: accepted

Date: 2026-09-18

## Context

ADR-059 recorded eleven pages lost from Azure on 2026-09-17, cause "not confirmed," Litestream generation inconsistency named as "the leading suspect." ADR-060 then found and fixed a real bug in `cairn sync` that would have turned an unproven absence into a real deletion, and recovered the same pages a second time. Hours later, after this session's redeploy, the same thirteen pages were gone from Azure again. This time `cairn sync`'s own state file showed `last_sync` unchanged since before the redeploy: sync had not run once in between. ADR-060 could not have caused this occurrence. Something else was still open.

Litestream (ADR-018, ADR-020) is Cairn's only durability path on Azure: the container has no mounted volume, so every start restores the database from whatever the replica in Azure Blob Storage last has. A restore that passes its integrity check (ADR-051) only proves the file is internally consistent, never that it is current. If the replica itself had stopped advancing, every restart since would silently and repeatedly revert to the same stale point, discarding everything written after it, no matter what caused the container to restart.

Litestream writes compacted files at several levels, each on its own timer: level 1 every 30 seconds, level 2 every 5 minutes, level 3 every hour, level 9 once a day, on top of raw level-0 segments pruned after 5 minutes. A healthy, running server therefore leaves a trail of level-1 and level-2 files as long as anything is being written.

Listing the replica's blob container directly (`az storage blob list --account-name cairnikh4laa53gam --container-name cairn --prefix cairn.sqlite/ltx/`) end to end, not a truncated sample, found:

- Level 1: 34 files, the newest at `2026-09-15T20:39:18Z`.
- Level 2: 34 files, the newest at `2026-09-15T20:40:00Z`.
- Level 3: one file, `2026-09-14T10:05:52Z`.
- Level 0 and level 9: one file each, both from `2026-09-18T08:18-08:19Z`, this session's redeploy.

Nothing exists at level 1 or level 2 between `2026-09-15T20:40:00Z` and `2026-09-18T08:18:36Z`, a gap of about 59.5 hours. The app was demonstrably active for most of that window: the ADR-059 loss, its investigation, and the first recovery all happened inside it, on 2026-09-17. Activity in the local database without matching activity in the replica, sustained for that long, is only consistent with one thing: Litestream's push to Azure Blob Storage was not advancing. It was not that nothing changed; it was that changes stopped reaching the replica.

**It reproduced live, within the hour, in front of the investigation.** After recovering the thirteen pages with `cairn sync` (Azure back to 122 pages, confirmed by `cairn overview`), the container's own log showed `l0 retention enforced ... max_l1_txid=0000000000000080` unchanged across a 17-minute span, `08:23:50` to `08:40:50`, even while level-0 files kept arriving every second from the fresh writes. `0000000000000080` (128) is the exact old high-water mark from before the 2026-09-15 stall, not a number the currently running process ever recomputed. Retention deletes an L0 file once its txid is at or below that number; the recovery's writes (txids 65-78) were all below it, so retention deleted them, unread by L1, about seven minutes after they landed, while the container was still up and serving them correctly from its live local disk the whole time. The loss only became visible once something restarted the container roughly forty-five minutes later (most likely the 30-minute idle timeout, `CAIRN_IDLE_MINUTES`), which restored from the replica and came back with the thirteen pages gone again, exactly as ADR-060's `cairn sync --dry-run` then showed: fourteen pages Azure had no history for at all, correctly turned into recreates instead of deletes by the fix that ADR just shipped. A second `cairn sync` recovered them again.

**This matches a confirmed, open upstream bug: Litestream issue #1515.** Litestream's own gap-bridging logic (`fillFollowGap` in `replica.go`) only consults compaction levels 1 through 8 when trying to bridge a hole in the transaction log; it never consults level 9, the daily snapshot level. When it cannot bridge a gap, it silently returns the unchanged position with no error, and the caller logs nothing: the process looks healthy, `sync-interval=1s` keeps firing, and nothing in Cairn's own logs or Litestream's own logs says replication has stopped advancing. A restart does not clear the stall; it resumes at the same stuck position and hits it again. The issue explicitly lists **0.5.14, 0.5.16, and 0.5.17** as affected, unchanged since 0.5.14; Cairn runs 0.5.17. No fix is released. Two competing fixes are open and unmerged: [PR #1516](https://github.com/benbjohnson/litestream/pull/1516) (a visibility-only change, surfacing the stall as a log line without changing the gap-bridging behaviour) and [PR #1514](https://github.com/benbjohnson/litestream/pull/1514) (a more complete fix, `fillFollowGapFromSnapshot`, letting the follower consult L9 snapshots to bridge the gap it currently cannot see past). Both are unreleased as of this ADR.

## Decision

1. **Record the cause as confirmed, not suspected.** Every restart between `2026-09-15T20:40:00Z` and the point this is fixed upstream reverts to whatever point Litestream's follower last actually reached, which can silently stop advancing at any time with no warning. This is Litestream issue #1515, not a Cairn defect, not a sync defect (ADR-060 already closed sync's own separate bug), and not fixed by redeploying, restarting, or recovering the data again: a recovery only holds until the next restart if the stall is still in effect, which nothing in the running system can currently tell you.

2. **ADR-059's "not confirmed" is now confirmed**, for cause and mechanism both. ADR-059 named "Litestream generation inconsistency" as a suspect; the real cause is more specific and is now traced to a named upstream issue.

3. **No code change in this repository fixes this.** The bug is in Litestream itself. Options going forward, in order of how much they change:
   - **Watch #1515/#1516/#1514 for a released fix** and upgrade the pinned Litestream version when one ships. Lowest effort, leaves the exposure open until then.
   - **Build Cairn's image against an unreleased Litestream commit** carrying one of the two fixes (most likely #1514's `fillFollowGapFromSnapshot`, the more complete of the two). Closes the gap now, at the cost of running an unreleased, unmerged upstream build.
   - **Add an application-level watchdog**: periodically compare the replica's actual advancement (readable the way this investigation read it, via the blob container's newest LTX timestamps, or by asking Litestream's own metrics if it exposes the follower's position) against recent writes, and alert if they diverge for more than a few minutes. Does not fix the underlying stall, but turns a silent, weeks-long gap into a same-day page.
   - **Take Cairn's own independent backups (ADR-049/050) more often** than the current 3-hour, write-triggered cooldown, since that path does not go through Litestream's follower logic at all and is unaffected by this bug. Cheapest mitigation, coarsest recovery point.

   None of these is decided by this ADR; they are the owner's call, since each is either an infrastructure change or an ongoing operational cost.

4. **Enabling a Log Analytics workspace for the Container App is still recommended**, independent of which mitigation above is chosen, so a future incident leaves a trail past the current revision's own console log. This needs the owner's go-ahead before it is deployed, per CLAUDE.md section 2.

## Consequences

1. The 2026-09-17 loss, the 2026-09-18 redeploy's repeat loss, and the same day's second repeat loss during this investigation are one root cause, reproduced three times, not three separate incidents.
2. Until one of decision 3's mitigations is in place, **every recovery on Azure is provisional**: it survives only as long as the container doesn't restart before someone confirms the replica actually advanced past it. That confirmation is the same check this ADR performed by hand: fresh level-0/level-1 activity in blob storage, not just that the write succeeded or that `cairn overview` looks right.
3. Without Log Analytics, root-causing exactly when a given stall started, versus just noticing it had, is still not possible after the fact for any incident before one is enabled.

## Relates to

ADR-059 (the original loss, cause superseded by this ADR), ADR-060 (the sync bug this ADR rules out as the cause of the repeat losses, and whose fix is what let the pages be recovered safely a second and third time), ADR-018 and ADR-020 (the Litestream replica architecture this ADR investigates), ADR-051 (the recovery ladder whose integrity check cannot detect a stale-but-consistent replica), ADR-049 and ADR-050 (the independent backup path unaffected by this bug).
