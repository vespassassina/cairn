# ADR-061: the 2026-09-17 and 2026-09-18 Azure losses were a stalled replica, not sync

Status: accepted

Date: 2026-09-18

## Context

ADR-059 recorded eleven pages lost from Azure on 2026-09-17, cause "not confirmed," Litestream generation inconsistency named as "the leading suspect." ADR-060 then found and fixed a real bug in `cairn sync` that would have turned an unproven absence into a real deletion, and recovered the same pages a second time. Hours later, after this session's redeploy, the same thirteen pages were gone from Azure again. This time `cairn sync`'s own state file showed `last_sync` unchanged since before the redeploy: sync had not run once in between. ADR-060 could not have caused this occurrence. Something else was still open.

Litestream (ADR-018, ADR-020) is Cairn's only durability path on Azure: the container has no mounted volume, so every start restores the database from whatever the replica in Azure Blob Storage last has. A restore that passes its integrity check (ADR-051) only proves the file is internally consistent, never that it is current. If the replica itself had stopped advancing, every restart since would silently and repeatedly revert to the same stale point, discarding everything written after it, no matter what caused the container to restart.

Litestream writes compacted files at several levels, each on its own timer: level 1 every 30 seconds, level 2 every 5 minutes, level 3 every hour, level 9 once a day, on top of raw level-0 segments pruned after 5 minutes. A healthy, running server therefore leaves a trail of level-1 and level-2 files as long as anything is being written.

Listing the replica's blob container directly (`az storage blob list --account-name cairnikh4laa53gam --container-name cairn --prefix cairn.sqlite/ltx/`) end to end, not a truncated sample, found:

- Level 1: 34 files, the newest at `2026-09-15T20:39:18Z`.
- Level 2: 34 files, the newest at `2026-09-15T20:40:00Z`.
- Level 3: one file, `2026-09-14T10:05:52Z`.
- Level 0 and level 9: one file each, both from `2026-09-18T08:18-08:19Z`, this session's redeploy.

Nothing exists at level 1 or level 2 between `2026-09-15T20:40:00Z` and `2026-09-18T08:18:36Z`, a gap of about 59.5 hours. The app was demonstrably active for most of that window: the ADR-059 loss, its investigation, and the first recovery all happened inside it, on 2026-09-17. Activity in the local database without matching activity in the replica, sustained for that long, is only consistent with one thing: Litestream's push to Azure Blob Storage was not advancing. It was not that nothing changed; it was that changes stopped reaching the replica.

## Decision

1. **Record the finding as confirmed, with its actual limits.** The replica stopped advancing sometime at or shortly after `2026-09-15T20:40:00Z` and did not resume until this session's redeploy triggered a fresh restore at `2026-09-18T08:18:36Z`. Every restart inside that window reverted to the `2026-09-15T20:40` state, which explains both the 2026-09-17 loss (ADR-059) and the repeat loss of the same pages after this session's redeploy, as one mechanism, not two. It does not explain what made Litestream's replication stall in the first place. No log from the revisions that ran inside the gap survived to check: the Container App has no Log Analytics workspace wired up (`az containerapp env show` returns `logAnalyticsConfiguration: null`), and `az containerapp logs show` only streams the currently active revision's console. That is a real gap in what this ADR can say, not a rounding error, and decision 3 addresses it.

2. **ADR-059's "not confirmed" is now confirmed, for the mechanism, not the trigger.** ADR-059 named "Litestream generation inconsistency" as a suspect; this was close but imprecise; the files found here are compaction levels, not generations, and the failure mode was a stall in the push to blob, not an inconsistent generation. Read ADR-059 decision on cause as superseded by this one.

3. **Enabling a Log Analytics workspace for the Container App is recommended**, so a future incident like this one leaves a trail past the current revision's own lifetime. This is an infrastructure change to Azure resources and is not made by this ADR; it needs the owner's go-ahead before it is deployed, per CLAUDE.md section 2.

4. **No code change follows from this ADR.** ADR-060 already closed the one part of this that code could fix: sync no longer turns an unproven absence into a deletion. What is still open is Litestream's own health, which this project does not have the visibility to diagnose further without decision 3.

## Consequences

1. The 2026-09-17 and 2026-09-18 losses are now understood as the same incident continuing, not two separate ones. Recovering the thirteen pages a third time only holds if the replica is confirmed to be advancing again; a recovery performed while the stall was still in effect would be lost exactly like the first one was.
2. Without Log Analytics, root-causing why the stall started, and confirming when exactly it resumed versus just noticing it had, is not possible after the fact. This ADR states that limit rather than guessing past it.
3. A recovery done after this ADR should be checked against the replica the same way this investigation checked it, before it is trusted: confirm fresh level-1/level-2 activity keeps appearing after the write, not just that the write succeeded.

## Relates to

ADR-059 (the original loss, cause superseded by this ADR), ADR-060 (the sync bug this ADR rules out as the cause of the second loss), ADR-018 and ADR-020 (the Litestream replica architecture this ADR investigates), ADR-051 (the recovery ladder whose integrity check cannot detect a stale-but-consistent replica).
