# ADR-043: AWS and GCP run the same Docker path as Proxmox, not a managed container service

Status: accepted
Date: 2026-09-15
Relates to: ADR-018, ADR-020, PRD section 7, PRD Q7

## Context

The owner asked for AWS, GCP and Proxmox deploy guides. Proxmox was already most of the way covered inside `docs/DEPLOY-DOCKER.md`, as one case of "any Docker host". AWS and GCP had no guide at all: ADR-020 named "whatever AWS service is chosen for containers" as a future target and reopened the AWS free-tier question (PRD Q7) without answering it, and GCP was not discussed anywhere.

ADR-020's own container-path decision already rules out Functions-style and Lambda-style compute for Cairn. What was still open was which shape of container hosting to write a guide for on each cloud:

1. **A managed container service**: ECS Fargate or App Runner on AWS, Cloud Run on GCP. Closest in spirit to Azure Container Apps (ADR-018): scale to zero, no server to patch. But neither gives a container a persistent local disk. ECS Fargate needs an EFS mount for that, which means a VPC, mount targets and a second billed resource; App Runner has no persistent volume at all; Cloud Run is the same as App Runner. Each would need its own Litestream-to-object-storage path, its own IAM setup, and its own troubleshooting section, for a target nobody has asked to run at Azure Container Apps' cold-start-and-idle model in the first place.
2. **A plain virtual machine running Docker**, the same image and the same `deploy/docker/compose.yaml` already written, tested in CI, and documented. The database sits on the VM's own disk, exactly as ADR-020 already decided for "a person's own server". Backups are the cloud's own disk snapshot, the same shape as a Proxmox VM backup. A Litestream replica to the cloud's own object storage is optional, the same as it already is for Docker.

Option 2 needs no new code: no new adapter, no new CI job, no new start-script branch. The existing `CAIRN_REPLICA_URL=s3://...` path in `docker/start.sh` and `deploy/docker/env.example` already covers AWS S3 directly, since Litestream's S3 replica type is what it was written against. Option 1 would need real engineering (an EFS-backed ECS task definition and IAM policy, or accepting no persistent disk at all) to reach parity with what a VM gives for free.

## Decision

1. **AWS and GCP get a VM running Docker**, the same `deploy/docker/compose.yaml` and `docs/DEPLOY-DOCKER.md` steps used on Proxmox and any other self-hosted target. `docs/DEPLOY-AWS.md` and `docs/DEPLOY-GCP.md` cover only what is cloud-specific: provisioning the VM, its firewall rule, and where the disk and any replica live. No `deploy/aws/` or `deploy/gcp/` folder is added; there is nothing cloud-specific to check into the repository, unlike Azure's Bicep template.
2. **Proxmox gets its own guide**, `docs/DEPLOY-PROXMOX.md`, promoted out of the subsection inside `docs/DEPLOY-DOCKER.md`. It stays the same Docker-on-a-machine-you-own model; only the VM-versus-LXC and storage-mount specifics are Proxmox's own.
3. **A managed container service on either cloud stays a future option**, the same way Cosmos and DynamoDB are optional adapters in ADR-020: built if someone needs scale to zero badly enough to trade away a local disk, or needs more than one instance. Nothing here blocks it; the adapter and entry-point boundaries (ADR-005, ADR-006) are unchanged.
4. **AWS S3 as a Litestream replica needs no new plumbing**: `CAIRN_REPLICA_URL=s3://bucket/cairn.sqlite` with `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` in `.env` is exactly the example already in `deploy/docker/env.example`. `docs/DEPLOY-AWS.md` gives the exact bucket and IAM policy.
5. **Google Cloud Storage as a Litestream replica is not documented as supported.** Litestream's S3 replica type can reach GCS through its S3-compatible interoperability endpoint in principle, but this has not been tried against this project's single-URL `CAIRN_REPLICA_URL` interface, which passes the URL straight to Litestream with no config file for a custom endpoint. `docs/DEPLOY-GCP.md` recommends the VM disk's own snapshots as the backup path, the same shape as a Proxmox VM backup, and calls out the GCS replica as untried rather than claiming it works.

## Consequences

1. Three new guides, no new code, no new CI job. What already runs in CI for the Docker image and compose file covers all three targets, since they run the identical container the identical way.
2. PRD Q7's AWS half is answered for the container-hosting question ADR-020 reopened: a VM's free tier, not a managed container service's, is what a person gets on AWS. The separate Cosmos-adapter half of Q7 (full-text and vector support on shared throughput) is untouched; it still waits on that adapter being built.
3. Free-tier terms for cloud VMs move over time and are not verified by a real deployment from this repository, the same caveat ADR-018 recorded for Azure before its first real deployment. Each guide says to check current terms rather than stating a price as fact.
4. Someone who wants scale-to-zero on AWS or GCP the way Azure Container Apps gives it does not get it from these guides. That is accepted for the same reason ADR-020 accepted it for the general container path: nobody has asked for it yet, and it is a configuration change away, not a rewrite, when someone does.
