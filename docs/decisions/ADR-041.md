# ADR-041: Discovery by following citations

Status: accepted
Date: 2026-09-15
Relates to: ADR-034 (self-description), ADR-037 (trusted cairns), ADR-039 (citations as JSON-LD), ADR-040 (receiving citation notices), PRD principle 6 (bridges between Cairns)

## Context

The last item on "Bridges between Cairns" is finding a Cairn you did not already know about, without a registry: "each self-description lists the Cairns it cites, so a reader can walk outward from any one Cairn by following them, starting from whichever Cairns are already in its own or a trusted friend's list." ADR-034 shipped the shape for this, a `cites` field on `/.well-known/cairn.json`, but left it always empty, a promise rather than a working feature, because nothing yet told a citation in `sources` apart from an ordinary web link. ADR-039 answered that: a source shaped like `<origin>/w/<id>` is now recognised, per page, as `isBasedOn`. Nothing yet rolls that up to the whole-Cairn `cites` field ADR-034 defined, and nothing yet walks it.

A registry was already rejected (ADR-037): a shared server every Cairn contacts is a thing someone has to run, pay for, and keep from becoming spam-magnet infrastructure the whole network then depends on. What replaces it here is the same idea `cairn trust` used: the CLI, on the owner's own machine, acting as an ordinary client of the web, this time following links between self-descriptions instead of checking one.

This walk is unlike ADR-040's fetch. There, the server fetched an address an anonymous stranger supplied, over the open internet, which made an SSRF guard the central concern. Here, the CLI fetches addresses the owner's own trusted list (or an explicit flag) supplies, run by the owner on their own machine, exactly the posture `cairn trust` and `cairn check-sources` already have. No new fetch-safety code is needed; the concern that matters here is not running away with the owner's bandwidth or attention, a possibly large and cyclic graph of Cairns citing Cairns.

Finding a Cairn is not the same as trusting it. ADR-037 keeps trust a deliberate act: `cairn trust` checks an address is a Cairn but the owner decides whether it deserves the "Trusted cairns" row. A Cairn found by walking citations deserves the same restraint, more so, since it arrived by an automated hop rather than the owner naming it directly.

## Decision

1. **`/.well-known/cairn.json`'s `cites` field is finally filled in** (ADR-034 consequence 3): for every published page, `isBasedOn`'s addresses (ADR-039) are reduced to their origins and the whole Cairn's `cites` is the deduplicated, sorted union across every published page. Empty exactly when no published page cites another Cairn's page. Computed in the same `/.well-known/cairn.json` handler in `packages/api/src/web/public.tsx` that already builds `collections`, from data already read to serve `/w`; nothing new is fetched or stored.

2. **A new CLI-only command, `cairn discover [--from URL]... [--depth N] [--limit N] [--timeout MS]`.** A client of the web, like `cairn trust` and `cairn check-sources`, run by the owner, so it carries none of ADR-040's SSRF concern: the addresses it visits come from the owner's own starting points and, from there, from `cites` fields the walk itself reads, never from an anonymous caller. Starting points default to every url in "Trusted cairns" (ADR-037); `--from` adds more, or stands alone if "Trusted cairns" is empty. Refuses to run with nothing to start from: "no starting point. Trust a Cairn first (`cairn trust <url>`), or pass `--from <url>`".

3. **Breadth-first, bounded, cycle-safe.** From each starting Cairn, `cairn discover` reads `/.well-known/cairn.json` and queues the origins in its `cites`, one hop at a time, up to `--depth` (default 2) hops out and `--limit` (default 200) Cairns visited in total, whichever comes first. A Cairn already visited in this walk is not visited again, so a citation cycle just stops there instead of looping. An address that does not answer, or does not look like a Cairn, is recorded as unreachable and the walk continues past it: one bad node does not stop discovery of the rest, the same tolerance `check-sources` already has for a dead source.

4. **A newly found Cairn is written to a new table, "Discovered cairns", lazily created like "Trusted cairns" (ADR-037): no new storage or schema.** Fields: `url` (`url`, required), `name` (`text`, from the found Cairn's own self-description), `discovered_via` (`url`, the Cairn whose `cites` named it), `depth` (`number`, hops from a starting point), `added_at` (`date`). Upserted keyed by `url`, so running `cairn discover` again updates rather than duplicates. A Cairn already in "Trusted cairns" is never added here: it is already known, and already trusted, so a "Discovered cairns" row for it would say nothing new.

5. **Discovery never trusts automatically.** A row in "Discovered cairns" is a lead, not a decision: the owner reviews it, the same way they review any table, and runs `cairn trust <url>` themselves on the ones worth trusting. ADR-040's "Citations" table still only auto-accepts a notice from an origin in "Trusted cairns"; being in "Discovered cairns" changes nothing about how a citation notice from that address is treated.

## Consequences

1. Two small pieces of new code: the `cites` computation in `public.tsx` (server), and `packages/cli/src/discover.ts` plus a new `cairn discover` case in `main.ts` (CLI). No new port, no MCP tool, no REST endpoint: reading and reviewing "Discovered cairns" costs nothing new, the same free parity ADR-037 already established for "Trusted cairns".
2. `cites` being real, not always empty, is what makes this ADR possible at all: a walk with nothing to read at each hop is not a walk. It also means ADR-034's promise is now kept.
3. `--depth` and `--limit` trade completeness for a bounded run: a large or deeply cited network of Cairns is explored partially, not exhaustively, by one call. Running `cairn discover` again with the same or a wider `--depth` after trusting a few of what it found deepens the walk over time, the way clicking through search results does.
4. An unreachable address is reported, not fatal: `cairn discover`'s output distinguishes Cairns visited, newly found, and unreachable, so the owner can see what the walk covered without reading a stack trace. Because every url already in "Trusted cairns" is itself a starting point, a Cairn the owner already trusts is never reported as newly found, whichever citation led back to it.
5. Nothing here changes `cairn check-sources` (ADR-036), which still only checks that a source resolves, or `cairn trust` (ADR-037), which still only confirms an address answers as a Cairn. `cairn discover` composes both patterns, walking with the second's check at each hop, but adds nothing to either.
