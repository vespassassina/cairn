# ADR-063: revert the source-built Litestream, its first restore corrupted a snapshot and lost data

Status: accepted

Date: 2026-09-18

## Context

ADR-062 switched the Dockerfile's Litestream stage from a pinned, checksummed release (0.5.17) to a source build at a pinned commit on an open, unmerged upstream PR (#1514), to work around issue #1515's replica stall. It was deployed to Azure the same day and, per ADR-062's own verification standard, watched live: a fresh L9 snapshot appeared at startup and a transaction advanced through L0, L1 and L2 by 12:40 UTC, which read as confirmation the stall was fixed.

The container's own startup log told a different story, read afterwards: the restore that produced that fresh snapshot had itself just failed and recovered from a fallback path.

```
F cairn: the replica would not restore: Error: decode database: decode page 1460: copy page 1500
  header: nonsequential page numbers in snapshot transaction: 1459,1500
F cairn: restored the replica as it stood at 2026-09-18T09:32:26Z, which passed its integrity
  check. 9 later points were unreadable and left behind.
```

The source-built Litestream had written a corrupt L9 snapshot: a page ordering that should never occur in a well-formed snapshot transaction. Cairn's own restore code (`docker/start.sh`, ADR-046, hardened by the commit "Never start Cairn on a database it cannot vouch for") caught the corruption and did what it is designed to do: refuse a database it cannot vouch for, and step backward through earlier points until one passes its integrity check. That landed on the state from 09:32 UTC, nine replication points before the corrupt one, discarding every write in between. On Azure that was 13 pages, including the whole "Home Assistant & Homelab" collection, only discovered because the owner separately noticed the console showing 2 collections instead of 3.

This is not the same bug as #1515. The stall in #1515 is silent and produces no error; PR #1514's fix for it worked, exactly as its own reporter said, and the L0/L1/L2 compaction watched afterward genuinely did advance. But the same branch's snapshot writer has a defect release testing would normally catch, and an unmerged branch carries no such testing. The mitigation traded a silent stall for a silent corruption, and the corruption is worse: a stall loses no data by itself, only availability of new writes until someone notices and restarts; this corruption discarded data outright, on the very first restart.

## Decision

Revert the Dockerfile's Litestream stage to the pinned, checksummed 0.5.17 release install (ADR-062's own stated rollback plan, taken sooner than hoped). `CAIRN_BACKUP_AFTER_HOURS=0.5` on Azure stays: that path never touches Litestream, was not implicated in this loss, and is what made the loss cheap to notice and to fix.

Issue #1515 is unfixed upstream again as of this ADR. No further attempt to build against an unmerged fix is planned; the risk of a released version's own testing catching what an unmerged branch's did not is exactly what a source build gives up. Watch for a tagged Litestream release that includes a reviewed fix, and reconsider then.

## Consequences

1. The Azure replica can silently stall again under issue #1515, exactly as ADR-061 described, until a released fix exists. `CAIRN_BACKUP_AFTER_HOURS=0.5` remains the bound on how much that can lose.
2. ADR-062's verification standard (fresh writes reaching L2, sustained past L0's retention) is necessary but was not sufficient: it can pass while a restore already silently lost older data before that point. A future check of any replica change should also read the container's own startup log for a restore fallback, not only watch compaction levels advance afterward.
3. The 13 pages were recovered the same day with `cairn export --instance laptop` followed by `cairn import --instance azure` (dry run confirmed first: 13 created, 1 updated, 108 unchanged, no deletions). Plain `cairn sync` was not used for the recovery: its dry run proposed deleting those same 13 pages from the laptop copy instead, because sync's bookkeeping read Azure's post-restore state as an intentional deletion made after the last successful sync, not as data loss. That reasoning is sound for an honest two-way edit history and wrong here; anyone recovering from a replica-level loss should export/import, not sync, until the pages exist again on both sides.

## Relates to

ADR-062 (the mitigation this supersedes in part), ADR-061 (the original #1515 root cause), ADR-046 ("Never start Cairn on a database it cannot vouch for", the restore integrity check that caught this rather than serving corrupt data).
