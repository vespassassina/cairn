# ADR-064: attachments are rows plus content-addressed blobs, uploaded direct

Status: accepted, with a thumbnail decision added on acceptance

Date: 2026-09-19

Relates to: ADR-005 (adapter boundary), ADR-020 (one container, no cloud SDK outside adapters), ADR-049 and ADR-050 (the existing blob archive for backups), hard rules 1, 2, 5, 6, 9, 10, 13, 14

## Context

PRD P1 item 4 promises attachments up to 25 MB, stored via a blob adapter, not yet built. The roadmap's "more kinds of content" item lists pictures and other files as attachments through the blob adapter, and separately and deliberately keeps diagrams as text: Mermaid, kept in the page body, so an agent can write them and history, search and the sync merge (ADR-030) all work on them unchanged. This ADR is about binary files only, pictures and documents. Diagrams are not in scope here; they are already answered by "keep them as text."

Two things already exist that attachments can be built from rather than around.

1. **Tables and rows.** Cairn already has a generic, synced, exported, searched store for structured records with relation fields. Every surface (MCP, REST, CLI) already reads and writes rows (hard rule 14). Attachment metadata is a structured record with a relation to the page it belongs to: a row.
2. **A blob client with no cloud SDK.** ADR-050 built REST clients for Azure Blob Storage and S3, `packages/api/src/backup/azure.ts` and `s3.ts`, authenticated as the managed identity or the platform's own credential chain, streaming rather than buffering. They exist today only for whole-database backup files. Attachments need the same four operations, put, get, head, delete, against arbitrarily many small objects instead of one growing archive.

What does not exist, and is the actual gap: a way to move bytes between an agent or a browser and blob storage without forcing every byte through the channel meant for structured records.

MCP tool results are JSON, and hard rule 6 caps every tool at a token budget. A 25 MB image, base64-encoded, is over 33 million characters. Proxying that through a tool call is not merely slow, it is the kind of thing hard rule 6 exists to prevent. REST has the same shape of problem at a smaller scale: proxying every upload through the Node process to relay it to blob storage means buffering or streaming 25 MB through a request handler for no reason, when ADR-050 rule 7 already established that Cairn does not hold upload bytes in memory when it does not have to.

## Decision

### 1. Attachment metadata is a row in a built-in table, not a new store

A workspace gets a system table, `Attachments`, present from init like `Peptides Index` is present in a fresh peptide wiki, except this one ships with Cairn itself rather than being owner-created. Its fields:

| Field | Type | Meaning |
|---|---|---|
| `id` | string | The row id, what a page's Markdown link points at |
| `page` | relation → pages | What it is attached to. A page can have many; an attachment belongs to exactly one page, the one that first uploaded it |
| `blobKey` | string | `sha256/<hex>`, see decision 2 |
| `sha256` | string | Same value, queryable on its own, and checked on the way in |
| `filename` | string | As uploaded, shown in the UI and in exports |
| `contentType` | string | Declared by the uploader, verified against sniffed bytes, see decision 5 |
| `bytes` | number | Size, checked against the 25 MB limit before the upload URL is even issued |
| `altText` | string, optional | For images. Never required, always asked for |

This means attachments inherit, for free, everything rows already have: optimistic concurrency (hard rule 3), the sync merge, export and import, backlinks-style queries via the relation field, and REST/CLI/MCP access through the table tools that already exist. No new port, no new adapter, no new conformance suite. `core` gains no new concept; it gains one built-in table definition.

### 2. Blob content is addressed by its SHA-256, not by the row id

The bytes live at `blobKey = sha256/<hex-digest>` in a new blob container, `cairn-attachments`, alongside the replica's and the backups' (ADR-049 decision 10's reasoning applies again: keep failure domains apart). Two rows that happen to reference the same file, the same screenshot pasted onto two pages, share one blob. A delete removes the row; the blob is garbage-collected separately once no row references its key, the same shape as ADR-005 decision 2's "derived data can be rebuilt": the set of live blob keys is always recomputable from the `Attachments` table, so nothing is lost by deleting a blob too early, only a redundant re-upload if the arithmetic was wrong, and nothing is lost by running garbage collection too rarely either.

Content addressing also gives deduplication and integrity for free: the SHA-256 the client computed before upload is the same one used to name the object, and a mismatch is caught by construction rather than by a separate checksum step.

### 3. Upload and download go direct to blob storage, signed by Cairn

The client, agent or browser, never sends attachment bytes to the Cairn API. It:

1. Computes the SHA-256 and size locally.
2. Calls `POST /api/v1/attachments` (and the matching MCP tool and CLI command) with `{page, filename, contentType, bytes, sha256}`. Cairn checks the size against the 25 MB limit, checks the workspace's write permission on `page`, and returns a short-lived signed upload URL for that exact key, `abs://.../sha256/<hex>` fronted by a SAS URL on Azure or a presigned PUT on S3, plus the row it created in `pending` state.
3. Puts the bytes straight to that URL. This is the same shape ADR-050 already solved: a bearer token from the managed identity, or SigV4, minted server-side, handed to the client, never a long-lived key.
4. Calls back to confirm; Cairn does a `HEAD` against the blob to confirm the size matches what was declared, then flips the row from `pending` to committed. A `pending` row older than one hour with no matching blob is swept, so an abandoned upload leaves no orphan.

Download is the mirror image: `GET` on the row returns metadata and a short-lived signed `GET` URL, not the bytes. A page rendered in the console fetches images directly from blob storage using those URLs, not through the API server. This is the direct extension of ADR-050's "stream, don't buffer" to the read side, and it is what keeps a 25 MB attachment from ever being the API server's problem.

MCP is the forcing case. A tool that returns `{row, uploadUrl}` costs a few hundred tokens. A tool that returns the bytes costs the whole budget on one attachment and breaks hard rule 6 outright. The agent's own HTTP client does the PUT; Cairn's MCP tool never sees the bytes at all.

### 4. Referenced from the page body as an ordinary Markdown link

`![a rack diagram](attachment:<row-id>)` for images, `[the datasheet](attachment:<row-id>)` for anything else. Not a bespoke block type. This keeps pages plain Markdown, so search indexing, the sync merge and history all keep working on the page body exactly as before; only the console and the REST page-render step need to know that an `attachment:` scheme resolves to a signed URL at render time. Export rewrites these links to relative paths inside the export folder (`attachments/<row-id>-<filename>`) and writes the bytes there, so an exported wiki opens and shows its pictures with no server and no live URLs, closing the PRD P0.7 gap that named attachments as the one thing export does not carry yet. Import reverses it: bytes from the folder are re-uploaded, rows re-created, links rewritten back to `attachment:` ids.

### 5. Never served in a way a browser will execute

An attachment's declared `contentType` is untrusted input. Cairn sniffs the first bytes against it at commit time (decision 3 step 4) and rejects a mismatch outright, and refuses `text/html` and `image/svg+xml` as content types entirely: an SVG can carry a script, and Cairn has no per-attachment origin to sandbox it in. Every signed download URL sets `Content-Disposition` from the stored `filename`, and images render through the console's own `<img>` tag, which never executes what it loads. This is the direct extension of the project's standing OWASP-top-10 discipline to a feature whose entire point is hosting content it did not write.

### 6. A raster image gets a generated preview; nothing else does

An image attachment (`image/png`, `image/jpeg`, `image/webp`, `image/gif`, checked against the sniffed bytes per decision 5, `image/svg+xml` already refused) gets a small thumbnail generated at commit time, best-effort, off the critical path: the confirm step in decision 3.4 queues it after flipping the row to committed, so a slow or failed thumbnail never blocks the upload finishing. The thumbnail is stored as its own blob, `blobKey` with a `-thumb` suffix, sized to fit inside roughly 320px on the long edge, WebP, and the row gets a `thumbnailKey` field, null until the thumbnail lands, null forever if generation fails or the type isn't a raster image. A failed or missing thumbnail is not an error; the console falls back to a generic file icon and the original stays reachable exactly as decision 3 describes.

Generation uses a WASM image codec running in the API process rather than a native library, so the container stays the one small image ADR-020 asks for and no new OS-level dependency is added to the Dockerfile. This is deliberately narrow: no PDF first-page preview, no video frame extraction, no thumbnail for anything but the four raster formats above. Widening it is a smaller, separate decision once there's a real case for it, not a default to build in now.

The page-body reference from decision 4, `![a rack diagram](attachment:<row-id>)`, is what makes a picture actually show inline on a page; this decision only makes that inline image fast to load and fast to browse in a list of attachments, by giving the console something small to fetch before anyone opens the full 25 MB original.

### 7. Sync treats content as immutable, metadata as an ordinary row

A blob, once uploaded, is never edited, only referenced or not; there is nothing about a SHA-256-keyed object for the sync merge to reconcile. The `Attachments` row (its filename, alt text, or a delete) merges exactly as any other row does today, last-write-wins per field with history kept (ADR-030's merge, hard rule 9's `replaceForSource` shape does not apply here since a row is not derived data, it is itself a source of truth for its own metadata). This is also why ADR-063's lesson applies unchanged: a sync dry run before a real sync remains mandatory, and this ADR adds nothing that changes that.

## Consequences

1. No new adapter package and no new port interface. The `Attachments` table rides the existing table/row machinery; the only new server-side surface is the blob container plus the sign-and-confirm upload flow, which is an extension of ADR-050's Azure and S3 clients, not a new kind of thing.
2. The 25 MB limit is enforced twice, once before a URL is even issued (cheap, rejects obviously-too-big requests instantly) and once implicitly by the client, which is trusted to declare its own size honestly since the confirm step's `HEAD` check catches a lie.
3. Garbage collection of unreferenced blobs (originals and thumbnails alike) is a background job, not built in this ADR's first cut; until it exists, a deleted attachment's row disappears immediately but its blobs are reclaimed only by a later maintenance pass. This is safe to defer because it costs nothing but storage, the same reasoning ADR-049 used for backup retention.
4. Attachments now depend on the workspace's write permission on the owning page, reusing existing auth (ADR-007), not a new permission model.
5. Diagrams stay entirely out of this: they are Mermaid text in the page body today and stay that way. Nothing here blocks embedding a rendered diagram as a picture later, through the same `attachment:` link, if the owner ever wants a rasterized export of one, but that is a separate, smaller decision if it comes up.
6. Thumbnail generation is one more asynchronous step between "upload confirmed" and "attachment fully usable," alongside the existing background sweep for orphaned `pending` rows; both are best-effort maintenance work, not on the write path, consistent with hard rule 5's ban on optional work blocking a write.

## Decisions made on acceptance

The owner accepted this ADR on 2026-09-19 and asked for the preview capability in decision 6, added at acceptance rather than left as a later follow-up. The two other open questions carried by the proposed draft are resolved here with the recommended default, not separately confirmed line by line; flagging that so it's visible rather than silently folded in:

1. **Sharing a blob across pages** (decision 2): kept as designed, deduplication by content hash, not a private copy per upload. Revisit only if the "why didn't storage shrink" confusion turns out to bite in practice.
2. **The 25 MB ceiling**: kept as the PRD's number. Direct-to-blob upload means raising it later is a one-line change, not a redesign, so there's no cost to leaving it as is now.
3. **SVG**: kept refused outright, per decision 5's reasoning. Not revisited.
