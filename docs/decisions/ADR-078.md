# ADR-078: Knowledge approval is a mark on the page, set by a person, honoured by search

Status: proposed

Date: 2026-09-24

Relates to: ADR-028 (freshness: `verifiedAt` is a different fact), ADR-032 (publishing is the owner's act, the precedent for person-only writes), ADR-057 (search results grouped by page, where the ranking change lands), ADR-073 (stale-page reviews, which found this item was needed), hard rules 3, 7, 9, 14. Spec: `docs/specs/knowledge-approval.md`.

## Context

Agents write most of Cairn. Nothing today records whether the owner has read what they wrote and agrees with it. `verifiedAt` (ADR-028) says when a page's facts were last re-checked, by anyone, and is set by agents too; it is not the owner's judgement. The roadmap carried "Agent activity digest and approvals" as a pending state for writes, which the core does not have and which would hold agents' work back until someone looked.

The owner's direction of 2026-09-24: a person marks a page approved, neutral or disapproved; agents retrieve everything but take the mark into account, or leave unapproved knowledge out of their work; approving and reviewing must be easy; the mark survives minimal changes; a side-by-side diff against the previous version is one button away.

Options weighed with the owner: (a) a pending state for agent writes, rejected as blocking; (b) a filter that hides everything not approved, rejected because most pages will be neutral for a long time and agents would go blind; (c) a mark that ranks and annotates, hiding only what is marked wrong. The owner chose (c).

## Decision

1. **Model.** `Page` gains `approval: "approved" | "neutral" | "disapproved"` (default `neutral`), `approvalAt: string | null`, `approvalVersion: Version | null` (the version the person looked at) and `approvalPrevious: "approved" | "disapproved" | null` (set when an edit reset the mark). Source data on the page (hard rule 9), stored in three new SQLite columns with a migration, covered by the conformance suite. Rows and tables carry no mark; a later ADR if wanted.
2. **Only a person sets it.** `setApproval(context, pageId, state, version, by)` in `operations.ts` refuses `actor.kind === "agent"` with an error naming the console and `cairn approve`. No MCP tool, stated in the instructions as publishing is. Surfaces: console `POST /p/:id/approval`, REST `POST /pages/:id/approval`, CLI `cairn approve|disapprove|unmark <id>`. The CLI refuses when `CLAUDECODE` or `CAIRN_AGENT` is set in the environment, the same signals it already uses to name an agent actor (`packages/cli/src/main.ts`), and otherwise declares a person with the request header `X-Cairn-Actor: person`, which the REST route translates into a `kind: "user"` actor (a bearer or OAuth token alone still names an agent). The write carries the version token (hard rule 3) and produces a revision whose note names the new state.
3. **Carry-over on edit.** In `updatePage`, when the page is not neutral: if the title is unchanged and the characters added plus removed against the body at `approvalVersion` are at most 5 % of that body and at most 200, the mark, `approvalAt` and `approvalVersion` stay and the note gains `(approval kept: small change)`. Otherwise `approval` becomes `neutral`, `approvalPrevious` takes the old state, `approvalVersion` stays as the diff baseline, and the note gains `(approval reset: was <state>)`. The rule applies to a person's edit too; the console edit form offers `keep_approval` to override. Both numbers are constants in `operations.ts`, expected to change once from evidence.
4. **Search.** `searchPages` multiplies a page's fused score by `APPROVED_BOOST = 1.25` when approved and drops disapproved pages unless `include_disapproved` is passed (MCP `search`, REST `?include_disapproved=1`, CLI `--include-disapproved`; the console passes nothing). Every `PageHit` carries `approval`. `pnpm eval` runs before and after per backend and both numbers go in the changelog (hard rule 7).
5. **Reading.** `get_page`, REST and `cairn read` return the four fields. A disapproved page's body is returned whole, preceded by one line saying the owner disapproved it and when, and not to build on it. A neutral page with `approvalPrevious` gets a line saying it was approved and has changed since. Instructions, summary and skill say the same three sentences (documentation rule 8); the summary adds a count line.
6. **Console.** Three buttons on the page view; a `/review` queue ordered changed-since-approval first, then agent-written neutral pages newest first, then never-approved pages by inbound links; a count on the home page. `/p/:id/v/:version?view=side` renders the existing diff as two columns, stacked under 700 px, no script, with a "Side by side" button on every version page and "Changes since approval" (`?from=<approvalVersion>`) on a page whose version differs from its approved one.
7. **Sync, export, import carry the mark.** Unlike `public` (ADR-032 decision 6), the mark is knowledge about the content and belongs with it.

## Consequences

1. Agents' writes go live as today; the owner's judgement becomes a separate, visible fact that ranks and annotates rather than gates. Neutral is the honest default for most pages and costs nothing.
2. Two facts now sit on a page that look alike: `verifiedAt` (facts re-checked, by anyone) and `approval` (the owner's judgement). The page view shows both with different words; the instructions say which is which.
3. A disapproved page still exists in the graph: backlinks, neighbours and `list_children` return it with its mark. Nothing is hidden except from search results, and only there by default.
4. The thresholds and the boost are guesses. Every carry-over decision is written into the revision note, so `/changes` shows when the rule was wrong, and the eval says whether 1.25 moves anything.
5. The CLI's person-versus-agent test rests on environment variables an agent could unset. Accepted: the same trust already applies to `CAIRN_AGENT` naming, and the console is the primary surface for approving.
