# ADR-033: A refresh token answers a repeat for one minute before it counts as theft

Status: accepted
Date: 2026-09-14
Relates to: ADR-007 (auth), ADR-017 (sign-in everywhere), ADR-020 (one container, scale to zero)

## Context

ADR-017 gave Cairn OAuth with rotating refresh tokens. A refresh token is single use: presenting it exchanges it for a new pair and deletes the old record. Presenting it a second time means someone else has a copy, so the whole token family is revoked and every session from that sign-in has to connect again. That is the standard defence against a stolen refresh token, and it is worth keeping.

The problem is that a second use is not always theft. Three ordinary events look exactly the same to the server:

1. The answer never reached the client. The server rotated the token and the response was lost, so the client retries with the only token it has, which the server has already spent.
2. Two processes refresh at once. Both hold the same stored credential, both notice the access token has expired, and the second one arrives with a token the first has just used.
3. The database went backwards. Cairn runs as one container that stops after 30 minutes idle (ADR-020), with SQLite replicated by Litestream. If a rotation is written and the container stops before that write is replicated, the restored database holds the old token while the client holds the new one.

The owner hit this: the MCP sign-in stopped working without being anywhere near its 30 day lifetime. In each of these cases the honest cost is high and the security gain is nil. Revoking a family because a response was lost punishes the legitimate client for a network failure, and a thief who replays a token seconds after the real client does is not meaningfully different from one who replays it a minute later.

The options were to make refresh tokens longer lived, which does nothing here because rotation restarts the clock anyway; to drop rotation, which gives up theft detection entirely; or to allow a short window in which a repeat is treated as a repeat.

## Decision

1. **A refresh token that has just been used keeps answering for 60 seconds, with the same tokens it was already given.** The response to the first use is kept under a `refresh_replay` record keyed by the hash of the used token. A second use inside the window returns that stored response verbatim: the same access token, the same new refresh token, no further rotation.

2. **Past the window, a second use still ends the whole family.** The `refresh_replay` record expires on its own after 60 seconds, and the `refresh_used` record that drives theft detection is unchanged and still lives for the full refresh lifetime. Nothing about the revocation path changes except when it fires.

3. **A revoked sign-in stops replaying immediately.** The replay record carries its family, and a replay is refused if that family has been revoked. Revocation must not be undone by a request that arrives a moment later.

4. **The replay record is written before the record that marks the token used.** A repeat that arrives while the first request is still in flight then finds the answer rather than the evidence of theft.

5. **Nothing else about the lifetimes changes.** Access tokens stay at one hour and refresh tokens at 30 days. A longer access token is the one change that genuinely weakens the system, because access tokens are verified locally with no store read, so a revoked sign-in stays usable until its access token expires.

## Consequences

1. A lost response or a concurrent refresh no longer costs the sign-in. This is the whole point, and it is the case the owner met.

2. A stolen refresh token replayed within 60 seconds of the real client's use now succeeds instead of raising the alarm, and the thief receives the same new refresh token the real client holds. That is a real loss, bounded by the window. Past the window the behaviour is what it always was. The alternative, revoking on every lost packet, was costing more.

3. The store holds a live refresh token in readable form for up to 60 seconds, where before it held only hashes. The record's expiry is what deletes it, so the window must stay short, and this is written on the `AuthRecordKind` definition where the next person will meet it.

4. The third cause, a database restored to an earlier point, is only partly addressed. Inside a minute the replay covers it; a rollback of longer still ends the sign-in, because the client's token is genuinely absent from the restored database. Fixing that properly means refresh tokens the server can verify without a stored row, which is a different shape of system and would need its own ADR. It is not worth building until a rollback is shown to be what actually happened.

5. Every adapter that implements `AuthStore` gains a record kind. It needs no schema change: the kind is a value, not a column.
