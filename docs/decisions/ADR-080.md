# ADR-080: A mobile capture app at /m, a progressive web app with one service worker

Status: proposed

Date: 2026-09-24

Amends: ADR-009 decision 1, "What it does not do", item 3, for one file. Relates to: ADR-056 (phone layout), ADR-079 (the endpoint it posts to), ADR-075 (daily notes), ADR-010 (no sign-in on localhost), ADR-017 (auth elsewhere). Spec: `docs/specs/mobile-capture-app.md`.

## Context

The owner asked for "a simple mobile first webapp to add notes/images/files". Options: (a) a native app, rejected: two stores, signing costs, a second codebase for one form; (b) a separate front-end project with a framework, rejected by ADR-006 and ADR-009 (no build step, no client-side application); (c) server-rendered screens in the same Hono process, installable as a progressive web app, chosen. The owner picked (c).

A PWA needs a manifest, which is data, and to be useful offline it needs a service worker, which is client-side code. ADR-009 says: "No client-side application. Pages are rendered on the server and work with JavaScript off, apart from table sorting and the `/` search shortcut." A worker that queues a failed post is not an application, but the rule must say so.

## Decision

1. **Routes under `/m`**, server-rendered with the console's layout components and artifactkit tokens, a phone-first layout with a four-item bottom bar: `/m` capture (textarea, files, camera, tags), `/m/today` (the daily note with an append box), `/m/recent`, `/m/search`, `/m/p/:id` (read plus append), `/m/login`. Every screen works with JavaScript off. Editing bodies stays in the console.
2. **Manifest** at `/m/manifest.webmanifest`: `start_url: "/m"`, `display: "standalone"`, the existing icons, and a `share_target` posting multipart to `/m/share`, which calls `createDrop` (ADR-079). iOS has no share target; the person's guide gives an iOS Shortcut that posts to `/api/v1/drops` with a drop token, and the drop-token screen prints the three fields the Shortcut needs.
3. **ADR-009 amendment.** One service worker, `/m/sw.js`, plain JavaScript, no dependencies, is allowed. Its whole job: pre-cache the `/m` shell (the page, the CSS, the icons); intercept `POST /m` and `POST /m/share`, and on network failure store the form data in IndexedDB, answer a "Queued" page, register a Background Sync tag where supported and otherwise retry on the next open; never cache an authenticated GET beyond the shell; never render a page. Anything beyond that is a new ADR. The rule in ADR-009 now reads: no client-side application; pages render on the server and work with JavaScript off, apart from table sorting, the `/` shortcut, the editor preview fetch (ADR-081) and the `/m` service worker's offline queue.
4. **Auth** is the console's: session cookie and OAuth flow, `/m/login` styled for a phone. Same-origin check on every POST. Sign-out clears the queue.
5. **Capture time.** A queued drop's body carries its capture time as its first line; the revision time is delivery time.

## Consequences

1. Cairn becomes an icon on a phone with no store, no signing and no second codebase; the same container serves it.
2. The first client-side component ships. Its boundary is one file with one job, stated above, and every screen must still pass with JavaScript off (spec criterion 7), which keeps ADR-009's intent.
3. iOS is weaker: Safari-only install, storage that some versions clear after inactivity, no share target. The queue is a convenience there, and the screen says so. Background Sync is Chromium-only; the fallback retry runs on open.
4. Two layouts now exist, the console's and `/m`'s. They share components and tokens; a component that diverges is a bug.
